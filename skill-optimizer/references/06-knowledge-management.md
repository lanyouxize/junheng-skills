# 模块 6：知识沉淀与复盘机制

> 一次优化如果不留下可复用的知识，它的价值只维持到下一个 bug 为止。
> 本模块给出**四类知识库**的目录约定、**反模式库 12 条**、**最佳实践库 12 条**、
> **案例库模板 + 一个完整真实案例**、**跨 skill 经验迁移机制**、**复盘模板**与**效率度量指标**。

---

## 一、四类知识库

### 1.1 目录约定

建议在每个项目工作区下建 `knowledge/`（或复用 `report/` + `build/`）：

```
knowledge/
├── anti-patterns.md      # 反模式库：什么做法是错的、为什么错、正确做法
├── best-practices.md     # 最佳实践库：什么做法是好的、适用场景
├── cases/
│   ├── web-article-to-epub-v1.3.0-v1.5.1.md   # 优化案例库：一个技能的完整过程
│   └── <other-skill>.md
└── retro/
    └── 2026-09-14-web-article-to-epub.md      # 复盘记录（每轮一份，可并入案例）
```

### 1.2 四类知识库的分工

| 知识库 | 记什么 | 关键字段 | 使用时机 |
|---|---|---|---|
| **反模式库** | 「什么做法是错的」——陷阱、误判、踩过的坑 | 编号 / 名称 / 症状 / 根因 / 正确做法 / 来源 | 开始新优化前先扫一遍；写任务书时把相关条目标进「已知的坑」 |
| **最佳实践库** | 「什么做法是好的」及适用场景 | 编号 / 名称 / 做法 / 为什么好 / 适用场景 / 来源 | 写任务书时直接引用；新 skill 从零设计时作为默认选择 |
| **优化案例库** | 每个 skill 的完整优化过程 | 初始状态 / 问题诊断 / 优化方案 / 实施过程 / 验收结果 / 经验教训 | 遇到相似场景时找参照；向用户汇报长期进展时作为素材 |
| **跨 skill 迁移** | 把 A 的经验用到 B | 问题模式 / 匹配到的历史案例 / 适配调整 | 每次开始新技能优化时走一次迁移流程 |

### 1.3 触发时机（什么时候写）

| 时机 | 动作 |
|---|---|
| **每轮交付后（必做）** | 填写复盘模板；把本轮新发现的反模式 / 最佳实践入库 |
| **发现一个「不报错但结果错」的问题后（必做）** | 立即入库 —— 这是最高价值的一类条目 |
| **每次开始新 skill 优化前（必做）** | 扫一遍反模式库；走一次跨 skill 迁移流程 |
| 用户主动提到「这个之前是不是遇到过」 | 检索案例库，确认是否同源 |
| 一个方法在 3 个不同场景下都有效 | 提升为「最佳实践」，并写清边界 |

## 二、反模式库（初始条目 13 条，全部来自真实事故）

| 编号 | 名称 | 症状 | 根因 | 正确做法 |
|---|---|---|---|---|
| **AP-01** | 裸写 `off` 被解析为布尔 | 配置写 `off`，行为不是「关闭」而是 `False`，与预期相反 | YAML 1.1 把 `off/on/yes/no` 解析为布尔 | 配置值显式加引号 `'off'`，或在解析层做白名单校验并告警未知取值 |
| **AP-02** | `find_all` 递归取到嵌套表单元格 | 外层表单元格数比实际多，嵌套表的格子被重复计入 | `find_all` 是递归的 | 取单元格时限定层级：`table.find_all('td', recursive=False)` 或逐层遍历。**凡是计数类的收集，都要问一句「会不会递归取多了」** |
| **AP-03** | 用字节数判断「这是装饰图还是正文图」 | 一张 530×52、6742 字节的正文示意图被当图标丢弃 → 图片少 1 张 | 窄而扁的示意图压缩率极高，字节数对它是坏判据 | 正文内 `<img>` 来源的图改用**像素面积**判占位符（如面积 < 64 = 8×8）；按来源分流（`size_gate_exempt_sources`） |
| **AP-04** | 静默丢弃（最高频、最危险） | 不报错、不告警，但产物里少了东西；用户到很晚才发现 | 被过滤 / 跳过 / 降级的对象不计入任何计数器 | ① 每个「丢弃」都进计数；② 在**发生的那个阶段**就打告警；③ 把计数写进结构化报告；④ 加账目自洽校验 |
| **AP-05** | 「取首个可解析」的启发式选择 | 4 章 19 课时被判成 1 章 2 课时，且不报错 | 页面里有 7 个候选目录 JSON，只有第 7 个是本课，取首个稳定拿到别的课 | 启发式必须**打分取最优**，打分依据要能解释（命中数、路径匹配、规模）；选择结果要有证据可查 |
| **AP-06** | 用兜底值冒充真实数据 | 书名变成一串 URL；元数据看似存在，实际是垃圾 | 真实值缺失时用另一个字段兜底，且不标记 | 宁可留空 + 标记 `has_xxx=false`，也不要用其他字段冒充；需要值时从可靠来源提取（如从 `<title>` 剥站点后缀） |
| **AP-07** | 自检的 detail 无条件写死 | 结论 ✅，但详情里写着「不是合法 zip 包」 | `_check(name, ok, detail)` 的 detail 传的是固定字符串 | detail 必须随结果取值；断言登记函数里由 `ok` 决定 detail 内容 |
| **AP-08** | 分母取错位置导致账目重复计数 | 自检报「发现 20 张，但 1+20+0+0=21」 | 用了「已过滤后的列表长度」当分母，被截断的那张图同时出现在分母和丢弃列表 | 分母必须取**过滤前**的原始数量；中间态（前置丢弃 / 下载队列）单独成字段 |
| **AP-09** | 空值判断写成 `str(x) != ''` | 默认空配置每次都告警「字体不存在」 | `Path(x or '')` 的字符串形式是 `'.'`，于是「非空」恒为真 | 先判空再构造对象；**误报与漏报同样有害** —— 它训练用户忽略告警 |
| **AP-10** | 无守卫的 unwrap | 归一阶段刚生成的 `<p>`/`<ul>` 被二次 unwrap，一章少 69 个 `<p>`、5 个 `<ul>` 且无提示 | 「去标签保内容」的白名单里混进了内容型标签 | 为 unwrap 设**内容型标签守卫**（白名单只允许纯容器）；且这类结构改动要打印统计 |
| **AP-11** | 「两者必须相等」当零回归判据 | 判据失败（差 1883 字 / 5.74%），但实现是对的 | 把「有意的省略」和「意外的丢失」混在一条判据里 | 拆成两条：① 内容零丢失用逐格比对证明（1443/1443）；② 数量差异用**可归因区间**看住（每格 1.5~3.0 字） |
| **AP-12** | 把每个标题都当出书单元 | 正文被切成 410 篇，51 篇不足 100 字；出现只含一行装饰文字的空壳页 | 分组单元选错（按标题层级而非业务单元）；装饰容器被当交互容器保内容 | 分组单元按**业务语义**定（例：恒为「课时」）；装饰容器整棵删除、交互容器去标签保内容；两类语义必须在配置里分开声明 |
| **AP-13** | 验收脚本硬编码路径 | 换一台机器或换一个被测对象就跑不了；脚本只在作者机器上有效 | 技能路径、输出目录被写死在脚本里 | 一律 `argparse` 参数化（`--skill/--output/--raw-dir/--url`），自动探测 + 可执行报错 + 兼容两种文件命名；失败 `exit 1` |

**使用方式**：开工前扫一遍；写任务书时把相关条目原文复制进「已知的坑」一节。

## 三、最佳实践库（初始条目 14 条）

| 编号 | 名称 | 做法 | 为什么好 | 适用场景 |
|---|---|---|---|---|
| **BP-01** | 新功能走开关，默认保持旧行为 | 新增能力一律加配置开关：或默认关（`auto_confirm: false`），或新默认 + 保留旧行为开关（`format: list`，`paragraph` = 旧行为） | 用户可以一行配置退回旧行为，**不必回滚版本**；回滚版本会连带丢掉本轮所有其他修复 | 所有新增功能 |
| **BP-02** | 单一事实来源 | 判别逻辑只写一次，多个调用方共用（例：`figure_card_kind()` 被清单层 / 清洗层 / 汇总层三处共用） | 避免「清洗层说保留、清单层说丢弃」的分叉 | 同一判断在多处被使用 |
| **BP-03** | 零回归用逐字节判据 + 「未解释项 = 0」 | 未改动功能与上一版逐字节比对；所有差异逐条归因，归不了因的算回归 | 最强、最无争议的判据；「未解释项 0」防止把差异清单当噪音忽略 | 任何有历史产物的改动 |
| **BP-04** | A/B 对照 + 抖动基线 | 对照脚本支持第三种输入 `--rerun`（同版本重跑），先测出天然抖动项，再从差异里剔除 | 不做抖动基线，每轮都会看到一堆假差异，最后所有人开始无视差异 | 产物含时间戳 / 遍历顺序等天然差异 |
| **BP-05** | 门禁参数化 + 退出码语义 | `--skill/--output/--url` 全部可覆盖；失败 `exit 1`；结果落 JSON | 可复跑、可进 CI、可换被测对象；避免只在作者机器上能跑 | 所有验收脚本 |
| **BP-06** | 门禁反向自检 | ① 严格模式 vs 授权模式对照（未授权时必须报错）；② 配对断言（F8 该报警 / F9 不误报）；③ 故意引入错误确认能检出 | 一个永远通过的门禁比没有门禁更危险 | 所有门禁 |
| **BP-07** | 账目自洽恒等式 | 报告里写出恒等式：`前置丢弃 + 下载成功 + 跳过 + 失败 == 发现数`，不平即告警 | 把「有没有少东西」变成一个可计算的问题 | 任何「发现 N 个、处理 M 个」的流程 |
| **BP-08** | 负向用例组 | 未授权必须抛错且无产物；非 zip 必须判失败；缺图 + 空 spine 必须判失败并点名 | 证明失败路径真的会失败 | 所有验收矩阵 |
| **BP-09** | 出书后自检，失败只告警不删成品 | 产物生成后自动跑完整性自检（8 项），失败时保留产物并告警 | 用户可能就想先拿这份有瑕疵的产物 | 生成最终产物的技能 |
| **BP-10** | 阶段化告警 + 结构化报告 | 丢弃 / 跳过 / 降级在**发生的阶段**就打 stderr 告警，并落到 `chapter_stats` / 质量报告 | 用户不必等到最后才发现问题，且问题定位到阶段 | 多阶段流水线 |
| **BP-11** | 交付包解压后复跑门禁 | 解压交付包 → 比对关键文件哈希（包内 vs 技能目录）→ 用 `--skill` 指向解压目录再跑一遍专项门禁 | 证明交出去的包与测过的目录是同一份东西 | 需要打包交付的技能 |
| **BP-12** | 上架字段补全 + 范围钉死 | 补 `display_name` / `display_name_en` / `description_zh` / `description_en`；长度规范（≤20 字 / ≤150 字）、中英一致性机器校验、YAML 可解析、无 BOM/CRLF；用**逐行 diff + 全文件哈希**证明只有 1 个文件变了 | 上架被拒最常见的两类原因：字段缺失、改动夹带 | 需要平台上架的技能 |
| **BP-13** | 结构失败中止而非静默退化 | 自动发现 / 自动识别失败时返回**结构化错误并中止**，不退化成「另一种看起来能用的结果」 | 静默退化会让用户拿到一本只有一页的书，还以为成功了 | 有自动识别 / 自动选择环节的技能 |
| **BP-14** | 内容完整性开关不得用于压体积 | 体积告警时给出「调整图片宽度上限」等安全手段，并**明确警告**不要用 `min_file_size` 这类内容开关压体积 | 用内容完整性开关压体积会静默丢内容（正是 AP-03 那次事故） | 产物体积与内容完整性存在取舍时 |

**使用方式**：设计新功能时先对照 BP-01 / BP-02 / BP-05 / BP-06；写任务书时把相关条目直接引用为「必须遵守的做法」。

### 4.2 完整真实案例：`web-article-to-epub` v1.3.0 → v1.5.1

**一、初始状态**

| 项 | 值 |
|---|---|
| 起始版本 | v1.3.0（已备份镜像：`web-article-to-epub-backup-v1.3.0-20260914-005228`） |
| 结束版本 | v1.5.1 |
| 交付包 | `web-article-to-epub-v1.5.1-final.zip`（338,725 B / 12 条目） |
| 轮次 | 6 轮 |
| 用户核心痛点（原话） | 「听书的时候表格读不出来，听完不知道哪个值对应哪一列」 |

**二、问题诊断（按发现顺序）**

| # | 问题 | 严重度 | 证据 | 是否静默 |
|---|---|---|---|---|
| 1 | 只能抓单页，多页课程需手工拼 | P0 | v1.3.0 无多页入口 | 否（功能缺失可见） |
| 2 | 站点 WAF 对浏览器式请求头下发 JS 挑战页（HTTP 200，29182 字节），真页面需 `Accept: */*`（82620 字节） | P0 | 各 3 次复现（**当轮最耗时的坑**） | **是**（伪装成「站点适配问题」） |
| 3 | 内联目录取到别的课：4 章 19 课时 → 1 章 2 课时 | P0 | 页面内联 7 个 `contentTree`，仅第 7 个是本课 | **是**（不报错） |
| 4 | EPUB 书名是一串 URL | P1 | 目录 API/内联 JSON 不带课程名，旧代码用 base_url 兜底 | **是** |
| 5 | 正文丢图：266 张只进 265 张 | P0 | 530×52、6742 字节的正文示意图被 10 KB 阈值当图标丢掉 | **是** |
| 6 | 图片账目对不上：报告 265/失败 0，清单 266 条 | P1 | 被过滤的图不计入任何计数器 | **是** |
| 7 | 正文被切成 410 篇，51 篇空壳；缺口 2.3% | P0 | 分组单元选错 + 装饰容器保内容 + 清单只认块级标签 | **是** |
| 8 | 「含图 + 正文」的 figure 整块被丢 | P0 | 缺口 0.08%（105 字） | **是** |
| 9 | `off` 模式自检误报账目不平 | P1 | 分母取错位置 | **是**（新引入的缺陷） |
| 10 | 上架解析失败，缺 4 个 frontmatter 字段 | P0 | 平台报错 | 否（可见） |

> **注意这张表里「是否静默 = 是」占了 8/10**。这是本技能最重要的一条统计：**静默类缺陷是主力**，而它们只能靠拆包对数、账目校验、正反用例发现。

**三、优化方案（逐轮）**

| 轮次 | 版本 | 主题 | 核心改动 | 关键判据 | 断言 |
|---|---|---|---|---|---|
| 1 | v1.4.0 | 课程模式 | 结构发现（三路径 + 打分）/ 逐章抓取 + 断点续爬 / 合并 + 清洗层 / EPUB 直通 opt-in | 字数 126543 逐项相等；图片 266/266；表单残留 0 | 85 |
| 2 | v1.4.1 | 分篇 + 静默丢内容 | 分组单元改为「课时」/ 装饰容器整棵删除 / 裸文本包 `<p>` + 仅课程模式 | 410 → 20 篇；空壳 0；缺口 2.3% → 0.08% | 105 |
| 3 | v1.4.2 | 缺口归零 + 视频保活 | 含图 figure 登记为 card 块 / 视频链接保活不下载 / 站点预设 +2 | 缺口 → **0.00%**；包内 `.mp4` = 0；36/36 | 123 |
| 4 | v1.5.0 | 表格可朗读 | 表格额外转可朗读文本（`append` / `replace`） | 104 原表 + 104 朗读版；数据格零丢失 | 169 |
| 5 | v1.5.1 | 表格列表形式 | 列表形式（新默认）/ 两列表不嵌套 / 规则 B `tt-untitled` / 移除引导语 | 1443/1443 命中；段落 + `off` 模式**逐字节零回归**；TTS 0 违规 | 82（专项） |
| 6 | v1.5.1 | 上架字段 | 补 4 个 frontmatter 字段 + `displayName` 对齐（经批准） | 专项 32/32（包内 28/28）；范围钉死：只 1 个文件变 | 32 + 41 |

**四、实施过程（关键取舍）**

| 决策 | 选择 | 放弃 | 理由 |
|---|---|---|---|
| 直通出书怎么做 | 新增显式 opt-in（默认关）+ 可审计字段 | 取消确认门禁 | 安全的本质是「跳过这件事留下证据」，而不是「没有门禁」 |
| 体积怎么处理 | 打印体积 + 给安全压缩手段 + 警告 | 自动压缩 / 用 `min_file_size` 压 | 性能与内容完整性冲突时不替用户取舍 |
| 表格朗读版 | 保留原表（append 默认）+ 新增列表形式 | 替换原表 | 原表是原始信息，朗读版是附加能力 |
| 段落到列表 | 保留 `paragraph` 作为开关值 | 直接替换段落形式 | 用户可一行配置退回旧听感，不必回滚版本 |

**五、验收结果**

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 内容缺口 | 2.3% | **0.00%** |
| 正文 XHTML 篇数 | 410（51 篇空壳） | **20**（最小 2933 字） |
| 目录条目 | 410（3 层） | **23**（2 层） |

| 上架 | 解析失败 | 4 字段齐备，包内自洽 |

**六、经验教训**

- **提前预见到的**：零回归需要逐字节判据；新功能需要开关；验收需要脚本化。
- **意外发现的**：站点 WAF 的 JS 挑战页（伪装成站点适配问题，当轮最耗时）；「含图 + 正文」的 figure 全课程只有 1 个但直接决定缺口归零；内联目录里有别的课的 JSON。
- **判据被推翻的**：① 「列表形式与段落形式文本量必须相等」→ 改为「内容零丢失（逐格比对）+ 差异可归因（每格 1.5~3.0 字）」；② v1.4.0 的 85 项全绿被证明**覆盖面不足**（没有一项在问「章节是不是切太碎」）。
- **若重来一次会怎么做**：第 1 轮就把「打开真实产物看一眼」列为收尾必做项；第一轮就建立「账目自洽恒等式」而不是等到第 3 轮才发现账目不平；每个新增自检**当场配正反用例**（AP-08 那个自己引入的缺陷就能避免）。

**七、沉淀出的知识**：新增反模式 AP-03 ～ AP-12；新增最佳实践 BP-01 ～ BP-14（本模块第二、三节即为其最终形态）。

## 五、跨 skill 经验迁移机制

知识库的价值在于**从一个技能迁移到另一个技能**。三步：

### 步骤 1：问题模式识别

把当前问题抽象成**不依赖具体业务**的模式。识别信号：

| 信号 | 可能的模式 |
|---|---|
| 「不报错，但结果少了东西」 | AP-04 静默丢弃 |
| 「同一段逻辑在多处各写了一遍，改了一处漏了一处」 | BP-02 单一功能来源 |
| 「自动识别偶尔选错，且不会报错」 | AP-05 启发式选择 |
| 「新功能上线后，老功能悄悄变了」 | BP-03 / BP-01 零回归与开关 |
| 「自检从上线起从没失败过」 | BP-06 门禁反向自检 |
| 「换个环境就跑不起来」 | AP-13 验收脚本硬编码路径 / 隐性维度 7 可迁移性 |

### 步骤 2：解决方案匹配

在知识库里找同模式的条目，读它的**根因分析**和**正确做法**，而不是只读结论。例如「静默丢弃」的通用解法是四件套：每个丢弃进计数 → 在发生阶段告警 → 写入结构化报告 → 加账目自洽校验。

### 步骤 3：适配调整

**不要照抄，要适配**。适配时问三个问题：

1. 这条经验的前提在这个技能里成立吗？（例：不是所有流程都有「发现 N 个」这个分母）
2. 判据的强度可以保留吗？（例：没有历史产物时无法用逐字节，那就退到「与基准版本逐项计数相等」）
3. 有没有相反的约束？（例：某个技能的产物不含时间戳，就不需要抖动基线）

**迁移示例（真实推演）**：假设要优化一个「批量文件重命名」技能，用户抱怨「有几个文件没改到」。

- 模式识别 → 「不报错，但结果少了东西」→ AP-04；
- 方案匹配 → 四件套：① 每个跳过都进 `skipped_*` 计数；② 跳过的当下就打告警（「跳过 3 个：文件名含非法字符」）；③ 落一份 CSV 报告；④ 加恒等式校验 `输入总数 == 重命名成功 + 跳过 + 失败`；
- 适配 → 该技能没有「过滤前/过滤后」两段，分母直接取扫描总数；因为无历史产物，零回归判据改为「未命中的文件列表与上一次运行集合相同」。

## 七、效率度量指标

| 指标 | 定义 | 本案例实测 | 用途 |
|---|---|---|---|
| **平均每轮迭代周期** | 从上一轮报告落盘到本轮报告落盘的时间 | 第 1 轮 ≈ 39 分钟（00:52 备份 → 01:31 报告）；第 2 轮 ≈ 39 分钟（01:36 → 02:15）；第 3 轮 ≈ 52 分钟 | 判断「这一版该拆几轮」；周期突然变长通常说明判据出了问题 |
| **问题首次识别率** | 首轮就发现的问题数 ÷ 全周期发现的问题总数 | 6 轮共 10 类主要问题，首轮识别 1 类（**10%**） | 本案例的结论：**多阶段流水线类技能的缺陷绝大多数在后几轮才暴露**，所以要预留轮次预算 |
| **回归率** | 优化引入的新缺陷数 ÷ 优化改动数 | 六轮中出现 **1 个自引入缺陷**（AP-08 分母取错位置 / AP-09 空值判断），占比很低但影响自检可信度 | 回归率 > 0 时应要求「每个新增自检配正反用例」（BP-06） |
| **用户满意度** | 是否还需要追加修改；追加轮次是否为「修正方向」而非「新增需求」 | 表格朗读版：v1.5.0 → v1.5.1 是**修正方向**（1 次追加后收敛） | 追加多为「修正方向」= 第 2 步需求具象化没做够；追加多为「新增需求」= 正常迭代节奏 |

**看指标的三个经验**：

1. **周期突然变长** → 大概率是判据没定清楚，执行方在反复试探；
2. **问题首次识别率低** → 正常现象，但**要在任务书里预留「下一轮修静默缺陷」的位置**，别把第 1 轮的任务书排满；
3. **自引入缺陷 > 0** → 不要只修那个 bug，要检查同类判据（AP-08 修好后立刻补了 F8/F9 正反用例）。
