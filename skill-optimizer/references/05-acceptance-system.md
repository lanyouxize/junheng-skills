# 模块 5：硬判据验收体系

> 验收的目标不是「证明我做完了」，而是**「证明改对了、而且没改坏」**。
> 本模块给出：3 条核心原则、模糊需求→硬判据的转化表、6 维验收模板、门禁脚本设计规范、
> 反向自检机制，以及一个真实案例的 **321 项断言体系**拆解。
> 案例全部来自 `web-article-to-epub` v1.3.0 → v1.5.1。

---

## 一、三条核心原则

### 原则 1：能用数据证明的，不用主观判断

| ❌ 主观表述 | ✅ 数据证明 | 真实实测 |
|---|---|---|
| 「内容很完整」 | 逐单元格比对，非空数据格全部命中 | **1443/1443** 命中 |
| 「没有回归」 | `off` 模式 21 篇正文 XHTML 与上一版**逐字节相同** | 逐字节相同，未解释项 **0** |
| 「体验好」 | TTS 顺畅性 0 违规（连续标点 / 标签·实体·URL 残留 / 机械报数） | 各 **0** 处 |
| 「图片都在」 | 图片数 266/266，ID 全局连续无缺口，账目自洽 | 全下载，缺口 0 |
| 「清洗干净了」 | 8 类表单元素计数 = 0；class 唯一 token 数 | 表单 **0**；class **57 → 1** |
| 「体积正常」 | 打印体积 + 图片数 + 最大分辨率 | 106.3 MB / 266 张 / 最大 3840×1986 |

**为什么这条原则最重要**：主观判断无法复跑、无法对比、无法交给第三方验证。而数据可以。一旦判据变成数据，争论「改好了没有」就变成了跑一次脚本。

### 原则 2：零回归是底线，不是目标

「新功能生效」与「旧功能零回归」必须**同时**证明，缺一不可。

**最强判据的优先级**（从上到下依次降级，能用上面的就不要用下面的）：

| 强度 | 判据形式 | 真实用法 |
|---|---|---|
| ★★★★★ | **与上一版逐字节相同** | 段落模式 104/104 个 div 逐字节相同；`off` 模式 21 篇 XHTML 逐字节相同 |
| ★★★★ | 与上一版**逐项计数相等** | `p/table/ul` = 1680 / 104 / 109，与清洗层逐项相等 |
| ★★★ | 与上一版**行为一致**（A/B 对照 + 抖动基线） | 单篇模式对照：A = 旧版产物，B = 新版产物，`--rerun` = 同版本重跑 |
| ★★ | 关键字段抽查 | 仅在没有其他办法时使用 |
| ★ | 「应该没改到」 | **禁止作为判据** |

**关于「未解释项 = 0」**：做 A/B 对照时一定会出现差异（时间戳、文件遍历顺序、CSS 追加）。要求是**每一条差异都被归因**：「OPF 时间戳」属于天然抖动，「CSS 新增」属于本轮预期改动 —— 归不了因的差异就是回归。这句话是整个零回归判据的灵魂。

### 原则 3：门禁脚本化，可复跑

- 验收标准必须固化为**脚本**，而不是一份「检查清单文档」；
- 每次修改后**自动运行**，避免人工核对的遗漏和主观性；
- 脚本必须**参数化**（换技能路径、换被测对象不用改代码）；
- 脚本失败必须给出**正确的退出码**（`exit 1`），否则它无法进 CI；
- 门禁自身也要有**反向自检**能力（见 §五）。

## 二、模糊需求 → 硬判据 转化表（10 组真实案例）

这是本模块最实用的一页：左边是用户会说的话，右边是可直接写进验收清单的判据。

| # | 用户原话（模糊） | 硬判据写法 | 实测结果 |
|---|---|---|---|
| 1 | 「内容不要丢」 | 逐数据单元格比对，非空格 100% 命中，报出分子/分母 | 1443/1443 |
| 2 | 「读起来要顺」 | TTS 顺畅性 0 违规：无连续标点、无标签/实体/URL 残留、无机械报数 | 各 0 处 |
| 3 | 「不要太复杂」 | 最简用法只需 1 个必需参数（URL），全链路跑通并产出全部产物 | 单篇模式产出 7 件，EPUB 4.14 MB |
| 4 | 「不要改坏老功能」 | 未改动功能与上一版**逐字节相同** | 21 篇 XHTML 逐字节相同 |
| 5 | 「原来的东西还要留着」 | 原表 104 个全保留 + 朗读版 104 个全生成 | 104 + 104 |
| 6 | 「手机电脑都要能用」 | 跨平台：路径不硬编码、编码显式 UTF-8；同一命令在三平台可跑 | — |
| 7 | 「别老报一些没用的警告」 | 默认配置下告警数 = 0；每条告警都必须对应一个真实问题 | 修复「默认空字体路径却告警」后 → 0 |
| 8 | 「跑得快一点」 | 与基准版本对比耗时 / 资源占用，给出百分比 | — |
| 9 | 「文件别那么大」 | 打印体积 + 图片数 + 最大分辨率；≥ 阈值时给压缩手段 | 109 MB → 提示设图宽 1200 |
| 10 | 「要能上架」 | frontmatter 必需字段存在 + 长度合规 + 中英一致 + YAML 可解析 + 包内自洽 | 专项 32/32（包内 28/28） |

**写判据时的三个自问**：

1. 这个数字的**分子和分母**分别是什么？（只写「命中率 100%」不够，要写「1443/1443」）
2. 这条判据**失败了会不会被立刻发现**？（判据必须能真的失败）
3. 这条判据**有没有可能被偷换口径**？（例：把「逐字节」偷换成「字数接近」—— 所以口径要写进判据文字里）

## 三、验收维度模板（6 维）

| 维度 | 验收项示例 | 硬判据方法 | 真实案例 |
|---|---|---|---|
| **功能验收** | 新功能是否按预期工作 | 输入输出比对、特定行为断言 | 默认 `format=list`、`max_depth=2`；外层 `<li>` = 行标题 |
| **内容完整性** | 数据是否丢失 | 逐元素比对、计数核对（必报分子/分母） | 1443/1443 数据格；`p/table/ul` 逐项相等 |
| **零回归** | 旧功能是否被破坏 | 与上一版逐字节比对、行为一致性、抖动基线 | 段落模式 104/104 div 逐字节；off 模式 21 篇逐字节 |
| **结构合法** | 输出格式是否正确 | schema 校验、解析器验证、拆包核对 | EPUB 自检 8/8；XHTML 良构；mimetype 首位且内容正确 |
| **性能基准** | 是否有性能退化 | 与基准版本对比耗时 / 资源 / 体积 | 体积告警：106.3 MB / 266 张 / 最大 3840×1986 |
| **文档配置** | 文档是否同步更新 | 版本号一致性、配置键存在性、文档与配置默认值一致 | 三处版本号一致（frontmatter / yaml 注释 / 变更记录） |

### 3.1 每组验收必须包含的「四类断言」

一个成熟的验收矩阵，每一轮都应该包含这四类：

| 类型 | 作用 | 真实例子 |
|---|---|---|
| **正向断言** | 证明该做的做了 | 「104 个朗读版全部生成」 |
| **负向断言** | 证明不该出现的没出现 | 「表单元素全为 0」「包内 `.mp4/.mov` 数量 0」 |
| **边界断言** | 证明极端输入下行为正确 | 「`date_published` 为空时 `has_date=false` 且**不报错**」 |
| **配对断言** | 一正一反看住同一条逻辑 | 「账目有差额时**必须**告警（F8）/ 账目平衡时**不得**误报（F9）」 |

> **配对断言是最容易被漏掉、也最有价值的一类**。它的来源是一个真实教训：新增「账目自洽校验」后，因为分母取错位置，它变成了一个**天天误报的噪音**；如果没有 F9（平衡时不得误报），这个错误会一直存在，并且训练用户忽略这条告警。

### 3.2 负向用例组示例（真实）

| # | 负向输入 | 期望行为 | 实测 |
|---|---|---|---|
| 1 | 未授权的直通出书 | 抛 `PermissionError` 且**不产生任何产物** | ✅ |
| 2 | 非 zip 文件 | 自检判定失败 | ✅ |
| 3 | 缺图 + 空 spine | 自检判定失败并**点名**缺失项 | ✅ |
| 4 | 账目有差额 | 必须告警 | ✅（F8） |
| 5 | 账目平衡 | 不得误报 | ✅（F9） |
| 6 | 空配置的字体路径 | 不得产生告警 | ✅ |

## 四、门禁脚本建设指南

### 4.1 设计规范

| 要求 | 说明 |
|---|---|
| **一功能一脚本** | 每个核心能力对应一个专项校验脚本（如「表格专项」「章节拆分专项」「frontmatter 专项」） |
| **参数化** | `--skill` / `--output` / `--raw-dir` / `--url` 全部可覆盖；不硬编码路径 |
| **自动探测 + 可执行报错** | 找不到被测产物时给出「该跑什么命令」的提示，而不是抛堆栈 |
| **结构化输出** | 结果落 JSON（通过数 / 失败数 / 每项详情），可被其他工具消费 |
| **退出码语义** | 全绿 `exit 0`；有失败 `exit 1` |
| **可复跑** | 任何时间任何人跑，结果一致（除已声明的抖动项） |
| **汇总脚本** | 一个 shell 汇总脚本串起全部门禁，输出「摘要」（便于一眼看全绿） |

### 4.2 Python 门禁脚本骨架

```python
#!/usr/bin/env python3
"""<skill 名称> <专项名> 门禁 —— 可复跑、可参数化。

用法:
    python check_xxx.py [--skill PATH] [--output PATH] [--out REPORT.json]
退出码:
    0 = 全部通过    1 = 存在失败项
"""
import argparse, json, sys
from pathlib import Path

def check(results, name, ok, detail=""):
    """统一的断言登记函数。

    注意：detail 必须随结果取值，不能在通过时也写着失败描述。
    真实教训：曾出现「结论 ✅ 但 detail 写着『不是合法 zip 包』」——
    根因是 detail 被无条件写成固定字符串。
    """
    results.append({"name": name, "ok": bool(ok), "detail": detail if not ok else ""})

def main() -> int:
    ap = argparse.ArgumentParser()
    ap.add_argument("--skill", default=str(Path.home() / ".workbuddy/skills/<name>"))
    ap.add_argument("--output", default="output/<case>")
    ap.add_argument("--out", default=None, help="结果 JSON 落盘路径")
    args = ap.parse_args()

    skill, out = Path(args.skill), Path(args.output)
    results = []

    # ---- 前置探测：给出可执行的报错 ----
    if not (skill / "SKILL.md").exists():
        print(f"[错误] 技能目录不存在或缺少 SKILL.md: {skill}", file=sys.stderr)
        print(f"[提示] 用 --skill 指定技能目录", file=sys.stderr)
        return 1

    # ---- 断言组 A：功能 ----
    check(results, "A1 产物存在", (out / "article.html").exists())
    # ...
    # ---- 断言组 B：内容完整性（必报分子/分母）----
    td_found, td_total = 1443, 1443
    check(results, "B12 数据格逐格比对", td_found == td_total, f"{td_found}/{td_total}")
    # ---- 断言组 C：零回归 ----
    # ---- 断言组 D：反向用例 ----
    #     D8 有差额时必须告警；D9 平衡时不得误报（配对断言）
    # ---- 断言组 E：文档与配置 ----

    passed = sum(1 for r in results if r["ok"])
    failed = [r for r in results if not r["ok"]]
    label = skill.name
    print(f"\n===== {label} 门禁结果 =====")
    print(f"通过：{passed}/{len(results)}")
    for r in failed:
        print(f"  ❌ {r['name']}  {r['detail']}")

    if args.out:
        Path(args.out).write_text(json.dumps(
            {"skill": str(skill), "passed": passed, "total": len(results),
             "results": results}, ensure_ascii=False, indent=2), encoding="utf-8")
    return 1 if failed else 0

if __name__ == "__main__":
    sys.exit(main())
```

### 4.3 交付包自洽门禁（容易被忽略的最后一道）

最容易被漏掉、但价值很高的一道门禁是：**解压交付包后，在解压目录上复跑专项门禁**，并比对哈希。

```bash
# 第 8 道门禁：解压交付包后复跑（证明交付包自洽）
rm -rf /tmp/pkgcheck && unzip -qo "$ZIP" -d /tmp/pkgcheck
# ① 关键文件哈希一致性（包内 vs 技能目录）
shasum -a 256 /tmp/pkgcheck/<skill>/main.py "$SKILL/main.py"
# ② 包内独立跑专项门禁（用 --skill 指向解压目录）
"$PY" build/check_xxx.py --skill /tmp/pkgcheck/<skill>
```

**它防的是什么**：本机目录里能跑，但交出去的包缺文件、文件是旧版本、路径写死指向本机 —— 这类问题在「用户下载安装后才发现」之前，应该被最后一道门禁拦住。真实案例：frontmatter 补全那一轮，技能目录跑出 **32/32**，解压包跑出 **28/28**（包内条目数不同），两个数字都被记录 —— 差异本身被核对了，而不是无视。

## 五、门禁的反向自检（防止门禁「放水」）

**一个永远通过的门禁比没有门禁更危险** —— 它给所有人虚假的安全感。因此门禁需要具备**证明自己能失败**的能力。四种真实做法：

| # | 做法 | 真实实现 | 证明了什么 |
|---|---|---|---|
| 1 | **配对断言** | F8「账目有差额时必须告警」/ F9「账目平衡时不得误报」 | 检查既不会退化成摆设，也不会变成噪音 |
| 2 | **负向用例组** | 未授权直通必须抛 `PermissionError`；非 zip 必须判失败；缺图 + 空 spine 必须判失败并点名 | 失败路径真的会失败 |
| 3 | **严格模式 / 授权模式对照** | frontmatter 门禁在「严格模式（未授权对齐）」下必须报 **3 条失败**，在授权模式下 **32/32** | 门禁按规则判定，不是恒真 |
| 4 | **故意引入错误** | 人为制造一个缺陷（如删一个字段、改一个默认值），确认门禁**能检出** | 门禁覆盖了该缺陷 |

> **最好的反向自检是第 3 种**：不需要额外构造错误，「严格模式 vs 授权模式」的差异本身就是证据 —— 同一批断言，换个条件就该失败，说明它真的在看条件。

**没有反向自检时的典型症状**：
- 门禁从上线起一直是 100% 通过，从未有过失败记录；
- 出现问题时，报告说「门禁全绿」，而用户已经看出了问题（**全绿陷阱**）；
- 告警天天刷屏，用户已经习惯性忽略。

## 六、真实案例：321 项断言体系的组成

`web-article-to-epub` v1.5.1 的门禁由 **8 道**组成，核心五道共 **321 项**断言：

| 道 | 脚本 | 断言数 | 管什么 |
|---|---|---|---|
| 1 | `check_tables_v151.py`（表格列表形式专项） | **82** | 12 项功能 + 内容完整性 1443 格 + 规则 A/B/qa/compare/plain 各模式的渲染正确性 |
| 2 | `acceptance_v140.py`（验收矩阵） | **169** | A 配置 / B 清洗 / C 图片 / D 元数据 / E EPUB / F 负向 / G 视频 / H 表格 等分组 |
| 3 | `check_offline.py`（离线链接化） | **24** | 离线场景下的链接与资源完整性 |
| 4 | `check_epub_split_v141.py`（章节拆分 / XHTML 良构） | **26** | 分篇粒度、目录层级、XHTML 良构 |
| 5 | `check_single_mode_v142.py`（单篇模式 A/B 对照） | **20** | 零回归：A = 旧版、B = 新版、`--rerun` = 抖动基线 |
| | **小计** | **321** | |
| 6 | `check_index_html_v151.py`（文档静态门禁） | 41 | 结构、外链、内容齐备 |
| 7 | `check_index_render.py`（文档真实渲染与交互） | 不计入 | Chromium 无头真实渲染 + 真点击 + 截图 |
| 8 | 解压交付包后复跑 | 复用 1/6 | 证明交付包自洽 |

**演进轨迹**（断言数随轮次增长）：

| 版本 | 断言数 | 增长原因 |
|---|---|---|
| v1.4.0（第 1 轮） | 85 | 建立矩阵：配置 15 + 清洗 24 + 图片 14 + 元数据 11 + EPUB 11 + 负向 10 |
| v1.4.1（第 2 轮） | 105 | 脚本参数化 + 补 20 项 |
| v1.4.2（第 3 轮） | 123 | 新增视频链接、epubcheck、单篇回归断言（+18） |
| v1.5.0–v1.5.1（第 4–5 轮） | 169 | H 组升级为 v1.5.1 口径 + 表格专项独立成 82 项 |

> **一个健康的门禁体系是会长大的**：每修一个 bug，就补一条断言，防止它回来。**断言数只增不减**是这条原则的量化体现。

## 七、验收中最常见的六种误判

| # | 误判 | 症状 | 正确做法 |
|---|---|---|---|
| 1 | **全绿陷阱** | 85/85 全绿，但用户打开产物一眼看出问题 | 判据要有覆盖面；收尾必须**人工看一眼真实产物** |
| 2 | **口径偷换** | 「逐字节零回归」被执行成「字数接近」 | 把口径写进判据文字；复跑时逐条核对口径 |
| 3 | **判据口径本身错了** | 「两种形式文本量必须相等」→ 判据失败，但实现是对的 | **判据失败时先怀疑判据**：把「相等」改成「可归因区间」 |
| 4 | **只验新功能** | 老功能「应该没事」 | 零回归单列一组断言，越严越好 |
| 5 | **自检无反向用例** | 自检从上线起从未失败过 | 配对断言 / 严格模式 / 故意引入错误 |
| 6 | **详情与结论矛盾** | 结论 ✅，detail 写着「不是合法 zip 包」 | 断言登记函数里 detail 必须随结果取值 |
