# 模块 4：结构化任务指令生成模板

> 需求确认后，把它翻译成**执行方能照着做、能被验收**的任务书。
> 一个好的任务书让执行方不需要猜、不需要扩大范围、不需要自己定质量标准。
> 案例：`web-article-to-epub` 的三份真实任务书（课程模式 / 表格列表形式 / 上架字段补全）。

---

## 二、五条生成原则（附真实教训）

### 原则 1：验收标准必须可量化、可验证

**禁止出现的词**：优化体验、更稳定、更友好、性能提升、基本完成、差不多了。

| ❌ 不合格写法 | ✅ 合格写法 |
|---|---|
| 「表格转换效果更好」 | 「104/104 个表格全部转成嵌套列表；1443/1443 非空数据格逐格比对命中」 |
| 「内容不丢失」 | 「正文缺口 0.08% → 0.00%；`p`/`table`/`ul` 计数与清洗层逐项相等（1680 / 104 / 109）」 |
| 「兼容旧配置」 | 「单页模式默认值逐项不变：图片上限 20 / 总字节 100 MB / 图宽 1200 / 旧签名 / 默认键值」 |
| 「错误处理更清晰」 | 「未授权直通抛 `PermissionError` 且**不产生任何产物**（负向用例断言）」 |

**真实教训**：v1.4.0 的任务书写了「验收矩阵 85 项」，全部通过；但**读者打开产物一眼就看出问题**。原因是那 85 项里没有一项在问「章节是不是被切得太碎」—— 判据的**覆盖面**比判据的**数量**重要。所以现在写判据时要额外问一句：**这组判据能覆盖用户会用到的每一种场景吗？**

### 原则 2：每轮只聚焦 1–2 个核心问题

**反例**：一轮里同时做「课程模式 + 图片配额 + 目录分层 + 清洗层 + EPUB 直通」。这不是「效率高」，这是把回归风险叠加到无法定位。

**正例**：v1.4.1 一轮只做三件同源的事（分篇粒度、装饰残留、静默丢弃），因为它们的根因都在「清单与分组逻辑」这一处；v1.4.2 一轮只做「内容缺口归零 + 视频链接保活」。

**判断方法**：如果一轮里有两个改动会**同时改变同一份产物的同一部分**，就拆成两轮。

### 原则 3：明确边界 —— 什么要改、什么不要改

**真实教训**：v1.5.1 的表格列表形式任务里，有一处极易被顺手改坏的逻辑 —— 段落形式。它是 v1.5.0 的既有行为，业务上已被验证、用户可能正在用。任务书因此写了**双向约束**：

- 要改：列表形式的渲染（新增）；
- 不要改：段落形式的输出（必须与上一版**逐字节相同**）。

结果：`format: paragraph` 与 v1.5.0 对照产物 **104/104 个 div 逐字节相同**，文本量 `32823 = 32823`。

> 写边界的技巧：**不要只写「不要动 X」，要写「不要动 X，判据是 Y」**。前者是意愿，后者是可验证的约束。

### 原则 4：给出执行顺序

**真实教训**：v1.4.1 的三个缺陷里，「装饰容器被当成交互容器保留内容」这一处，修改点位于清洗流程的步骤 3a。如果先改后面「包裸文本」的步骤，再改清洗步骤，那么新包的 `<p>` 会被后来的清洗二次处理 —— 这正是项目里真实发生过的 bug：归一阶段刚生成的 `<p>`/`<ul>` 被二次 unwrap，**一章少 69 个 `<p>`、5 个 `<ul>` 且无任何提示**。

所以任务书要写明：**先改哪一步、后改哪一步**，以及每步后跑什么命令确认没跑偏。

### 原则 5：保留退路 —— 用开关控制新行为

**真实做法（三种形态）**：

| 形态 | 真实例子 | 效果 |
|---|---|---|
| 新能力默认**关** | `epub.auto_confirm: false`（直通通道）；`--tables-to-text off` | 旧用户完全不受影响 |
| 新行为为新默认，但**保留旧行为开关** | `tables_to_text_format: list`（新默认）｜`paragraph`（= 旧行为） | 用户可以一行配置退回旧听感，**不必回滚版本** |
| 新模式自动适配，**旧模式默认值冻结** | 课程模式自动切到 500 张 / 1 GB / 不限图宽；单页模式默认值逐项不变 | 新模式不污染老模式 |

> **「不需要回滚版本」本身就是一项交付质量**。回滚版本会连带丢掉这一版所有其他修复。

## 三、真实示例

### 示例 1：v1.4.0 课程模式（大改动 + 分阶段）

````markdown
# 任务：web-article-to-epub v1.4.0 —— 支持多页课程合并出书

> 本轮聚焦：让「课程 → 章 → 课时」的多页站点能一次抓取、合并成一本书
> 前置条件：v1.3.0 产物已备份至 web-article-to-epub-backup-v1.3.0-20260914-005228

## 一、背景与问题
| # | 问题 | 证据 | 复现方式 |
|---|---|---|---|
| 1 | 只能抓单页，多页课程需手工逐页抓 + 手工拼 | v1.3.0 无任何多页入口 | 对课程 URL 执行默认命令，只得到 1 篇正文 |
| 2 | 私有对象存储的正文页需要签名，直接请求拿不到内容 | 章节 URL 直连返回拒绝 | 直接请求章节 URL |
| 3 | 出书前卡在交互确认，无法无人值守 | — | 非交互场景执行到底会停住 |

根因：抓取链路按「单页」设计，缺少结构发现、逐章抓取、合并三层；确认门禁是硬性交互。

## 二、核心改动
### 改动 1：课程结构自动发现
- 改什么：新增 `discover_course_structure()`：三条路径「站点目录 API → 页面内联目录 JSON → DOM」
- 怎么改：**候选必须打分取最优**（`courseId` 命中数 → URL 路径数字命中数 → 有内容 URL 章数 →
  章数 → 课时数），不得「取首个可解析」；全部失败返回**结构化错误并中止**，不得静默退化为单篇抓取
- 预期效果：实测 4 章 / 19 课时，`via=api`
- 风险：页面内联了同站其他课程的目录 JSON（实测 7 个 `contentTree`），打分逻辑错则抓到别的课

### 改动 2：逐章抓取 + 断点续爬
- 改什么：新增 `fetch_course_pages()`；`raw/chapter_NN.html` 增量落盘
- 怎么改：私有对象存储正文先经站点签名接口换临时地址；`resume=true` 支持断点续爬
- 预期效果：4 个章节全部抓取，失败 0

### 改动 3：合并与清洗
- 改什么：新增 `merge_course_html()`（标题层级归一 h1=章 / h2=课时 / h3=小节）、
  `sanitize_course_content()`（清表单控件 / `data-*` / `aria-*` / `role` / 站点私有 class）
- 怎么改：清洗顺序不可颠倒；容器类标签 unwrap 前必须判断**内部是否含内容型标签**
  （否则刚生成的 `<p>`/`<ul>` 会被二次 unwrap）
- 预期效果：表单元素全为 0；class token 由 57 收敛到 1

### 改动 4：EPUB 直通通道（显式 opt-in）
- 改什么：`epub.auto_confirm`（默认 `false`）、`epub.output_path`、CLI `--epub-direct`
- 怎么改：自动建清单 → 写入确认字段（`user_confirmed` / `confirmed_at` /
  `confirmed_change_count`）→ 断言 → 出书；**未授权抛 `PermissionError`**；
  `editing.require_user_confirmation` 恒为 `true`
- 预期效果：无人值守可用，且事后可审计

## 三、配置项变更
| 配置键 | 变更 | 默认值 | 兼容性 |
|---|---|---|---|
| `course_mode.*` | 新增 | 见配置档 | 不配置则完全走旧单页路径 |
| `epub.auto_confirm` | 新增 | `false` | 默认关，旧行为不变 |
| `images.size_gate_exempt_sources` | 新增 | `['img-tag']` | 正文内 `<img>` 改用像素面积判占位符 |
| 单页模式所有键 | **不变** | 图片 20 / 100 MB / 宽 1200 | 逐项冻结 |

## 四、验收标准（节选）
### A 功能
- [ ] 单条命令端到端跑通：`--course-mode --epub-direct -o <out>`
- [ ] 结构发现 4 章 / 19 课时，`via=api`
- [ ] 图片 266/266 全下载，ID 全局连续无缺口
- [ ] EPUB 生成，自检 8/8 通过，目录锚点全部有效

### B 内容完整性
- [ ] 正文字数 126543 与 v1.3.0 手工链路**逐项相等**
- [ ] `h1/h2/h3 = 4/19/386`，`p=1666`，`table=104`，`ul=109`
- [ ] 表单元素（input/textarea/select/option/button/form/fieldset/label）全为 0
- [ ] class 唯一 token 数 = 1

### C 零回归
- [ ] 单页模式：图片上限 20 / 总字节 100 MB / 图宽 1200 / 旧签名 / 默认键值 全部不变
- [ ] `editing.require_user_confirmation` 恒为 `true`

### D 反向用例
- [ ] 未授权直通 → 抛 `PermissionError` 且**无产物**
- [ ] 非 zip 文件 → 自检判失败
- [ ] 缺图 + 空 spine → 自检判失败并**点名缺失项**
- [ ] 账目有差额时必须告警；账目平衡时**不得**误报

## 七、不要做的事
- ❌ 不要修改单页抓取链路的任何默认值
- ❌ 不要取消 `require_user_confirmation`（只允许新增显式 opt-in 通道）
- ❌ 不要用 `images.min_file_size` 这类内容完整性开关来解决体积问题
````

**这一轮的实际结果**：验收矩阵 **85/85** 全绿；但紧接着的 v1.4.1 一轮暴露出三个**任务书未预见**的静默缺陷（分篇 410 篇、装饰残留 23 处、内容缺口 2.3%）。

> **这说明什么**：任务书能保证「你要求的被做对了」，但保证不了「实现者是完备的」。所以任务书里要专门留一组**反向用例**和**零回归判据**，它们的作用就是在执行方自己没想到的地方设一道网。

### 示例 2：v1.5.1 表格朗读版列表形式（中等改动 + 强零回归）

````markdown
# 任务：web-article-to-epub v1.5.1 —— 表格朗读版改为「列表形式」

> 本轮聚焦：把表格朗读版从「段落形式」改为「嵌套列表形式」，让 TTS 听得出列归属
> 前置条件：v1.5.0 已交付（段落形式），门禁全绿

## 一、背景与问题
| # | 问题 | 证据 |
|---|---|---|
| 1 | 段落形式下每行是一个 35~50 字长句，TTS 只在句号间停顿，听者分不清列归属 | 用户原话：「听完不知道哪个值对应哪一列，一串念下来糊在一起」 |
| 2 | 表格前的引导语冗余 | v1.5.0 默认会插入引导语 |
根因：段落形式把「行标题 + 各列值」压成一个句子，丢失了「列」这个结构维度。

## 二、核心改动
### 改动 1：新增列表渲染形式（新默认）
- 改什么：`tables_to_text_format: list | paragraph`，默认 `list`
- 怎么改：
  - 三列表（规则 A）：外层 `<li>` = 行标题（加粗），内层 `<li>` = 「列名：值」；列名与值用「：」连接，**不得使用「是」**
  - 两列表：**不嵌套**，直接输出「行标题：值」（有意省略重复列名）
  - 规则 B（第一列本身是数据）：外层 `<li>` 不写行标题，外层 `<ul>` 加 `tt-untitled` 类，CSS 去掉该层项目符号与缩进
  - qa（两列问答）：扁平列表，输出 `问题？：答案`
  - 空单元格：默认 `skip`（内层为空，行标题保留）
- 预期效果：104/104 表格转成嵌套列表；`</li><li>` 边界 850 处

### 改动 2：移除表格引导语
- 改什么：默认引导语数量 = 0；六类关键词分类逻辑从源码彻底移除
- 怎么改：保留 `include_guide`（默认 `false`）+ `guide_text` 自定义入口，空白时回落「如下：」

### 改动 3：新增 `list_nested` 开关
- 改什么：`list_nested=false` 时扁平化（深度 1，列间用「；」）

## 三、配置项变更
| 配置键 | 变更 | 默认值 | 兼容性 |
|---|---|---|---|
| `tables_to_text_format` | 新增 | `list` | 设 `paragraph` 即**完全退回 v1.5.0 行为**（不需要回滚版本） |
| `list_nested` | 新增 | `true` | — |
| `include_guide` | 默认值改 | `false` | 需要引导语可打开 |

## 四、验收标准（节选）
### A 功能（12 项，节选）
- [ ] 默认 `format=list`，产出嵌套列表，`max_depth=2`
- [ ] 外层 `<li>` = 行标题；内层 `<li>` = 「列名：值」
- [ ] 列表渲染区段内**不得**出现「是」式列名连接（源码级断言）
- [ ] 两列表不嵌套；规则 B 外层 `<ul>` 带 `tt-untitled` 且外层 `<li>` 文本为空
- [ ] qa 扁平；空单元格 `skip`；`list_nested=false` 扁平化生效；`include_guide=true` 时可按自定义文本插入

### B 内容完整性
- [ ] 104 个原表全部保留（append）
- [ ] 104 个朗读版全部生成
- [ ] **非空数据格逐格比对 1443/1443 命中**（分子分母都要报）
- [ ] 表级项数核算 0 处不符（列表项 1348 条）

### C 零回归（最强判据）
- [ ] `format: paragraph` 与 v1.5.0 对照产物 **104/104 个 div 逐字节相同**，文本量 32823 = 32823
- [ ] `off` 模式 **21 篇正文 XHTML 与 v1.5.0 全部逐字节相同**
- [ ] EPUB 层差异**逐条归因**：仅 OPF 时间戳 + CSS 新增；**未解释项 = 0**
- [ ] 抖动基线：同版本重跑一次，确认天然抖动项已识别

### D 反向用例
- [ ] TTS 顺畅性 0 违规（连续标点 / 标签·实体·URL 残留 / 机械报数，各 0 处）
- [ ] 文本量差异判据「每格摊到 1.5~3.0 字」（实测 1.99）——**不得**用「两者字数相等」当判据

## 五、执行顺序
1. 改渲染层（新增列表分支，段落分支不动） → 跑专项门禁
2. 改配置默认值与引导语移除 → 跑专项门禁
3. 跑验收矩阵（H 组口径升级为 v1.5.1）
4. 跑零回归对照（段落模式 / off 模式 / 抖动基线）
5. 跑文档门禁 + 打包 + **解压交付包后复跑门禁**

## 七、不要做的事
- ❌ 不要改动段落形式的输出（必须逐字节相同）
- ❌ 不要让 `off` 模式受到任何影响
- ❌ 不要为了「更好听」而删除数据格（内容完整性优先于听感）
````

**这一轮的判据收口方式值得记住**：「内容零丢失」和「文本量差异」被拆成**两条独立判据** —— 前者用逐格比对（1443/1443），后者用「每格 1.5~3.0 字」的可归因区间。合成一条「字数相等」会把「有意的省略」和「意外的丢失」混在一起，必然误判。

### 示例 3：v1.5.1 frontmatter 上架字段补全（小改动 + 范围钉死）

````markdown
# 任务：web-article-to-epub v1.5.1 —— 补全上架必需的 4 个 frontmatter 字段

> 本轮聚焦：上架平台解析失败，补 4 个字段。**除这 4 个字段外不得有任何改动**
> 前置条件：已备份改动前的 SKILL.md 作为基线（用于逐行 diff）

## 一、背景与问题
| # | 问题 | 证据 |
|---|---|---|
| 1 | 上架 WorkBuddy 开放平台时解析失败 | 平台提示缺少 4 个字段 |
根因：现有 frontmatter 只有 `name` / `description` / `version` / `tags` / `user-invocable`，
缺少平台的 i18n 展示字段。

## 二、核心改动
### 改动 1：补 4 个字段
- 改什么：`SKILL.md` frontmatter，位置放在 `name` 之后、`version` 之前
- 怎么改：补 `display_name` / `display_name_en` / `description_zh` / `description_en`
- 字段规范：
  | 字段 | 规范 |
  |---|---|
  | `display_name` | ≤ 20 字 |
  | `description_zh` | ≤ 150 字 |
  | `display_name_en` | 与中文对应 |
  | `description_en` | 与中文对应，**不得含中文** |
  | 全部 | 值不得含会导致 YAML 解析失败的特殊字符（`": "` / `#` / 前导指示符） |
- 预期效果：YAML 解析通过，11 个顶层键 → dict

### 改动 2：`displayName` 取值对齐（需用户批准）
- 改什么：1 行（删除旧值、写入与 `display_name` 一致的值）
- **须先取得用户明确批准**，不得自行决定

## 四、验收标准
### A 功能
- [ ] 4 个字段均在，值非空，均为 `str`
- [ ] 用 YAML 解析器验证：11 个顶层键解析为 dict
- [ ] `---` 分隔符完整：首行恰为 `---`，闭合符独立成行，无 BOM、无 CRLF

### B 内容完整性
- [ ] 中英一致性机器校验：`description_zh` 含中文、`description_en` 不含中文，两者都提到关键术语
- [ ] `display_name` 与 `display_name_en` 同理

### C 零回归（范围钉死）
- [ ] 逐行 diff：新增 5 行、删除 1 行；删除的那行是**已获批准**的 `displayName` 对齐
- [ ] 10 个文件逐一哈希比对，**变更文件数 = 1**
- [ ] 可执行产物哈希不变（重建前后一致）
- [ ] 其余门禁未被波及：文档 41/41、表格专项 82/82、离线 ✅、章节拆分 ✅

### D 反向用例
- [ ] 门禁**反向自检**：严格模式（未授权对齐）必须报 3 条失败，授权模式 32/32
      —— 证明门禁不是在放水

### E 打包
- [ ] 重新打包为 v1.5.1.zip
- [ ] 解压后跑 frontmatter 专项门禁：技能目录 32/32、解压包 28/28

## 七、不要做的事
- ❌ 不要改动 `description` 块标量（原样保留）
- ❌ 不要调整其他字段的顺序（YAML 对键顺序不敏感，平台按名取值）
- ❌ 不要顺手优化措辞
````

**这一轮的亮点是「范围钉死」**：一个纯文本改动，用「逐行 diff + 10 个文件哈希 + 可执行产物哈希不变」三重证据证明**只有 1 个文件变了**。小改动也需要证据，因为小改动最容易夹带私货。

## 四、指令质量自查清单（12 项，下发前逐项过）

| # | 检查项 | 不通过的后果 |
|---|---|---|
| 1 | 本轮是否只聚焦 1–2 个核心问题？ | 失焦 + 回归无法定位 |
| 2 | 每个问题是否都有**数据或证据**（不是「感觉有问题」）？ | 执行方无法判断问题是否存在 |
| 3 | 每个改动是否写明了「改什么（文件/函数/配置键）」？ | 执行方自由发挥 |
| 4 | 验收标准里有没有出现「优化 / 更好 / 更稳定 / 基本」这类词？ | 无法验收 |
| 5 | 每条验收标准是否可量化（有分子/分母或明确断言）？ | 主观判断 |
| 6 | 是否单列了**零回归**判据，且未改动功能的判据尽量收紧到「逐字节」？ | 改坏老功能 |
| 7 | 「不改变」的默认值是否**逐项列出**（键 = 值）？ | 新模式污染老模式 |
| 8 | 是否包含**反向用例**（错误输入必须被检出）？ | 门禁放水 |
| 9 | 新增的自检是否配了**正反用例**（该报警时报警、不该报时不误报）？ | 自检退化成摆设或噪音 |
| 10 | 是否明确了**不要做的事**（硬边界）？ | 夹带改动 |
| 11 | 是否有**执行顺序**且每步后写明了验证命令？ | 出问题无法定位 |
| 12 | 未修项**披露格式**是否写明（数值 + 占比 + 位置 + 影响判定）？ | 「已知问题」了事 |

**使用方式**：写完任务书后，逐条打勾。任一项打不了勾就回去改，不要把不合格的指令发出去 —— 一份模糊的任务书换来的一定是返工。
