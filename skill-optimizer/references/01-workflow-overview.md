# 模块 1：优化流程总览

> 本模块回答三个问题：**谁做什么？一轮怎么走？什么时候可以停？**
> 所有案例来自真实技能 `web-article-to-epub` 从 v1.3.0 到 v1.5.1 的六轮迭代。

---

## 一、三方协作闭环：为什么是三方，而不是两方

### 1.1 角色与职责边界

| 角色 | 身份 | 职责 | 明确**不做**的事 |
|---|---|---|---|
| **用户**（需求方） | 真实使用者 / 产品负责人 | 提出体验问题、提供真实样例、确认方向、说清「做到什么程度算好」、最终确认收尾 | 不需要看代码、不需要写判据、不需要判断技术方案 |
| **AI 审查官**（本技能的核心角色） | 需求翻译官 + 质量守门人 | ① 需求挖掘与澄清 ② 多维度质量评估 ③ 生成结构化任务指令 ④ 验收并裁定 ⑤ 沉淀知识 | **不亲自改代码**；不替用户决定方向；不降低判据迁就执行方 |
| **执行方**（WorkBuddy / 工程师） | 实现者 | 按任务书改代码 / 改文档、跑门禁、产出产物、写交付报告、量化披露未修项 | 不擅自扩大改动范围；不修改验收标准；不把「做不到」藏进报告角落 |

### 1.2 完整闭环

```
用户（需求方）
    │  ① 提出优化需求、反馈体验问题（通常很模糊：「效果不好」「读不出来」）
    ▼
AI 审查官
    │  ② 需求挖掘与澄清（六步法，产出需求确认单 + 真实样例）
    │  ③ 多维度质量评估（15 维度基线评分卡，发现用户没提到的问题）
    │  ④ 生成结构化任务指令（任务书，含可量化验收标准 + 边界 + 执行顺序）
    ▼
执行方（WorkBuddy）
    │  ⑤ 按指令修改、跑测试、产出产物与交付报告
    ▼
AI 审查官
    │  ⑥ 复跑门禁 → 核验口径 → 检查反向用例 → 拆包验产物 → 复评 15 维度
    │  ⑦ 判定：达标 / 有条件达标 / 不达标
    ▼
用户
    │  ⑧ 确认（打开真实产物用一次）
    ▼
   ┌── 未达标或发现新问题 → 回到 ②，进入下一轮
   └── 达标 → 触发模块 6：复盘 + 知识库更新 → 收尾
```

### 1.3 为什么必须是三方

**两方（用户 ↔ 执行方）会出三个问题**：

1. **需求损耗**：用户说「读起来要顺」，执行方理解成「句子更短」，用户实际想要的是「每一项能听出属于哪一列」。中间没有翻译环节，双方在各自的理解里反复返工。
2. **无人守门**：执行方既写代码又写验收标准，等于自己出题自己判卷。真实案例：某轮「验收 85/85 全绿」，但产物打开后被用户一眼看出问题 —— 见 §三 案例。
3. **经验不沉淀**：讨论散在聊天记录里，同一个坑第三轮又踩一次。

**三方分工的关键是「审查官不写代码」**：一旦审查官开始顺手改代码，他就会不自觉地为自己写下的判据辩护，守门人角色失效。

## 二、单轮迭代的六步

每一轮（不论大小）都走这六步。步骤可以很快，但不能跳。

| 步骤 | 做什么 | 产物 | 常见失误 |
|---|---|---|---|
| **① 探查** | 读现状：现有 SKILL.md / 配置 / 代码 / 上一轮报告；复现用户描述的场景 | 现状盘点（含证据：命令、日志、产物路径） | 基于假设行事，「我以为它是这么实现的」 |
| **② 约束** | 定边界：本轮只解决哪 1–2 个问题；哪些明确不动；零回归的判据是什么 | 边界清单 + 零回归判据 | 范围过大，一轮塞 5 个需求 |
| **③ 证据** | 拿真实样例：用户的真实输入、期望输出、可复现的最小案例 | 真实样例 + 期望输出描述 | 用自己编的例子代替用户真实样例 |
| **④ 执行** | 按执行顺序改：先低风险后高风险，每步后跑测试 | 改动 + 每步的门禁结果 | 一次性大改后统一测试，出问题无法定位 |
| **⑤ 验证** | 用硬判据验证：新功能生效 + 旧功能零回归 + 反向用例能被检出 | 验收矩阵结果（含负向用例） | 只验新功能；自检没有反向用例 |
| **⑥ 交付** | 报告 + 产物 + 量化披露未修项 + 版本号三处同步 | 交付报告 + 交付包 | 未修项写「已知问题」不量化；版本号不同步 |

### 2.1 六步中的时间分布（实测参考）

以 `web-article-to-epub` 六轮为例，按报告时间戳推算的经验值：

| 步骤 | 占比（经验值） | 说明 |
|---|---|---|
| ① 探查 | 10% | 常常被压缩到 0，然后代价在 ⑤ ⑥ 加倍偿还 |
| ② 约束 | 5% | 10 分钟的边界讨论，能省掉一轮返工 |
| ③ 证据 | 10% | 拿真实样例的耗时，远小于用错样例的返工代价 |
| ④ 执行 | 35% | 真正改代码 |
| ⑤ 验证 | **30%** | 验收耗时接近执行 —— 这是健康的，不是浪费 |
| ⑥ 交付 | 10% | 报告 + 披露 + 打包 |

> **反直觉但重要**：验证耗时应当与执行耗时同量级。如果验证只占 5%，通常意味着「只跑了一遍主流程」，没有零回归、没有负向用例、没有拆包核对。

### 2.2 完整一轮时序示例（真实）

`web-article-to-epub` v1.4.1 那一轮（修复分篇粒度与静默丢内容）：

| 时间 | 动作 | 产物 |
|---|---|---|
| 01:31 | 上一轮（v1.4.0）交付报告落盘 | `report/v1.4.0-优化与验收报告.md` |
| 01:36 | 探查：本地复现 + 拆包核对，发现 410 篇 XHTML / 51 篇空壳 / 内容缺口 2.3% | 现状盘点 |
| 01:45 | 定约束：本轮只修分篇粒度 + 装饰残留 + 静默丢弃三处，不改抓取链路 | 边界清单 |
| 02:00 | 执行完成，跑验收 | — |
| 02:15 | 交付报告落盘，4 道门禁全绿（105/105） | `report/v1.4.1-修复验证报告.md` |

> 该轮的关键事实：**三处缺陷都不报错、都不告警**，只能靠拆包逐项对数才能发现。这直接催生了本技能的两条底线：「不静默丢弃」和「每轮必须打开真实产物看一眼」。

## 三、六轮全景：一个真实技能的完整迭代轨迹

| 轮次 | 版本 | 主题 | 核心问题 | 关键硬判据 | 验收断言之初 → 之末 |
|---|---|---|---|---|---|
| 1 | v1.4.0 | 课程模式（多页合并出书） | 只能抓单页，多页课程需手工拼 | 正文字数 126543 与旧手工链路**逐项相等**；图片 266/266 全下载；表单残留 0 | 0 → 85 |
| 2 | v1.4.1 | 分篇粒度 + 静默丢内容 | 410 篇 XHTML、51 篇空壳、缺口 2.3% | 410 → 20 篇；空壳 0 篇；缺口 2.3% → 0.08% | 85 → 105 |
| 3 | v1.4.2 | 内容缺口归零 + 视频链接保活 | 「含图 + 正文」的 figure 整块被丢；`<video>` 地址丢失 | 缺口 0.08% → **0.00%**；包内 `.mp4` 数量 0 | 105 → 123 |
| 4 | v1.5.0 | 表格转可朗读文本 | TTS 读不出表格内容 | 原表 104 个全保留 + 朗读版 104 个全生成；数据格零丢失 | 123 → 169 |
| 5 | v1.5.1 | 表格朗读版改列表形式 | 段落形式「一行一个长句」，TTS 听不出列归属 | 1443/1443 数据格命中；段落模式与 `off` 模式**逐字节零回归** | 169 + 专项 82 |
| 6 | v1.5.1 | frontmatter 上架字段补全 | 上架平台解析失败，缺 4 个字段 | 专项 32/32；解压交付包后独立复跑通过 | +32 +41 |

**六轮呈现的规律**（可直接用于你的轮次预算）：

- **第 1 轮一定是「从不能到能」**，改动最大，回归风险最高；
- **第 2–3 轮通常是「修第 1 轮暴露的静默缺陷」**，这类缺陷只能靠拆包对数发现，任务书预不见；
- **第 4–5 轮才是「从能用到好用」**，也是用户真正在意的一轮；
- **最后一轮常常是「上架 / 发布合规」**，纯配置和元数据，风险最低但最容易漏（版本号三处不一致是典型）。

## 四、迭代终止条件

### 4.1 四条硬性条件（全部满足才算达标）

| # | 条件 | 判定方法 | 反面教材 |
|---|---|---|---|
| 1 | 需求确认单里的**所有硬判据全绿**，且判据**没有被放宽** | 复跑门禁 + 逐条核对比对口径（「逐字节」不许变成「接近」） | 把「1443/1443 命中」悄悄换成「覆盖率 ≥95%」 |
| 2 | **零回归已用最强判据证明** | 未改动功能与上一版一致（理想：逐字节；次选：A/B 对照 + 抖动基线） | 只跑新功能，老功能「应该没事」 |
| 3 | **所有未修项已量化披露**，用户已知悉并接受 | 披露格式：数值 + 占比 + 位置 + 影响判定 | 「已知问题，后续优化」 |
| 4 | **隐形维度无 0 分项** | 15 维度复评，隐形 8 项不得有 0 分 | 评测全过，但用户不知道自己的操作跑到哪一步了（可观测性 0 分） |

### 4.2 三条软性建议（不阻塞收尾，但要写进披露）

5. 模块 6 的**复盘记录已填写**（六个必答问题）；
6. **知识库已更新**：本轮新发现的反模式 / 最佳实践已入库；
7. **三处版本号一致**：主文件 frontmatter / 配置注释 / 变更记录。

### 4.3 什么时候**不应该**收尾

- 用户还没**亲手用过一次**真实产物；
- 出现了「报告全绿但产物一眼有问题」的情形 —— 这说明判据有缺口，**补判据**比收尾重要（v1.4.0 的教训）；
- 有 1 项失败但其成因未查明 —— 只有「查明原因 + 明确判定为不影响」才能算残余，否则它是未知风险。

## 五、轮次预算：不同类型的 skill 需要几轮

| skill 类型 | 典型轮次 | 每轮聚焦 | 首轮风险 |
|---|---|---|---|
| 纯文档类（模板、规范、清单） | 2–3 轮 | 第 1 轮：结构与完备性；第 2 轮：表达与示例；第 3 轮：上架元数据 | 低 |
| 单次执行类（转换、提取、生成一次产物） | 3–4 轮 | 第 1 轮：跑通主流程；第 2 轮：内容完整性；第 3 轮：边界与降级；第 4 轮：体验与文档 | 中 |
| 多阶段流水线类（抓取 → 加工 → 输出） | 5–7 轮 | 见 §三 的六轮轨迹 | 高（每阶段的静默缺陷都会累积到最终产物） |
| 需要平台上架的类 | 在上表基础上 +1 轮 | 元数据 / 分发包自洽 | 低但易漏 |

> `web-article-to-epub` 属于「多阶段流水线 + 上架」，实际用了 6 轮 —— 与预算吻合。

## 六、本模块的三个反模式

| 反模式 | 症状 | 正确做法 |
|---|---|---|
| **审查官下场写代码** | 审查官自己改了代码，后续验证时倾向为自己写的判据辩护 | 审查官只产出评分卡 / 任务书 / 裁定；改动由执行方完成 |
| **一轮多需求** | 一轮塞 5 个需求，每个都改了一点，每个都没改好，回归难以定位 | 一轮 1–2 个核心问题；其余进 backlog 排下一轮 |
| **跳过探查直接改** | 基于「我以为的实现」修改，改完发现改错了地方，或与既有开关冲突 | 探查必须产出物证：命令、日志片段、产物路径、行号 |
