# 模块 2：多维度质量评估体系

> **7 个显性维度 + 8 个隐形维度 = 15 维度、60 个评估问题。**
> 用途有两个：① 优化前做**基线评估**（找出用户没提到但确实存在的问题）；② 每轮交付后**复评**（确认分数真的涨了）。
> 所有案例来自 `web-article-to-epub` v1.3.0 → v1.5.1 六轮迭代实测。

---

## 一、怎么用这份清单

1. **先跑显性 7 项**（功能、正确性、体验、回归、工程化、性能、安全）—— 这些是「能不能用」的问题。
2. **再跑隐形 8 项**（认知负荷、可观测性、容错、心智模型、可组合性、依赖、迁移、元数据）—— 这些是「好不好用、能不能长期用」的问题。
3. 每个问题打分 **0–3 分**：
   - `0` = 完全没有 / 明显有问题；
   - `1` = 有但不完整 / 需要用户自己想辙；
   - `2` = 基本可用，有小瑕疵；
   - `3` = 做得很好，可以作为范例。
4. **不要平均**：15 个维度的分数不用求平均。判定用「短板」逻辑 —— 任一维度 0 分都是必须处理的，哪怕其他都是 3 分。
5. 评分卡模板与优先级建议见本文 §四、§五。

**关键提醒**：基线评估的目的**不是**给 skill 打总分，而是**产出一张「用户没提到但确实该改」的清单**。用户通常只会提他碰到的那个问题；专业审查官的价值在于看到他没碰到的。

---

## 二、显性维度（7 个）

### 维度 1：功能完整性 —— 「该做的做了吗？」

| # | 评估问题 |
|---|---|
| 1.1 | 核心功能能否**端到端**跑通（一条命令 / 一次调用，从输入到最终产物）？ |
| 1.2 | 输入输出的形状是否符合预期（格式、字段、文件命名、目录结构）？ |
| 1.3 | 有几种使用模式（单次 / 批量 / 特殊模式）？每种是否都独立可用？ |
| 1.4 | 边界场景是否覆盖：空输入、超大输入、输入格式异常、目标不可达？ |

**真实案例（v1.4.0 新增课程模式）**
优化前该技能只能抓单页文章，多页课程需要手工拼装。新增课程模式后，用**用户输入的一条命令**验证端到端：

```bash
python web_article_to_epub.py "<课程URL>" --course-mode --epub-direct -o output/adp_fde_test
```

产出实测：结构发现 4 章 / 19 课时（`via=api`）；4 个私有对象存储章节全部抓取，失败 0；合并后 `h1=4 / h2=19 / h3=386 / p=1666 / table=104 / ul=109`；图片 266/266 全下载且 ID 全局连续无缺口；EPUB 109 MB，自检 8/8 通过；目录 410 条锚点全部有效。

> 注意这里用的是**用户会用的那条命令**，不是开发者方便造的一堆分段调用。功能完整性必须在真实入口上验证。

**常见误判**：把「每个函数单独测试通过」当成「功能完整」。函数级别全绿而端到端跑不通，在多阶段流水线类技能里非常常见。

### 维度 2：实现正确性 —— 「做对了吗？」

| # | 评估问题 |
|---|---|
| 2.1 | 是否存在「不报错但结果错」的逻辑？有没有可复现证据（多次运行一致）？ |
| 2.2 | 数据在流转中是否完整（各阶段的计数能否对上账）？ |
| 2.3 | 配置项是否真的生效（改了默认值，行为真的变了吗）？ |
| 2.4 | 启发式 / 猜测型逻辑（自动识别、自动选择）有没有「命中证据」，还是碰运气？ |

**真实案例 1：启发式选择必须打分，不能「取第一个」**
课程页内联了**同站其他课程**的目录 JSON —— 实测页面里有 7 个 `contentTree`，只有第 7 个是当前课程。原实现「取首个可解析的」，于是稳定拿到别的课：4 章 19 课时被判成 **1 章 2 课时，而且不报错**。修复方式是候选打分，按「`courseId` 命中数 → URL 路径数字命中数 → 有内容 URL 章数 → 章数 → 课时数」排序取最优。

> 教训：凡是「从多个候选中自动挑一个」的实现，都要问「挑错了会不会被发现」。如果不会，那就必须有打分和证据。

**真实案例 2：分母取错位置导致账目重复计数**
图片报告写「下载成功 265 / 失败 0」，但清单里却有 266 条。根因是被下载后按体积/配额过滤掉的图**不计入任何计数器**（既非 downloaded 也非 failed）。修复时新增了账目自洽校验（`前置丢弃 + 下载成功 + 跳过 + 失败 == 发现数`），但**分母取错了位置**：代码里 `report['discovered']` 原本是个从未赋值的死字段（恒为 0），接上时写成了「调用方传入的已过滤列表长度」，导致被截断的那张图同时出现在分母和丢弃列表里，两侧重复计数。最终把赋值挪进过滤**之前**（真正的过滤前分母），并新增 `pre_download_dropped` / `download_queue` 两个可核算字段。

**正确性自检三问**：这个数字谁算的？它的分母是什么？如果它错了，谁会先发现？

### 维度 3：体验质量 —— 「好用吗？」

| # | 评估问题 |
|---|---|
| 3.1 | 打开最终产物，第一眼有没有明显问题（空页、残留装饰、排版错乱、标题重复）？ |
| 3.2 | 输出是否符合**目标使用场景**（不是「技术正确」，是「在这个场景里顺」）？ |
| 3.3 | 典型操作的步骤数是合理的，还是需要用户手工补救？ |
| 3.4 | 交互是否自然：提示语、确认时机、错误措辞是否符合用户语言？ |

**真实案例（v1.4.1：全绿但读者打开就能看出问题）**
上一轮 v1.4.0 的验收是 **85/85 全绿**，但用户打开 EPUB 立刻能看出三个问题：

| 症状 | 根因 | 修复后 |
|---|---|---|
| 正文被切成 **410 篇** XHTML（1 前言 + 4 章 + 19 课时 + 386 小节），其中 **51 篇不足 100 字** | 分组逻辑把每个标题都当成出书单元 | **20 篇**（19 课时 + 1 封面），最小 2933 字 |
| 出现「只有 `<p>CHAPTER 01</p>`」的**空壳前言页**，`CHAPTER 01` 之类的装饰文字混进正文 23 处 / 403 字 | 装饰容器被当成交互容器「去标签保内容」 | 空壳 0 篇，装饰残留 0 |
| 正文缺口 **2.3%**（140 段 + 7 个列表 + 401 字丢失） | 清单只认块级标签，站点把正文放在非块级位置 | 缺口 → 0.08%（后续轮次 → 0.00%） |

> **这是本技能最重要的一条教训**：验收全绿 ≠ 好用。判据只能证明「你测过的东西是对的」。因此每轮收尾必须有一步**人工看一眼真实产物** —— 打开、听一遍、用一次。这一步不能外包给自动化。

### 维度 4：回归安全 —— 「改坏了吗？」

| # | 评估问题 |
|---|---|
| 4.1 | 未改动的功能与上一版是否一致？判据是「逐字节相同」还是退而求其次？ |
| 4.2 | 旧配置项、旧命令签名是否仍然兼容（含默认值不变）？ |
| 4.3 | 新增依赖是否带来新风险（体积、平台要求、许可证）？ |
| 4.4 | 天然抖动项（时间戳、随机序、绝对路径）是否被识别并排除，而不是混进差异里？ |

**真实案例 1：最强判据是「逐字节相同」**
v1.5.1 引入表格朗读版的新格式（列表形式）时，零回归判据写成：`format: paragraph` 与上一版对照产物 **104/104 个 div 逐字节相同**，文本量 `32823 = 32823`；`off` 模式 **21 篇正文 XHTML 与上一版全部逐字节相同**，EPUB 差异**仅** OPF 时间戳 + CSS 新增，**未解释项 0**。

> 「未解释项 0」这句话是整个判据的灵魂：差异清单必须被逐条归因，归不了因的就是回归。

**真实案例 2：抖动基线**
单篇模式的 A/B 对照脚本支持第三种输入：`--rerun`（**同一版本重跑一次**）。作用是把「天然抖动项」（时间戳、文件遍历顺序）先测出来，再从 A/B 差异里剔除 —— 否则每轮都会看到一堆假差异，最后所有人开始无视差异清单。

**真实案例 3：配置默认值零回归也要证明**
课程模式把图片配额自适应为 500 张 / 1 GB / 不限制宽度，但单页模式的默认值必须纹丝不动（20 张 / 100 MB / 宽 1200 / 旧签名 / 旧默认键值）。这类「新模式不能污染老模式」的判据要显式写进验收清单，不能靠「应该没改到」。

### 维度 5：工程化 —— 「可持续吗？」

| # | 评估问题 |
|---|---|
| 5.1 | 验收是否脚本化、可复跑、可参数化（换一个被测对象能否直接跑）？ |
| 5.2 | 脚本失败时是否有**正确的退出码**与结构化结果（能被自动化消费）？ |
| 5.3 | 文档是否与实现同步（配置键、默认值、命令、示例）？ |
| 5.4 | 环境是否可复现（依赖版本、路径、运行入口是否有记录）？ |

**真实案例：验收脚本硬编码路径 → 全参数化**
v1.4.0 的验收脚本把技能路径、输出目录写死在文件里，换一台机器或换一个被测对象就跑不了。v1.4.1 的 P1-1 任务把它重写为 `argparse`：`--skill` / `--output` / `--raw-dir` / `--url` 全部可覆盖，自动探测 + 可执行报错，兼容两种章节文件命名（`chapter_01.html` / `chapter_1.html`），结果落 `acceptance_result.json`，**未通过时 `exit 1`**。

**可复跑的门禁汇总长什么样**（真实脚本骨架，节选）：

```bash
#!/bin/zsh
# 全量门禁汇总（最终定版，8 道）
set -u
ROOT="<工作区>"
SKILL="$HOME/.workbuddy/skills/web-article-to-epub"
PY="<python>"
LOG="$ROOT/build/e2e/gates_final.log"
cd "$ROOT" || exit 1

{
  echo "=== 门禁汇总 ==="; date '+运行时间：%Y-%m-%d %H:%M:%S'
  echo "### [1/8] 专项校验";  "$PY" build/check_tables_v151.py;           echo "exit=$?"
  echo "### [2/8] 验收矩阵";  "$PY" build/acceptance_v140.py 2>&1 | tail -12; echo "exit=${pipestatus[1]}"
  echo "### [3/8] 离线回归";  "$PY" build/check_offline.py;              echo "exit=$?"
  echo "### [4/8] 章节拆分";  "$PY" build/check_epub_split_v141.py;      echo "exit=$?"
  echo "### [5/8] 单篇 A/B";  "$PY" build/check_single_mode_v142.py \
        --a /tmp/single_v150_off_ref --b /tmp/single_v151_off --rerun /tmp/single_v151_off_b
  echo "### [6/8] 文档静态";  "$PY" build/check_index_html_v151.py;      echo "exit=$?"
  echo "### [7/8] 文档渲染";  "$PY" build/check_index_render.py;         echo "exit=$?"
  echo "### [8/8] 解压交付包后复跑（证明包自洽）"
  rm -rf /tmp/pkg && unzip -qo "$ZIP" -d /tmp/pkg
  shasum -a 256 /tmp/pkg/web-article-to-epub/web_article_to_epub.py "$SKILL/web_article_to_epub.py"
} > "$LOG" 2>&1

awk '/^### \[|^exit=|全部通过|^失败项/' "$LOG"   # 汇总摘要
```

> 注意最后一道门禁是「**解压交付包后复跑**」—— 证明「交出去的包」和「我测过的目录」是同一份东西，而不只是「本机目录里能跑」。

### 维度 6：性能与成本 —— 「跑得快、省资源吗？」

| # | 评估问题 |
|---|---|
| 6.1 | 典型任务的耗时与资源占用是多少？与上一版比有没有退化？ |
| 6.2 | 大输入下的稳定性如何（会不会内存爆、超时、被限流）？ |
| 6.3 | 是否需要联网 / 付费 API？调用次数与成本可预估吗？ |
| 6.4 | 产物体积是否在可用范围内？有没有给用户**可选的**压缩手段？ |

**真实案例：体积告警 + 明确的「不要这么做」**
课程产物 EPUB 达到 **109 MB**（266 张 1920×1080 截图，课程模式默认保原分辨率）。修复不是「自动压缩」，而是新增 `report_epub_volume()`，出书后打印：体积 + 图片数 + 最大分辨率（实测记录到 `106.3 MB / 266 张 / 最大 3840×1986`），≥80 MB 时给出两种压缩手段，并**明确警告不要用 `images.min_file_size` 这类内容完整性开关去压体积**（用它会静默丢图 —— 见隐性维度 3 的案例）。

> 这一条很典型：性能与内容完整性冲突时，**不要替用户做取舍**，要把取舍讲清楚，让用户带着信息决定。

### 维度 7：安全与合规 —— 「安全、合规吗？」

| # | 评估问题 |
|---|---|
| 7.1 | 有没有注入风险（把外部内容当代码 / 当命令执行）？ |
| 7.2 | 隐私与凭证：是否读取或写入凭证文件？密钥是否落在产物里？ |
| 7.3 | 是否遵守目标站点的 robots.txt 与限速要求？ |
| 7.4 | 版权与授权：抓取/分发的内容是否有越界风险？破坏性操作有没有二次确认？ |

**真实案例 1：确认门禁不能取消，只能「显式 opt-in + 可审计」**
该技能有一条铁律：未经用户明确确认不生成 EPUB。但自动化场景需要无人值守，于是新增直通通道 `--epub-direct` / `epub.auto_confirm`（**默认 `false`**），其内部行为是：自动建清单 → 写入确认字段（`user_confirmed=true` / `confirmed_at` / `confirmed_change_count=0`）→ 断言 → 出书；**未授权时抛 `PermissionError`**。同时 `editing.require_user_confirmation` 恒为 `true`。

> 安全设计的正确姿势不是「加个开关跳过检查」，而是「让跳过这件事本身留下可审计的证据」。

**真实案例 2：凭证边界写进技能契约**
技能声明「不直接调用任何 API、不需要密钥」，并明确「**绝不读取或修改 `.env`、`.env.local` 或任何含实际凭证的文件**」；若用户要求接入 LLM 增强，密钥一律用 `os.environ.get()` 读取，**不得写入生成的脚本或配置文件**。

## 三、隐形维度（8 个）

> 隐形维度不会让功能报错，但决定用户会不会弃用。它们通常在「从能用到好用」的那几轮被处理。

### 隐性 1：认知负荷 —— 「用户要用多少脑力才能用起来？」

| # | 评估问题 |
|---|---|
| 1.1 | 最简用法能否做到「只给一个必需参数」（或零参数）就产出可用结果？ |
| 1.2 | 默认值是否覆盖了 80% 的常见场景，让用户不必配置？ |
| 1.3 | 参数/配置的命名是否符合用户直觉（用户能否猜出用途）？ |
| 1.4 | 错误信息是否告诉用户「怎么改」，而不只是「哪里错了」？ |

**真实案例**：单页模式的最简用法就是**一个 URL**（不加任何模式开关，全链路跑通并产出 7 件产物、EPUB 4.14 MB）。课程模式则只多一个 `--course-mode`。默认值设计上，「课程模式自动切换配额、单页模式默认值不变」—— 用户不需要知道自己该设多少张图，模式替他决定了。这类「模式级默认值」是降低认知负荷的高效手段。

---

### 隐性 2：可观测性 —— 「运行时用户能看到什么？」

| # | 评估问题 |
|---|---|
| 2.1 | 长任务有进度反馈吗（到第几章 / 第几张图）？ |
| 2.2 | 失败时能否一眼定位到「哪一项、哪个 URL、哪个阶段」？ |
| 2.3 | 有没有日志文件或结构化报告（而不只是屏幕输出）？ |
| 2.4 | **任何被丢弃 / 跳过 / 降级的东西，是否都有显式告警**？ |

**真实案例 1：图片账目不平（最典型的一类）**
报告写「下载成功 265 / 失败 0」，清单里却有 266 条。被过滤的图既不算成功也不算失败 —— 用户要到很晚（甚至出 EPUB 看到 `[warn] 未能本地化`）才知道少了一张图。修复：新增 `skipped_images` / `skipped_count` 计数，并在**阶段 4 就打 stderr 告警**；质量报告新增**账目自洽校验**，不平即告警。

**真实案例 2：把「正文有没有变形」变成两个数字**
把 `dropped_decorations`（删掉多少装饰）和 `wrapped_bare_text`（包了多少裸文本）写进 `chapter_stats` 并打到阶段日志。这两个数字直接对应「正文是否被改动过」，避免「静默通过」。

> 可观测性的判据可以总结成一句话：**凡是「少了东西」的地方，必须有一个数字在看着它。**

---

### 隐性 3：容错与降级 —— 「部分失败时整体还能用吗？」

| # | 评估问题 |
|---|---|
| 3.1 | 单个单元失败（某一页 / 某一张图）是跳过还是整体失败？这个选择对用户合理吗？ |
| 3.2 | 有多策略级联吗（从轻到重：简单方法 → 重方法）？ |
| 3.3 | 降级是否**透明**（日志里说清了「用了兜底方案」）？ |
| 3.4 | 结构性失败会不会静默退化成「另一种结果」（最危险的一类）？ |

**真实案例 1：结构发现失败必须中止，不能静默退化**
三条发现路径 （站点目录 API → 页面内联目录 JSON → DOM）都失败时，返回**结构化错误并中止**，**不静默退化为单篇抓取** —— 因为「静默退化成单篇」会让用户拿到一本只有一页的书，且以为成功了。

**真实案例 2：透明的兜底**
正文提取的主策略在私有对象存储页面上总是返空，实际由配置化选择器兜底。日志明确打出「`trafilatura` 未产出有效正文，改用配置化选择器兜底」——结果正确、内容零丢失，但**用户知道发生了降级**。这一条被记入遗留事项，等待后续单独评估。

**真实案例 3：自检失败不能毁掉成品**
出书后的自动校验 `validate_epub()` 在失败时**只告警、不删除成品** —— 用户可能就想拿这份有瑕疵的书先看看。

### 隐性 4：用户心智模型 —— 「用户以为它会怎样，实际怎样？」

| # | 评估问题 |
|---|---|
| 4.1 | 功能名称与默认行为是否符合用户预期？ |
| 4.2 | 文档里写的默认值与代码里的默认值是否一致？ |
| 4.3 | 行为不符合预期时，是否有提示解释？ |
| 4.4 | 有没有「看起来在正常工作、实际什么都没做」的假成功？ |

**真实案例 1：文档与代码默认值不一致**
文档里 `use_epubcheck` 写 `false`，配置里是 `true`。用户按文档理解行为，实际行为不同。修复是对齐取值 —— 这类问题在验收时要专门设一项「文档与配置一致性」断言。

**真实案例 2：默认空配置却每次都告警**
`epub.embed_font` 默认是空串（意思是「不嵌入字体」），但每次出书都打印「字体不存在」告警。根因是把空串构造成路径后得到 `'.'`，于是「非空」判断恒为真。用户以为配置坏了，实际是误报。**误报和漏报一样有害** —— 它训练用户忽略告警。

**真实案例 3：假成功**
`<video>` 标签原本只转出封面图，视频地址丢失。读者看到封面以为「这里有视频」，但拿不到链接 —— 功能看起来正常，信息已经丢了。修复后保留远程链接并前缀标记 `[视频] `，同时明确**不下载视频文件**（几十 MB 量级，打包不划算；实测包内 `.mp4/.mov` 数量 0）。

### 隐性 5：可组合性 —— 「能和其他 skill 协作吗？」

| # | 评估问题 |
|---|---|
| 5.1 | 输出格式是否标准、可被其他工具直接消费（JSON / 标准文件结构）？ |
| 5.2 | 中间产物是否独立可用、可复用（不必重跑全链路）？ |
| 5.3 | 是否支持管道 / 命令行调用（非交互式也能跑完）？ |
| 5.4 | 元数据是否完整（来源、时间、版本、参数），足够让下游判断来源？ |

**真实案例**：该技能的核心产出设计成「**三件套**」——纯净 HTML + 图片映射 JSON + 编辑清单 —— 加上质量报告 JSON。好处是每个中间产物都能单独被检查、被替换（例如只换图片不动正文），不必重跑全链路。元数据层记录 `source_url`（恒为原始输入 URL）、`date_published`、`course_structure`；且 `date_published` 为空时 `has_date=false` **不报错** —— 下游可以据此判断字段是否存在，而不是靠猜空串含义。

### 隐性 6：依赖健康度 —— 「脚下的地基稳吗？」

| # | 评估问题 |
|---|---|
| 6.1 | 依赖是否活跃维护？版本是否锁定（避免上游一变就崩）？ |
| 6.2 | 有没有已知漏洞或平台限制（如需要 Java、需要特定系统库）？ |
| 6.3 | 依赖是否过重（为一个次要功能引入大依赖）？ |
| 6.4 | 可选依赖缺失时是否优雅降级，并给出替代方案？ |

**真实案例**：`epubcheck` 严格校验需要 Java，用户机器上未安装。处理方式是三件事：**① 缺失时静默跳过，不影响内置 8 项自检**（不误伤主流程）；**② 文档给出三种安装法 + 运行命令 + 6 类常见告警的处理表 + 无 Java 的替代方案**；**③ 验收脚本加「可选断言」—— 缺失则跳过并标注替代方案**。同时新增 `site_headers`（按 host 覆盖请求头，后缀匹配、最长者胜）而**不是改全局请求头**，避免影响其他站点的抓取行为 —— 这是「新需求不污染老路径」的依赖层体现。

---

### 隐性 7：可迁移性 —— 「换个环境还能跑吗？」

| # | 评估问题 |
|---|---|
| 7.1 | 跨平台：路径处理、命令、编码是否兼容（macOS / Windows / Linux）？ |
| 7.2 | 编码统一（读写是否都显式指定 UTF-8）？ |
| 7.3 | 有没有硬编码的绝对路径、用户名、本机专属目录？ |
| 7.4 | 接入新目标（新站点 / 新数据源 / 新平台）需要改代码还是改配置？ |

**真实案例 1：接入新站点应该「改配置不改代码」**
站点预设机制带 `match_hosts` 等字段，接入新站点只需在 `course_mode.site_presets` 里补 `toc_api` / `sign_api` / `content_url_pattern`，**代码零改动**。实测新增了慕课网、极客时间两个预设。

**真实案例 2：做不到就明确说不支持**
两个新预设都标记 `need_login: true`，并在 `unsupported_reason` 里附**实测依据**（而不是硬着头皮写「支持」然后让用户撞墙）。主文件里同时给出「站点预设支持状态表 + 新增预设最小模板」。

### 隐性 8：元数据与可发现性 —— 「用户能找到这个 skill 吗？」

| # | 评估问题 |
|---|---|
| 8.1 | 名称是否含用户会搜索的关键词？ |
| 8.2 | 描述是否说清了「好处」而不只是「功能」（用户为什么该用它）？ |
| 8.3 | 标签是否覆盖多种表达方式（口语化说法、英文术语、近义词）？ |
| 8.4 | 有没有 2–3 个能让人一眼看懂价值的示例？ |

**真实案例 1：上架必需的 4 个字段**
该技能上架时因缺少 4 个 frontmatter 字段直接解析失败：`display_name` / `display_name_en` / `description_zh` / `description_en`。补全时的规范与机器校验：`display_name` ≤ 20 字、`description_zh` ≤ 150 字、`description_en` 与中文对应且**不含中文字符**、`display_name` 与 `display_name_en` 同理。字段值不得含会导致 YAML 解析失败的特殊字符（`": "`、`#`、前导指示符）。

**真实案例 2：触发词要覆盖用户的「大白话」**
该技能的描述里塞进了大量用户口语化说法，例如「听书时表格读不出来」「让朗读功能能读表格」「TTS 读不了表格」「把表格转成列表朗读」「表格用嵌套列表展示」「听书时表格分不清哪一列」。原因很直接：**写技能的人说「表格映射」，用技能的人说「听书时读不出来」** —— 描述里必须两种话都有，否则匹配不上。

## 五、维度优先级建议

| 检查时机 | 必查维度 | 理由 |
|---|---|---|
| **每轮必查（4 个）** | 功能完整性、实现正确性、回归安全、可观测性 | 分别对应「做了吗 / 做对了吗 / 改坏了吗 / 用户看得见吗」。任一项失守都直接导致返工 |
| **每轮建议查（3 个）** | 体验质量、容错与降级、用户心智模型 | 这三项是多阶段流水线类技能的主要缺陷来源 |
| **每 2–3 轮查一次** | 工程化、性能与成本、依赖健康度 | 变化慢，但累积到阈值会突然爆发（如验收脚本彻底不可用） |
| **收尾轮 / 上架轮** | 安全与合规、可迁移性、元数据与可发现性、认知负荷、可组合性 | 前两项在收尾轮做一次完整复核；后两项在上架前必须达标 |

**判断优先级的三条经验规则**：

1. **「用户会撞上但用户没说」的问题优先于「用户说了但只影响一次」的问题**；
2. **静默类问题（不报错但结果错）优先级最高** —— 六轮案例里它出现 4 次，是最高频的一类；
3. **修一个 bug 时顺手检查同源问题的其他实例**（例：发现「字节数当占位符判据」错了，就顺着检查所有用字节数/尺寸做判断的地方）。
