# Skill 优化大师（Skill Optimizer）

## 一、这个技能是做什么的

这是一个 **元技能（meta-skill）**：它自己不做业务，它教你怎么把**别的 skill** 改好。

绝大多数 skill 的优化失败不是「做不出来」，而是三类问题：

| 典型症状 | 真实原因 | 本技能对应模块 |
|---|---|---|
| 用户说「效果不好」，AI 立刻动手改，改完用户还是不满意，来回五六轮 | 需求没有具象化，双方对「好」的理解不一致 | 模块 3 六步需求管理法 |
| 改一个功能，坏了三个老功能 | 验收只看新功能，没有零回归判据 | 模块 5 硬判据验收体系 |
| 门禁全绿，但用户打开产物一眼就看出问题 | 验收口径只覆盖了「字段对不对」，没覆盖「人用起来怎么样」 | 模块 2 隐形维度 + 模块 5 「全绿≠好用」 |
| 同一个坑踩第三次 | 优化经验散落在聊天记录里，没有沉淀 | 模块 6 知识沉淀与复盘机制 |
| 执行方（AI/工程师）自由发挥，改了不该改的东西 | 任务书没写边界，没写执行顺序 | 模块 4 结构化任务指令模板 |

**核心价值**：把一个「凭感觉来回改」的过程，变成「有评估维度、有需求确认、有任务书、有门禁、有复盘」的标准化流水线。它的实质是**降低沟通损耗 + 把质量变成可证明的东西**。

本技能沉淀自一个真实的六轮优化案例：`web-article-to-epub`（网页转 EPUB 技能）从 v1.3.0 迭代到 v1.5.1，期间新增了课程模式、把内容缺口从 2.3% 压到 0.00%、把 410 篇碎片章节收敛到 20 篇、给表格做 TTS 可朗读版本、补全上架元数据 —— 六轮里踩过的坑、做对的取舍、写过的判据，全部变成了本技能的清单和案例。**全文所有案例均为该案例的真实数据，非虚构举例。**

## 二、什么时候应该调用这个技能

### 必须使用

- 用户提出要**优化 / 改进 / 重构 / 评审**任何一个已有 skill；
- 用户反馈某个 skill「效果不好 / 不好用 / 结果不对」，但说不清具体要什么；
- 需要给某个 skill 的改动**写任务书**（交给 AI 或工程师执行）；
- 需要**验收**某个 skill 的改动是否达标、是否引入回归；
- 需要判断某个 skill 的**迭代是否可以结束**（从「能用」到「优秀」的那条线在哪里）；
- skill 上架 / 发布被平台拒绝，需要定位缺什么、补什么。

### 不适用

- 从零**创建**一个全新 skill（那是 skill 创建类技能的事，本技能只管「优化已有」）；
- 纯粹的业务执行（例如「帮我抓这个网页」）—— 直接调用对应的业务 skill；
- 与本技能无关的代码库优化（本技能的方法论可迁移，但清单和案例是为 skill 场景写的）。

## 四、使用方法

### 场景 1：用户提出 skill 优化需求 → 挖掘需求 + 基线评估

**触发**：用户说「XX skill 效果不好」「帮我优化一下 XX」。

**执行步骤**：

1. **不要立刻动手，也不要立刻问「你想要什么」**。先读 [`references/03-requirement-management.md`](references/03-requirement-management.md)，按六步法从**场景还原**开始问：
   > 「你上次用这个 skill 时，在什么情况下觉得不好？能具体描述一下那个场景吗？」
2. 按第 2 步**需求具象化**，拿到一份**真实输入样例 + 期望输出描述**，作为验收基准。这一步没拿到样例，就不要往下走。
3. 同时读 [`references/02-assessment-dimensions.md`](references/02-assessment-dimensions.md)，做一次**基线评估**：15 个维度逐项打分（0–3 分），产出一张评分卡。基线评估的作用是——**发现用户没提到但确实存在的问题**，并给后续轮次排优先级。
4. 如果涉及主观体验（「读起来要顺」「不要太复杂」），按第 3 步走**最小原型验证**：先做 10% 给用户看，方向确认后再全量。
5. 按第 5 步把模糊标准转成硬判据（转化表见 [`references/05-acceptance-system.md`](references/05-acceptance-system.md) 第二节）。
6. 按第 6 步做**期望管理**：说清什么能做、哪里有 trade-off、大概几轮。

**产出**：需求确认单（含真实样例）+ 基线评分卡 + 硬判据清单。

### 场景 2：生成给执行方的任务指令

**触发**：需求已确认，准备开工。

**执行步骤**：

1. 打开 [`references/04-instruction-template.md`](references/04-instruction-template.md)，复制任务书模板。
2. 按 5 条生成原则填写，特别注意：
   - **每轮只聚焦 1–2 个核心问题**（贪多的轮次必然失焦）；
   - 验收标准**必须可量化**，禁止出现「优化体验」「更稳定」这类词；
   - 明确写**边界**：什么要改、什么**不要**改；
   - 写**执行顺序**：先低风险后高风险，每步后跑什么命令；
   - **保留退路**：新增功能一律用配置开关控制，默认关闭或保持旧行为，保证零回归。
3. 填完后用该文档的**指令质量自查清单**（12 项）逐项过一遍，任一项不通过就回去改指令，不要把不合格的指令发出去。

**产出**：一份可直接下发的任务书。

### 场景 3：审查执行方提交的产物

**触发**：执行方交付产物 + 报告（常见格式：任务书验收标准逐条对照表 + 门禁结果 + 披露事项）。

**执行步骤**：

1. **先复跑门禁，再看报告**。报告是自述，门禁是证据。顺序反了就会被「报告写得很漂亮」骗过去。
2. 读 [`references/05-acceptance-system.md`](references/05-acceptance-system.md)，按验收维度模板逐维核对，重点检查三类**必然出问题的地方**：
   - **判据口径是否被偷换**（例：把「逐字节零回归」偷偷改成「字数接近」）；
   - **通过的项里有没有 detail 与结论矛盾的**（例：结论 ✅ 但 detail 写着「不是合法 zip 包」）；
   - **新增的自检有没有反向用例**（一个永远不触发的自检等于没有）。
3. **对「未改动功能」验零回归**，最严判据是与上一版**逐字节相同**；做不到逐字节时用 A/B 对照 + 抖动基线（同版本重跑两次，把天然抖动项排除）。
4. **检查产物本身，而不只是检查报告**：拆开交付包、打开真实产物、跑一次真实端到端。v1.4.0 那轮的教训就是「85/85 全绿，但读者打开就能看出问题」。
5. **对未修的残余要求量化披露**（不能写「已知问题」了事，要写「0.08%，105 字，位于第 3 章」）。
6. 回到 [`references/02-assessment-dimensions.md`](references/02-assessment-dimensions.md) 复评 15 个维度，与基线对比。

**产出**：裁定结论（达标 / 有条件达标 / 不达标）+ 未通过项清单 + 下一轮任务书（若需要）。

### 场景 4：判断迭代是否可以结束

**触发**：想收尾时。

**执行步骤**：读 [`references/01-workflow-overview.md`](references/01-workflow-overview.md) 的「迭代终止条件」一节，**4 条硬性条件必须全部满足**：

1. 用户确认单里的**所有硬判据全绿**，且判据本身没有被放宽；
2. **零回归已用最强判据证明**（未改动功能与上一版一致）；
3. **所有未修项已量化披露**，且用户已知悉并表示接受；
4. **隐形维度不再有 0 分项**（至少没有「用户第一次用就会撞上」的坑）。

另有 3 条软性建议（模块 6 复盘已填、知识库已更新、文档与版本号已同步）—— 未满足不阻塞收尾，但必须写进披露事项。

**产出**：收尾裁定 + 复盘记录 + 知识库更新。

## 五、调用示例

### 示例 1：用户说「这个 skill 效果不好」（走场景 1）

```
用户：web-article-to-epub 转出来的电子书，听书的时候表格读不出来，很难受。

你：（读模块 3，不直接改）
    先确认场景 —— 「你是在哪个平台上听？是整段表格都没读出来，还是读了但分不清哪一列
    对哪一列？能贴一个具体表格的样子吗？」
    拿到例子后 → 「你期望听到的效果大概是什么样？我理解是『每一项都能听清它属于哪个
    列』，这样对吗？」
    → 转成硬判据：「104 个表格全部转成可朗读结构；1443 个非空数据格逐格比对
       100% 命中；TTS 顺畅性 0 违规（无连续标点、无标签残留）」
    → 期望管理：「原表格会保留，朗读版是额外附加的；可以退回旧行为，但我们先做一版给你听。」
    → 产出需求确认单，进入场景 2。
```

### 示例 2：写任务书（走场景 2）

复制模块 4 模板，本轮只聚焦一个主题（「表格朗读版改为列表形式」），写清 3 处改动、1 个新增配置键（默认值 = 新行为，同时保留旧行为开关）、12 项可勾选验收标准、执行顺序（先改渲染 → 跑专项门禁 → 跑验收矩阵 → 跑零回归对照 → 拆包自洽），最后用 12 项自查清单过一遍再下发。

### 示例 3：审查产物并裁定（走场景 3）

```
执行方报告：「专项 82/82、验收矩阵 169/169、单篇回归 20/20 全绿，另披露 1 项残余。」

你的动作（顺序不能反）：
  ① 复跑 8 道门禁 → 确认与报告数字一致；
  ② 检查口径 → 「段落形式与 v1.5.0 逐字节相同」是否真的逐字节？拒绝「字数接近」替代；
  ③ 检查自检的反向用例 → 门禁在「严格模式」下会不会真的报错（证明不是在放水）；
  ④ 拆开交付包 → 包内文件哈希与技能目录一致？包内门禁能否独立跑通？
  ⑤ 打开真实产物 → 语音播一遍，确认没有「全绿但人一听就皱眉」的地方；
  ⑥ 复评 15 维度 → 输出裁定。
```

## 六、注意事项与边界

1. **本技能不写业务代码**。它的产物是：评分卡、需求确认单、任务书、验收标准、裁定结论、复盘记录。真正改 skill 的代码由执行方（人或 AI）完成。
2. **不要跳过需求具象化**。没有「真实输入样例 + 期望输出描述」，后面的任务书和判据全是空中楼阁 —— 这是返工的最大来源。
3. **零回归是底线，不是目标**。「新功能生效」和「旧功能零回归」必须**同时**证明；只证明前者不算达标。
4. **警惕「全绿陷阱」**。门禁全绿只证明「你测的东西是对的」，不证明「用户会觉得好」。每轮收尾必须有一步「打开真实产物看一眼 / 听一遍 / 用一次」。
5. **不静默丢弃**。任何内容、字段、条目的丢失或跳过，必须在对应阶段显式告警并落到报告里；「不报错但少东西」是本技能案例库中出现频率最高的一类缺陷（6 轮里出现 4 次）。
6. **每轮只聚焦 1–2 个核心问题**。一轮塞进 5 个需求，结果必然是「每个都改了，每个都没改好」，而且回归风险成倍上升。
7. **新增功能默认走开关，保留退路**。让用户能一行配置退回旧行为，比事后回滚版本便宜得多。
8. **未修项必须量化披露**，格式：数值 + 占比 + 位置 + 影响判定。写「已知问题，后续优化」等于没披露。
9. **文档、配置、代码三处的版本号必须一致**，这是最常见的上架被拒原因之一。

## 八、与 darwin-skill 的角色边界（B1）

> 本技能与 `darwin-skill` 同属 Tier1 元优化（GOVERNANCE.md §2），但分工不同；触发词有重叠时按本表区分，避免混淆。

| 维度 | **skill-optimizer（本技能）** | **darwin-skill** |
|------|------------------------------|------------------|
| 角色 | **人驻环方法论**：只沉淀方法论、模板、清单、裁定 | **自主执行闭环**：自己编辑 SKILL.md 并 git 棘轮 |
| 是否改代码 | **不改**（§六-1：本技能不写业务代码） | **改**（hill-climbing 编辑 SKILL.md + commit/revert） |
| 核心产物 | 评分卡 / 需求确认单 / 任务书 / 验收标准 / 裁定结论 | 实测评分卡 + 改进后的 SKILL.md（git 分支） + 成果卡片 |
| 验证方式 | 复跑执行方门禁、拆包看真实产物（人审） | 跑测试 prompt（子agent 对比 baseline）+ 棘轮自动保留/回滚 |
| 闭环位置 | 人/执行方在回路外执行，本技能只审查裁定 | 自主循环，仅每 skill 优化完暂停等用户确认 |

**选用指引**：
- 需要「把需求挖清楚 + 设计可验收门禁 + 出一份能下发给执行方的任务书」→ 用本技能（人驻环，不改代码）。
- 需要「一个 agent 自主把 SKILL.md 改了、实测验证、好就保留坏就回滚」→ 用 `darwin-skill`（自主闭环）。
- **可串联**：本技能出评审结论与硬判据 → 把任务书交给 `darwin-skill` 作为执行方跑闭环；darwin 的实测评分亦可回填到本技能的验收维度。

**触发消歧**：两者 frontmatter 触发词有重叠（如「帮我改改skill」「skill review」「skill质量检查」）。默认按意图区分——要"方法论+任务书"优先本技能，要"自动改+实测"优先 `darwin-skill`；若不确定，先问用户要"方案"还是"自动改"。

**与常带三 skill 纪律的关系**：本技能作为铁律⑥常带三 skill 之一，平时以"判据在场"形式存在；全量加载仅当任务确为 skill 评估/优化（见 GOVERNANCE.md §4）。
