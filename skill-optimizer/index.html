Skill 优化大师

一套标准化的 skill 技能优化协作体系，帮你把任何 skill 从「能用」迭代到「优秀」

它是一个「审查官」，不是一个「代笔者」。当你手上某个技能用起来总觉得哪儿不对 —— 结果不全、听感别扭、上架被拒、改了新的坏了旧的 —— 这个技能会陪你把这团模糊的不适感，一步步收敛成一份说得清、做得准、验得了的需求与验收方案：先问清场景，再从 15 个角度体检一遍，然后写成执行方能照着做的任务书，最后用可复跑的门禁脚本证明「改对了，也真的没改坏」。

它全部沉淀自一个真实技能 web-article-to-epub 六轮迭代的完整过程 —— 包括那些踩过的坑、被推翻的判据、以及「报告全绿但用户打开就看出问题」的教训。所有方法、模板、清单都能直接拿来用，不写可执行代码。

一技能简介

它是做什么的、解决什么问题、核心价值是什么。

一句话说清：把「这个技能用着不太行」变成一份能让执行方照着做、也能被公正验收的施工方案。

大多数技能优化之所以反复返工，不是因为改得不够努力，而是因为三件事没说清：要改什么（用户只会说「效果不好」）、改到什么程度算好（没有可量化的判据）、怎么证明没改坏别的地方（只跑了新功能）。本技能就是来补这三块的。

核心卖点

↻

三方协作闭环

用户提需求 → AI 审查官评估并生成指令 → 执行方改代码交产物 → AI 审查官验证裁定 → 用户确认。每一轮都走「探查 → 约束 → 证据 → 执行 → 验证 → 交付」六步，角色边界清晰，不越位、不空转。

15

15 维度质量评估

7 个显性维度（功能完整性 / 实现正确性 / 体验质量 / 回归安全 / 工程化 / 性能与成本 / 安全与合规）+ 8 个隐形维度（认知负荷 / 可观测性 / 容错降级 / 用户心智模型 / 可组合性 / 依赖健康度 / 可迁移性 / 元数据可发现性），共 60 个可逐项勾选的评估问题，专门用来发现用户没提到的问题。

6

六步需求管理

场景还原 → 需求具象化 → 最小原型验证 → 变更分类响应 → 验收标准共同定义 → 期望管理。从用户说「效果不好」开始，一步步挖到可验收的硬判据，不熟悉技术的新手也能说清需求。

✓

硬判据验收体系

零回归是底线而非目标：未改动的功能要与上一版逐字节相同。判据全部脚本化、可复跑，且脚本自身要做反向自检 —— 能测出故意引入的错误，证明它不是在放水。最大反面教材是「全绿陷阱」：门禁全过，用户打开产物一眼就看出问题。

二什么时候用这个 skill

判断标准很简单：只要有「已有技能」需要变好，就该用它。

必须使用（6 个场景）

  • 要优化 / 改进 / 重构 / 评审任何一个已有 skill
  • 用户反馈某个 skill「效果不好 / 不好用 / 结果不对」，但说不清具体要什么
  • 需要给某个 skill 的改动写任务书（交给 AI 或工程师执行）
  • 需要验收某个 skill 的改动是否达标、是否引入回归
  • 需要判断某个 skill 的迭代是否可以结束
  • skill 上架 / 发布被平台拒绝，需要定位缺什么

不适用（3 个场景）

  • 从零创建一个全新 skill —— 本技能面向「优化已有技能」，不含需求从无到有的设计方法
  • 纯粹的业务执行（如「帮我抓这个网页」「帮我转这个格式」）—— 直接调用对应技能即可
  • 与 skill 无关的代码库优化 —— 方法论可借鉴，但触发条件不成立

四快速上手：三步开始使用

不需要提前准备什么，第一句话就可以是「这个技能效果不好」。

  1. 加载本技能

    在 WorkBuddy 对话框中输入 @skill-optimizer，或从「我的技能」列表中选择「Skill 优化大师」。加载后本技能会以「AI 审查官」的身份与你协作。

  2. 描述你的优化需求

    哪怕只是「这个 skill 效果不好」也可以 —— 本技能会用六步需求管理法帮你挖清楚：发生在什么场景、你的预期是什么、实际发生了什么、影响多大。你只管描述感受，不需要给出技术方案。

  3. 按引导完成三个阶段

    需求确认（含真实样例与硬判据）→ 任务书生成（交给执行方）→ 执行验收（裁定是否达标）。每次你需要做的事只有一件：确认或补充说明。

五使用方法：4 个典型场景

每个场景都给了可直接复制的提示词，以及你能拿到的产出。

场景 1用户提出 skill 优化需求 → 挖掘需求 + 基线评估

你只知道「不好用」，说不出具体要改什么。本技能会用六步需求管理法提问，并向你要一个真实样例，同时给出 15 维度基线评分卡，让后面的改进方向有依据、有对比。

预期产出
  • 需求确认单（含真实样例与模糊标准的量化转化）
  • 15 维度基线评分卡（7 显性 + 8 隐形，每项带证据）
  • 硬判据清单（本轮要证明什么，用什么方法证明）

场景 2生成给执行方的任务指令

需求已经确认，接下来要把「需求」翻译成「执行方能照着做、也能被验收」的任务书。任务书会明确标注什么要改、什么不要改，避免过度发挥。

预期产出
  • 一份结构化任务书：背景与问题 / 核心改动 / 配置项变更 / 可勾选的验收标准 / 执行顺序 / 注意事项
  • 附「已知的坑」清单（从反模式库中挑出与本轮相关的条目）

场景 3审查执行方提交的产物

执行方交了技能包和测试报告，报告可能全绿。本技能不会只看报告 —— 它会复跑门禁、核对比对口径有没有被悄悄放宽，并抽查真实产物。

预期产出
  • 裁定结论：达标 / 有条件达标 / 不达标
  • 未通过项清单（数值 + 占比 + 位置 + 影响判定）
  • 下一轮任务书（若不达标或仍有未修项）

场景 4判断迭代是否可以结束

已经改了好几轮，想知道能不能收尾。本技能会用四条硬性条件逐条核对 —— 缺一条就不算达标，而不是「感觉差不多了」。

预期产出
  • 收尾裁定：四条硬性条件逐条核对（判据未放宽且全绿 / 零回归用最强判据证明 / 未修项已量化披露 / 隐形维度无 0 分）
  • 复盘记录（六个必答问题）
  • 知识库更新建议（本轮新增的反模式与最佳实践）

七常见问题（FAQ）

新手最常问的 6 个问题。

Q这个 skill 能帮我写代码吗？

不能。本技能扮演「审查官」角色，负责需求挖掘、质量评估、任务书生成和验收裁定。真正改代码由执行方（WorkBuddy 或工程师）完成。

Q我完全不懂技术，能用这个 skill 吗？

可以。本技能的六步需求管理法就是为不熟悉技术的新手用户设计的，你只需要描述「哪里不好用」，剩下的由本技能引导你完成 —— 包括把「读起来要顺」这类感受，翻译成「TTS 顺畅性 0 违规」这类可验证的标准。

Q优化一个 skill 一般需要几轮？

根据 skill 类型不同：纯文档类 2-3 轮，单次执行类 3-4 轮，多阶段流水线类 5-7 轮，需要上架的额外 +1 轮。轮次不是越多越好 —— 每轮只聚焦 1-2 个核心问题，聚焦才能深入。

Q什么是「零回归」？为什么这么重要？

零回归指「未改动的功能与上一版完全一致」。它是优化的底线 —— 改新功能不能改坏老功能。最强判据是与上一版逐字节相同；做不到时退一步用 A/B 对照加抖动基线。只跑新功能、老功能「应该没事」，是典型的反面做法。

Q什么是「全绿陷阱」？

门禁全部通过，但用户打开产物一眼就能看出问题。原因是判据覆盖面不足 —— 断言只验证了「能跑通」，没验证「结果对不对」。所以每轮收尾必须有一步「打开真实产物看一眼 / 听一遍 / 用一次」，不能只看门禁结果。一旦遇到全绿但有明显问题，补判据比收尾更重要。

Q这个 skill 的知识沉淀怎么用？

每次优化结束后，本技能会引导你填写复盘模板（六个必答问题），并把新发现的反模式和最佳实践入库。下次优化其他 skill 时，先扫一遍反模式库，避免重复踩坑 —— 目前库中已有 13 条反模式与 14 条最佳实践，全部来自真实事故，不是理论清单。
