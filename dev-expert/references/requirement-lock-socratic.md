# 需求锁定门控（苏格拉底质询 · requirement-lock-socratic）

> **本文件是「澄清强度判定」的唯一权威**（v1.18.0 起）。
> `execution-safety.md`「澄清策略分级」已迁移为指针，`spec-driven-development.md` 的模糊词表、SKILL.md Step 1.5 的触发信号均以本文件为准，不得各自另立标准。

## 定位

本门控是**执行流程的前置门控**：在路由匹配完成、进入方案与执行之前，通过**多轮递进质询**暴露需求中的隐含假设，直到需求被"锁定"（LOCKED）或显式降级，才允许进入 Step 2。

它解决的问题：Agent 倾向于用"看似合理的默认值"填补需求空白，而这些默认值一旦猜错，返工成本远高于多问三句。本门控把"我觉得用户应该是要……"替换为"用户已确认要……"或"用户未答，此为显式假设，误判后果为……"。

**与既有 Step 1.5 的差异**：原 Step 1.5 的默认动作是「**先提案再纠**」——需求虽模糊但可行动时先输出方案让用户纠正。本门控在**复杂任务与高后果场景**把默认动作反转为「**先锁定再行动**」，并把"百分之百了解需求"转化为可判定的收敛条件（见第四步）。仅 Q1 档位保留"单轮确认后直行"的快速通道。

## 第一步：质询档位判定（Q0 – Q3）

| 档位 | 触发条件（满足任一即归入该档） | 质询轮数 | 每轮问数 | 是否阻塞执行 |
| - | - | - | - | - |
| **Q0 免问** | 纯信息查询 / 只读评估 / 解释比较类请求，未要求写文件 | 0 轮 | — | 否 |
| **Q1 单轮确认** | 简单任务：单文件或 ≤3 文件；风险低；有最小验证闭环；验收口径可从上下文无歧义推出 | 1 轮 | ≤3 问 | 否（用户确认或采纳默认值即执行） |
| **Q2 多轮质询** | 常规复杂任务：跨模块改动 ≥2 处且边界未定义；涉及数据模型变更但实体关系未澄清；验收口径需对齐；需求隐含多个视角未区分优先级 | 2–3 轮 | ≤3 问 | 是（须 LOCKED 或显式降级） |
| **Q3 深度质询** | **高后果场景**：不可逆操作 / 生产配置变更 / 数据库写入 / 权限与凭证 / 隐私数据 / 多利益方冲突 / 用户目标模糊且无历史上下文可推断 | 3–5 轮 | ≤3 问 | 是（**硬卡，不可降级**） |

**判定顺序**（自上而下，命中即停，避免档位摇摆）：

1. 先判 **Q3**：命中任一高后果条件 → 进 Q3。
2. 再判 **Q2**：命中任一复杂任务条件 → 进 Q2。
3. 再判 **Q1**：命中简单任务特征 → 进 Q1。
4. 兜底 → **Q0**。

**档位不可下调规则**：Q3 一经命中，任何理由（包括"改动看起来很小""有 .bak 备份""用户说快点做"）都不得降为 Q1/Q0。涉及数据库 / 权限 / 生产配置 / 凭证隐私时，安全闸门优先于效率诉求。**允许上调**（发现新信息后 Q1→Q2→Q3 可升级，升级时须说明原因）。

**与依赖分析的关系**：本体量判定在路由匹配（SKILL.md Step 1.2）之后、Step 2 方案之前执行。若任务触发 Wayfinder 模式（目标模糊且描述极短），先走 Wayfinder 收敛为明确任务，再回到本门控判档。

## 第二步：六槽位需求锁定清单（Requirement Lock Slots）

质询的目标是填满以下六个槽位。**槽位的值必须来自用户陈述，或用户从选项中选择的项；严禁 Agent 自行以"合理假设"填写后标注为已确认。**

| 槽位 | 名称 | 必填内容 | 合格判据（如何算填满） |
| - | - | - | - |
| **S1** | 目标 | 交付物是什么 + 成功判据（做完后如何判定"成了"） | 能写出「交付 X，判定标准为 Y」一句话 |
| **S2** | 边界 | In scope / Out of scope **显式清单** | 至少各列出 1 条；"都行""你决定"不算 |
| **S3** | 验收 | ≥1 条**可执行**验证判据 | 含可运行的命令 / 断言 / 可观测指标（如"P95 < 300ms""`npm test` 全绿""错误率 < 1%"）。仅"要好用""要稳定"不合格 |
| **S4** | 约束 | 技术栈与版本、兼容性、性能、合规、**风格基线**（沿用项目现有风格还是新建范式） | 每条约束可被一条命令或一次静态检查验证，或可明确指名基线文件 |
| **S5** | 数据与状态 | 涉及实体、状态机、持久化、迁移、缓存、并发 | 列出受影响的数据对象与状态流转；无数据影响须**显式声明"无"** |
| **S6** | 风险与回滚 | 不可逆点、回滚路径、受影响方（谁会因此改变行为） | 至少写明 1 个不可逆点及其处置；无不可逆点须**显式声明"无"** |

**槽位的两类合格值**：
- **已确认值**：用户明确陈述或从选项中选定 → 计入锁定。
- **未确认值**：Agent 的默认假设 → **不计入锁定**，只能出现在降级路径的「假设清单」中（见第五步）。

## 第三步：苏格拉底四式（提问方法）

单纯堆砌问题会退化为问卷。**本门控要求提问具备"递进质询"性质**——每一问都意在暴露一个用户尚未意识到的隐含假设。四式如下：

### 式一：定义式（把形容词转为可验收量）

用户给出的模糊形容词，一律要求转为可量化口径：

| 用户说 | 追问方向 |
| - | - |
| "快" | 哪条路径快？P95 还是平均？目标值 < ? ms |
| "稳定" | 可用性 ?% / 错误率 < ?% / 故障恢复 < ? min |
| "安全" | 需覆盖哪些威胁（XSS / CSRF / SQL 注入 / 权限绕过 / …）？哪一类可暂不覆盖 |
| "好用" | 关键路径几步完成？目标用户是谁？ |

### 式二：省略式（沉默点清单）

**主动指出需求中"没有说"的部分**，逐条请用户确认——这是本门控与普通澄清最大的区别。典型沉默点：

- 并发与会话：同一账号多端同时操作会怎样？
- 空值与异常：数据为空、字段缺失、接口超时时的表现？
- 权限边界：谁能看到 / 谁能改？
- 幂等性：重复提交怎么办？
- 存量数据：历史数据要不要一起处理？
- 兼容性：是否需要兼容旧版本 / 旧浏览器 / 旧接口调用方？

每轮至少点出 **1 条**沉默点。沉默点被用户确认或否决后即成为 S2/S4/S5 的正式内容。

### 式三：反例式（边界反例确认取舍）

给出一个**用户方案会失效的具体边界场景**，请其确认是"必须处理"还是"接受不支持"：

> "如果同一用户在两台设备上同时提交，当前设计会出现 X。你要（a）加锁串行（成本：Y）、（b）最后写入胜出（风险：Z），还是（c）这个场景不存在？"

反例式用于逼出隐性需求，也用于把"取舍"的责任明确交回需求方。

### 式四：反选式（要求给出"为什么不用 B"）

不只问"要什么"，还要问"**为什么不要**另一个常见选项"。这能暴露约束条件（成本 / 团队能力 / 已有系统 / 时间窗）——而这些约束往往比需求本身更决定实现方案。

> "同类需求常见做法还有 B（优势：…；代价：…）。你排除 B 的原因是什么？"

**使用约束**：每轮提问须至少覆盖 **2 式**；不得连续两轮只使用同一式（防止单维度盘问）；式二「沉默点清单」在 Q2/Q3 档位为**必用**。

## 第四步：轮次推进与收敛条件

### 每轮的固定输出结构

每轮质询结束、用户作答后，Agent 必须先输出三段小结再进入下一轮：

```
【第 N 轮小结】
· 本轮已锁定：S1 目标（…）；S4 约束（…）
· 仍空缺：S3 验收口径；S6 回滚路径
· 下一轮问什么：S3 的量化口径（2 问）、S6 的不可逆点（1 问）
```

**目的**：让用户始终看得见"还差什么"，避免无边界追问；同时使质询过程可审计。

### 收敛条件（判定为 LOCKED）

以下三条**同时**满足，方可判定需求已锁定：

1. **S1–S6 六个槽位全部非空**；
2. 槽位中**不含** `TBD` / `待定` / `你决定` / `随便` / `都行` 之类的空洞值；
3. **S3 至少含 1 条可执行判据**（命令 / 断言 / 可观测指标）。

达到 LOCKED 后，输出**需求锁定卡**（见第六步），请用户一次性确认或修正。用户确认后方可进入 Step 2。

### 轮次上限与强制收敛

| 档位 | 上限 | 达到上限仍未 LOCKED 时 |
| - | - | - |
| Q1 | 1 轮 | 直接采纳默认值并**在交付物中声明假设**（不阻塞） |
| Q2 | 3 轮 | 停止追问 → 转第五步降级 |
| Q3 | 5 轮 | 停止追问 → 转第五步降级（**但硬卡项仍须阻塞**，见第五步） |

**强制收敛触发器**（命中任一即停止追问，不必等轮次耗尽）：

- 用户连续 2 轮回答未产生任何新的槽位信息（空转）；
- 用户明确表达不耐烦（"到底要问多少"）；
- 某槽位经 2 次追问仍无法收敛 → 转为显式假设，不再追问该槽位。

## 第五步：退出协议（用户中断 / 轮次耗尽 / 强制收敛）

### 正常退出（用户显式授权跳过）

**触发**：用户说「直接做 / 别问了 / 按你判断 / 不用问了 / 先做出来再说」，或输入 `@skip-socratic`，或回答中明确表示愿意承担猜错风险。

**动作**（四步，不可省略）：

1. **立即停止追问**，不再补问任何槽位。
2. 输出**「假设清单 + 风险声明」**：逐条列出未锁定槽位的默认假设，每条标注 `【未确认】`，并写明**误判后果**。格式：

   ```
   【假设清单（未确认）】
   · S3 验收口径【未确认】：默认以"单元测试全绿 + 页面无控制台报错"为准。
     误判后果：若你实际需要性能指标（如首屏 < 1s），本轮交付将不含性能验证，需返工补测。
   · S6 回滚【未确认】：默认不涉及不可逆操作。
     误判后果：无（若有数据迁移，则此假设不成立，须立即告知）。
   ```
3. **自主度下调一档**，并在执行中降低批量操作规模（更小的提交粒度、更频繁的 checkpoint）。
4. 在交付物与 SELF-AUDIT 中记录：**需求锁定 = 已降级（未确认假设 N 条）**。

### 硬卡例外（Q3 不允许降级）

Q3 档位中，涉及**不可逆操作 / 生产配置 / 数据库写入 / 权限与凭证 / 隐私数据**的槽位**不允许跳过**：

- 用户拒绝回答 → 输出**「阻塞」**而非「降级」，明确写出"缺少 X 信息，无法安全执行，请提供后再继续"；
- 不得以"用户说直接做"为由越过安全闸门；
- 非安全相关的 Q3 槽位（如多利益方优先级）可在用户授权后降级。

### 失败回退机制

| 步骤 | 失败类型 | 回退目标 | 最大重试 | 不可恢复时升级路径 |
| - | - | - | - | - |
| 第一步 | 档位判定摇摆（Q1/Q2 反复） | 按判定顺序自上而下重判一次 | 1 | 就高不就低，取更高档位，并在小结中说明 |
| 第二步 | 某槽位用户明确表示"不知道" | 该槽位转为显式假设 | 2 | 记入假设清单，不阻塞（Q3 硬卡项除外，转阻塞） |
| 第三步 | 提问引发用户反感 | 立即改用语二"沉默点清单"式陈述，请用户确认/否决 | 1 | 转第五步降级 |
| 第四步 | 轮次耗尽仍未 LOCKED | 转第五步降级 | 0 | Q3 硬卡项转阻塞；其余按假设清单执行 |
| 第六步 | 用户对锁定卡提出修正 | 更新对应槽位，重新生成锁定卡 | 3 | 超过 3 次修正 → 判定需求不稳定，建议先澄清上游目标再开工 |

## 第六步：需求锁定卡（交付用户一次性确认）

LOCKED 或降级时，输出以下卡片请用户确认。**这是用户进入执行前的最后一道确认点。**

```markdown
【需求锁定卡】
· 质询档位：Q2（共 3 轮 / 7 问）
· 状态：LOCKED ／ 已降级（未确认假设 N 条）

| 槽位 | 内容 | 来源 |
| - | - | - |
| S1 目标 | … | 用户陈述 |
| S2 边界 | In：… ／ Out：… | 用户选定 |
| S3 验收 | 判据 1：`命令/断言` | 用户确认 |
| S4 约束 | 技术栈…；风格基线… | 用户陈述 |
| S5 数据与状态 | … ／ 无 | 用户确认 |
| S6 风险与回滚 | 不可逆点…；回滚… ／ 无 | 用户确认 |

· 未确认假设：（若有，逐条列于此，含误判后果）
· 请回复「确认」进入执行，或指出需修正的槽位。
```

用户回复「确认」后进入 Step 2。用户仅修正部分槽位时，只更新对应行并**只需重新确认该行**，不必重走全部质询。

## 第七步：落盘与可审计

### 落盘位置

写入 `{PROJECT_ROOT}/.ai-memory/{YYYYMMDD}/requirement_lock_{session-id}.md`（`session-id` 生成时机见 `execution-safety.md`，统一为 Step 0）。

内容为需求锁定卡全文 + 质询轮次记录（每轮的问题与用户答复摘要）。**append-only，不覆盖历史会话的锁定卡。**

### 交付物中的必填字段

以下三处必须出现需求锁定的记录，否则视为门控未执行：

| 位置 | 必填字段 |
| - | - |
| 执行计划 / `_plan.md` | `需求锁定：Q{n} / LOCKED 或 已降级（未确认 N 条）` |
| Step 5 交付物 | 需求锁定卡（或降级说明 + 假设清单） |
| SELF-AUDIT | 增列一项「需求锁定已完成或已显式降级」 |
| `session_memory` | 记录 `档位 / 轮次 / 未确认假设数` |

### 强制化 hook（可选）

若需把本门控从"指令约束"升级为"技术约束"，启用 `hooks/socratic_gate.py`（opt-in，默认关闭）：

```bash
export SOCRATIC_GATE=1        # 启用
export SOCRATIC_GATE=0        # 关闭（默认）
```

启用后，PreToolUse 阶段会检查当日是否存在状态为 `LOCKED` 的锁定卡；缺失则阻断对源码文件的写入（exit 2），并提示先完成需求锁定。Trivial Fix 通道（单文件且 ≤1 行，或 ≤3 文件且每文件 ≤5 行，且不含结构变更）自动豁免。

> 该 hook 的目的不是刁难，而是让"先锁定后执行"在 Agent 自我合理化时仍无法绕过。

## 反模式（真实执行易踩，逐条自查）

| 反模式 | 表现 | 纠正 |
| - | - | - |
| **伪锁定** | 把 Agent 自己的假设填进六槽位，然后判定 LOCKED | 槽位值必须能追溯到用户陈述或用户选定项；默认假设只能进降级路径的假设清单 |
| **空转追问** | 连续多轮提问但槽位无新增信息，只是换措辞重问 | 触发强制收敛，转降级；同一槽位最多追问 2 次 |
| **诱导式提问** | 把假设写成问句诱导用户默认同意（"我理解你想要 X 对吧？"连问） | 提问须给 ≥2 个真实候选项 + 各自代价，不得只给单向确认 |
| **越权跳过** | 用户说"快点做"就自行把 Q3 降为 Q1 | Q3 硬卡不可下调；安全相关槽位拒绝回答时输出"阻塞"而非"降级" |
| **只问不记** | 质询做了很多轮，但交付物与 SELF-AUDIT 无任何锁定记录 | 第七步四个落点位为必填，缺任一项视为门控未执行 |
| **档位僵化** | 开局判 Q1 后，后续发现涉及数据迁移仍不加码 | 允许且要求上调档位；发现新信息即重判 |

## 与既有机制的关系（避免规则打架）

| 既有机制 | 关系 |
| - | - |
| SKILL.md Step 1.5 | 本门控**取代**原 Step 1.5 的门控动作；Step 1.5 保留为触发入口，判定与执行一律以本文件为准 |
| `execution-safety.md`「澄清策略分级」 | 已迁移为指针，唯一权威为本文件。其安全闸门交叉引用保留：涉生产配置 / 数据库写入 / 权限 / 凭证 / 隐私 / 不可回滚操作时，档位不得低于 Q3 |
| `spec-driven-development.md` 模糊词表 | 该表用于 Spec 文档撰写时的措辞检查；**澄清强度的判定以本文件为准**，两者不重复计档 |
| `delivery-assurance.md`「确认超时默认规则」 | 「5 分钟无回复 → 最保守选项自动推进」**不适用于 Q3 硬卡项**；非硬卡的 Q2/Q3 槽位在用户授权降级后方可按该规则推进 |
| 意图三分法（信息查询 / 简单任务 / 复杂任务） | 三分法决定**执行模式**（是否改文件、是否先方案），本门控决定**澄清强度**；两者组合使用，不互相替代 |
| 「轮次与收敛」/ 失败熔断 | 本门控的轮次上限与收敛规则与之兼容；质询轮次计入同一会话的失败熔断计数 |
| `@<英文标识>` 显式调用 | 显式调用**不跳过**本门控（仅跳过关键词路由）；唯一跳过方式是 `@skip-socratic` 或自然语言显式授权 |
| `ai-coding-governance.md` | 为 AI 编码 Agent 设定行为边界时，本门控是该治理体系的"输入端"控制点 |

## 输入要求

- 用户原始需求文本（必填）
- 项目上下文（可选）：技术栈、已有架构、历史决策 —— 触发 Step 0 / Step 1.1 记忆加载时自动获取
- 复杂任务依赖闭包（可选，Q2/Q3）：由 `project-knowledge-graph` 提供，用于让质询问题更精准（例如"改动 A 会影响 B，B 是否在范围内？"）

## 输出格式

```markdown
【需求锁定卡】
（见第六步模板全文）

【假设清单（未确认）】（仅降级路径）
· S3 验收口径【未确认】：… ／ 误判后果：…

【质询记录摘要】
· 第 1 轮（3 问）：S1/S2/S4 → 已锁定
· 第 2 轮（3 问）：S3/S5 → 已锁定
· 第 3 轮（1 问）：S6 → 已锁定
· 状态：LOCKED
```

## 质量标准

- 档位判定可解释：能说出为什么是这一档，而不是另一档；
- 六槽位全部可追溯到用户输入，无 Agent 自填；
- S3 验收槽位含至少 1 条可执行判据；
- 每轮提问覆盖 ≥2 式，且 Q2/Q3 必用式二（沉默点清单）；
- LOCKED 或降级状态在交付物、SELF-AUDIT、`session_memory` 三处可查；
- 反模式自查表逐条过一遍，任一命中即纠正后再继续。
