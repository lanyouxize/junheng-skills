# 根因调试硬闭环（Root-Cause Debugging）

> **定位**：本文件是**修复过程门禁层**——复现(Red) → 假设 → 只修根因 → 验证(Green→Red 确认) → 回归留仓 → 防御纵深；**只定义"不可跳过的门禁与产出物"，不再定义与父文件平行的第二套诊断流程**。定位与结论层见 `bug-diagnosis.md`（第一~五步定位、诊断报告、证据交叉验证表、CMS 场景知识库），本文件不重复其条文。
> **触发**：修 Bug、排查报错、复现问题、回归失败、生产事故定位、"为什么 X 不工作"、`RCA`、`debug`。凡进入 Bug 诊断流程，本专项自动作为协同纪律加载。
> **铁律**：**无根因不修复**。禁止症状修补（symptom patch），禁止"这次不报错就算修好"；复现门禁（第五步）必须先于任何改码。

## 第一步：Triage 捕获（任何修复前必做）

动手前先补齐现场信息，缺关键项（尤其复现起点 / 症状）直接向用户追问，不得自行猜测：

```
## Triage

- **Symptom**: 用户描述的现象，一句话
- **Expected**: 正常应该怎样
- **Repro 起点**: 命令 / 输入 / URL / 触发动作
- **Environment**: OS / runtime / 相关依赖版本（只列与 Bug 可能相关的）
- **First seen**: 何时开始出现 / 关联哪些近期改动
- **Severity**: 阻塞 / 影响功能 / 视觉小瑕疵
```

**Clean-tree 检查点**：首次写文件前检查工作区状态（`git status --short` / `git branch --show-current`），明确当前分支与未提交改动，防止修复混入无关变更。

## 第二步：模式选择（按复杂度定投入）

| 模式 | 触发场景 | 假设数量 | 插桩 | 防御纵深 | 产出 |
| ---- | -------- | -------- | ---- | -------- | ---- |
| quick | typo / off-by-one / 单文件单函数 / 用户已点出疑似行 | 1 条即可 | 不做 | 跳过 | 简短摘要 |
| 默认 | 多文件 / 中等复杂度 / 描述含糊 | 1-2 条（标置信度） | 可选 | 跳过 | 标准修复报告 |
| deep | 间歇性 / 偶发 / heisenbug / 竞态 / 跨系统 / 生产事故 | **强制 3-5 条跨维度** | **必做**（tagged log） | 强烈建议 | 完整 RCA + 预防措施 |

**模式自动升级信号**（命中任一，主动建议升 deep，交用户确认）：
- Severity 为 blocker / 涉及财务影响 / 数据破坏
- First seen 含"间歇性 / 偶发 / ~N% 概率 / heisenbug"
- 症状跨服务 / 跨进程 / 跨线程 / 跨 host
- 复现 flaky（连续 3 次失败不足 3 次）

## 第三步：假设列表（Hypothesis）

强制列出多个假设并显式排除，**不许直接"我觉得是 X"就动手**。假设须跨维度覆盖：代码逻辑 / 数据 / 并发 / 环境 / 需求误解。

```
## Hypotheses
- H1: [描述]  — 置信度 H/M/L — 排除动作: [最小验证]
- H2: [描述]  — 置信度 H/M/L — 排除动作: [最小验证]
- H3: [描述]  — 置信度 H/M/L — 排除动作: [最小验证]
```

每个候选根因至少匹配一种验证证据（**6 类证据 × 适用场景 × 验证方式见 `bug-diagnosis.md` 第四步「证据交叉验证表」**），证据不足时输出"最可能原因 + 待验证动作"，不得写成已确认根因。

## 第四步：反向追溯（Backward Trace）

从症状出发**向后**追踪：最后一次正确的输出在哪个环节？之后发生了什么？

- 沿调用链从出错分支向上游回溯，逐层确认前置条件是否成立
- 记录关键变量的状态变化，说明"为什么会进入该非法状态"
- 涉及图遍历 / 环检测 / 状态机 / 依赖解析的缺陷，先建立方向语义模型（边方向、遍历方向、状态迁移是否解耦）再判定，不得仅凭"跑通了"判定修复有效（**本处为方向语义模型唯一出处**，`bug-diagnosis` 仅引用）

## 第五步：失败测试复现（Red）

**修复前必须先有失败测试**——这是硬门禁，任何模式不可跳：

1. 构造最小输入 / 最小用例，使测试**稳定复现失败**（Red）
2. 复现不稳定（flaky）时，回到第二步升级 deep 模式，先解决确定性再继续
3. 测试能证明"Bug 确实被抓到"才算数；测试没写、或测试在修复前就通过 → 视为未开始修复

## 第六步：只修根因（Surgical Fix）

- **只改根因路径**，禁止夹带"顺手优化"邻近代码
- 发现需要重构 → **单独提建议**交用户决定，不在本流程内夹带
- 根因 vs 补丁判定门禁（**唯一出处**，`bug-diagnosis` 仅单行引用）：
  - 修复是否消除**所有同类触发路径**？还是只在当前输入挡住了症状？
  - 若修改只针对"这次不报错"（如加一个 `if (x) return`）而未说明为何进入该状态 → 即补丁，必须继续追问上游成因
  - 每发现补丁式修复，写下"为何会进入该非法状态"，直到追溯到真正成因或明确标注"上游根因待查"
  - 命中补丁风险时，报告中单独标注「补丁风险」+ 上游最小排查动作

## 第七步：验证与回归（Green → Red 确认）

**Red→Green→Red 三步循环**是验收硬门槛：

1. **Green**：修复后测试通过，且原有测试全绿
2. **Red 确认**：临时还原修复（或 checkout 修复前版本）跑失败测试，确认它**确实会失败**——证明测试真能抓住该 Bug
3. **回归留仓**：失败测试**必须保留入库**作为回归测试，不得删除或注释掉

## 第八步：防御纵深与复盘

- **防御纵深**（deep 模式必做）：不止修当前触发点，还要在相邻层（入口校验 / 中间层 / 出口）补防御，防止同类路径再次进入非法状态
- **模式匹配查册**：排查耗时 ≥ 40 分钟时，先查 `error-ledger.md` 索引按错判形状做模式匹配；新踩的坑按该册强制记录（ERR-ID + 错判点 / 正确判据 / 盲区）
- **沉淀**：修复完成后按 SKILL.md「写后即记协议」追加 `daily.md`，并按 `bug-diagnosis.md` 第八步更新项目记忆

## 输出模板（修复报告）

> **适用条件**：**凡涉及改码修复的场景，本模板是唯一交付模板**（字段集与 `bug-diagnosis` 诊断报告不互含，两者不得混用）：本模板出「症状 / 根因 / 证据 / 修复 / 验证（Red·Green·Red 确认·留仓 4 勾选）/ 补丁风险 / 已知限制」；`bug-diagnosis` 的「错误类型 / 错误信息 / 发生位置 / 根因分析 / 修复方案 / 验证方法 / 预防措施」模板仅适用于**只读诊断、不改码**场景，在改码场景降级为本次修复的中间产物。

```
## 修复报告

**症状**：[一句话]
**根因**：[确认根因 + 为什么进入该状态]
**证据**：[失败测试 Red 输出 / 日志 / 复现路径]
**修复**：[文件:行号 + 改动说明；标注是否仅动根因路径]
**验证**：
- [x] Red：修复前失败测试复现失败（附输出）
- [x] Green：修复后测试通过
- [x] Red 确认：还原修复后测试重新失败
- [x] 回归测试已留仓：[测试文件:用例名]
**补丁风险**：[无 / 有，见说明]
**已知限制**：[无法验证项显式列出]
```

## 失败回退

| 步骤 | 失败类型 | 回退目标 | 最大重试 | 不可恢复时升级路径 |
| ---------------------------------------- | ------------------------------ | ------------------------------------------------------------ | -------- | -------------------------------------------------------------- |
| 第一步：Triage 捕获 | 缺复现起点 / 症状描述含糊 | 向用户追问最小信息集（现象 + 触发动作 + 环境） | 2 | 标注"现场信息不足"，只输出假设清单与待补信息 |
| 第二步：模式选择 | 复杂度无法判断 / 复现持续 flaky | 直接升 deep 模式 | 1 | 按 deep 模式执行并标注"模式待确认" |
| 第三步：假设列表 | 假设全部被排除 | 扩大假设维度（数据 / 并发 / 环境 / 需求误解），回到第一步补现场信息 | 3 | 列 2-3 条替代方向交用户选（SKILL.md「不卡死计数器」） |
| 第五步：失败测试复现（Red） | 复现不稳定（flaky） | 升 deep，先解决确定性再继续 | 3 | 暂停盲改，改按假设验证清单交付，标注"未能稳定复现" |
| 第六步：只修根因 | 修复后仍有失败 | 回到第四步重新追溯，不重复尝试同一修复 | 3 | 暂停，列 2-3 条替代方案交用户选 |
| 第七步：验证与回归 | 无测试框架，回归测试无法留仓 | 输出可手工执行的复现命令清单 | 1 | 标注"回归未留仓"，在 `daily.md` 记录遗留项并提示补建测试 |
| 第八步：防御纵深与复盘 | 排查耗时 ≥ 40 分钟仍无结论 | 查 `error-ledger.md` 索引做错判形状模式匹配 | 1 | 按册强制记录（ERR-ID + 错判点 / 正确判据 / 盲区）后升级用户 |

与 SKILL.md「失败重试基线」冲突时，以基线为准。
