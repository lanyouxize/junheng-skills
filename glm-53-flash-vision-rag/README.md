# GLM-5.3-Flash Vision RAG

> 让 AI **真正"看懂"** 一份 PDF，然后你对它提问：它告诉你答案、答案在第几页，
> 并把那一页的原图展示出来给你核对。

基于智谱视觉大模型 **GLM-5.3-Flash** 的 PDF 深度问答与检索（vision RAG）agent
skill。支持文字版 PDF，也支持**扫描版**；能看懂**图表、表格、代码块、公式**，
而不只是认字。

> 姊妹版：`../deepseek-v4-flash-vision-rag/`（DeepSeek 引擎，架构完全同构）。
> 两边可以同时索引同一本书，对照两引擎的回答质量。

---

## 一、它能做什么

| 你说 | 它做 |
|---|---|
| "帮我读一下这份 120 页的手册" | 逐页视觉阅读，建立可检索的索引（约 3 分钟，只需一次） |
| "审批策略出厂默认是什么？" | 给出答案，标注 `[第6页]`，并把第 6 页原图给你看 |
| "§05 在第几页？讲了什么？" | 定位章节起止页码 + 内容总结 |
| "这个概念在哪几页被提到？" | 找齐全书所有相关页（跨页召回） |
| "给我看看第 72 页" | 高清渲染该页图片 |
| "对比一下 XX 和 YY" | 基于相关页内容做深度对比分析 |

每次回答都会生成一个**自包含 HTML 预览页**（答案 + 全部引用页原图内嵌其中），
双击浏览器打开即可查看，无需联网。

## 二、实测效果（GLM 引擎，120 页中文技术书）

| 环节 | 结果 |
|---|---|
| 建索引（一次性） | **188 秒**：20 页/请求 × 6 次调用，零失败页 |
| 页面识别精细度 | 正确区分封面/版权/目录/**106 页正文/10 页附录**（DeepSeek 版未细分附录），大纲 151 条 |
| 提问响应 | 每次 **2 次 API 调用**，十几秒出答案 |
| 四模式问题 | 名称、机制全部正确：PTC=Code mode 跑 TypeScript、极简模式 Windows 跑不起来等细节均答出；引用页与 DeepSeek 版交叉吻合 |
| 诚实性 | 只索引前 8 页时追问全书问题，明确回答"§03 正文不在提供页面中"，不编造 |

## 三、工作原理（通俗版）

整个系统就做两件事，像人读一本书：

### 第一阶段：读一遍书，做笔记（ingest，一次性）

```
PDF ──渲染──> 每页一张图片
                │
                ├──抽取文字层──┐
                │              │
                └─→ 视觉模型逐页"阅读"
                    （20 页打包进 1 个请求，
                     吃满 1M token 上下文）
                            ↓
              index.json（每页一张"读书卡片"）
```

模型每读一页，就写一张卡片——**这就是 `index.json`**。第 22 页的真实卡片长这样：

```json
{"page": 22,
 "type": "正文",
 "headings": [{"level": 1, "text": "§03 四种模式，人话版"}],
 "summary": "介绍四种模式：标准、PTC、极简、创造，并指出它们不在同一维度上。",
 "keywords": ["四种模式", "标准", "PTC", "极简", "创造"]}
```

120 张卡片 + 每页文字层 + 由标题派生的全书大纲，一起存进缓存。
**从此这本书就被"读过了"，这个步骤永远不用再做。**

### 第二阶段：按笔记翻书，回答问题（ask，每次提问）

```
你的问题
   ↓ ① 查卡片     本地在 index.json 里筛出最可能的 12 页（毫秒级，零费用）
   ↓ ② 看图确认   模型看这 12 页截图，挑出真正相关的 4 页（第 1 次 API 调用）
   ↓ ③ 深读作答   这 4 页 ± 前后邻页原图摊开，高强度推理仔细读（第 2 次 API 调用）
   ↓
答案（每个论点标 [第N页]）+ 引用页图片 + 自包含 HTML 预览
```

**为什么是三层漏斗？**——便宜的方法粗定位、贵的眼睛做确认、最贵的推理只用在
刀刃上。120 页 → 12 页（免费）→ 4 页（low 档，快）→ 深读（high 档，质量）。

#### ① "查卡片"具体怎么查（本地检索，零 API 成本）

经典 TF-IDF 关键词打分，全程只是 Python 字符串运算：

1. **分词**：中文二字滑窗——"审批策略"切成 `审批 / 批策 / 策略`；英文取整词；去停用词
2. **造页面文档**：每页 = 标题、摘要、关键词各重复 3 遍 + 整页文字层 1 遍
   （摘要命中比正文顺嘴提一句值钱 3 倍）
3. **打分**：`得分 = Σ 词的稀有度(idf) × min(出现次数, 8)`
   ——只出现在 1 页的词很值钱，全书到处都是的词几乎不计分；次数封顶防刷分
4. **排序取前 12 名**交给第 ② 步看图确认

词面匹配有盲区（词对主题不对的噪声页、主题对用词不同的漏网页），
所以第 ② 步必须让模型**看图**凭内容把关。

## 四、为什么不用更简单的方案

| 方案 | 每次提问的成本 | 看得懂图表/扫描件吗 | 页码引用 |
|---|---|---|---|
| A. 每次整本塞给模型 | 数万 token，几十秒 | 能 | 能 |
| B. 传统文字 RAG | 便宜快 | **不能** | 常错 |
| C. PageIndex 类结构工具 | 只生成目录树，**没有问答** | 不能 | 靠模型猜+修复循环 |
| **本 skill** | **2 次调用、秒级** | **能**（看的是页面图） | **天然精确** |

页码天然精确的原因：每张图片就是"第 N 页"渲染出来的，标签与图像绑定——页码
来自物理事实，不需要模型猜。

## 五、快速上手

### 环境要求

```bash
pip install openai pymupdf    # 本机一般已装好
```

API key 不内置在代码里（skill 可公开分发）：设置环境变量 `GLM_API_KEY`，
或把 key 写入 `~/.glm_api_key` 文件首行（仅存在于本机）。

### 1. 建索引（每份 PDF 一次）

```bash
python scripts/ingest.py "你的文件.pdf"
```

- 120 页约 3 分钟；重复运行直接命中缓存，瞬间返回
- 常用参数：`--force` 重建｜`--limit 30` 先索引前 30 页试水｜`--clean` 清缓存
- 大文档建议先 `--limit 30` 看看页型分布对不对，再跑全量

### 2. 提问

```bash
python scripts/ask.py "你的文件.pdf" "审批策略出厂默认是什么？"
```

输出四段：`=== 答案 ===`（带 [第N页] 引用）、`=== 引用页 ===`、
`=== 页面图片 ===`（PNG 已复制到 `./pdf-vision-out/`）、`=== 预览 ===`
（HTML 文件路径，双击浏览器打开）。可调参数：`--top 4` 深读页数｜
`--cands 12` 粗筛候选数｜`--no-images` 不出图片。

### 3. 看指定页

```bash
python scripts/show.py "你的文件.pdf" --pages 6,33 [--dpi 220]
```

高清渲染指定页，无需先建索引。

## 六、目录结构

```
glm-5.3-flash-vision-rag/
├── SKILL.md                  # skill 入口：触发条件 + agent 使用的工作流
├── README.md                 # 本文件
├── scripts/
│   ├── glm_client.py         # API 客户端：推理档位/重试退避/JSON修复/密钥加载
│   ├── ingest.py             # 阶段一：渲染→批量视觉索引→大纲→缓存
│   ├── ask.py                # 阶段二：粗筛→精排→深读→HTML预览
│   └── show.py               # 指定页高清渲染
├── references/
│   └── api-notes.md          # GLM API 实测要点与坑（改代码前必读）
└── .cache/                   # 索引缓存（按 PDF 内容哈希分目录，可随时删）
    └── <sha256前16位>/
        ├── index.json        # 读书卡片 + 文字层 + 大纲
        └── pages/p0001.png   # 每页渲染图
```

产出文件在运行目录 `pdf-vision-out/`：`<书名>_p<N>.png` 和 `<书名>_<问题>.html`。

## 七、成本账（GLM 计费特性）

图片按分辨率计费（约 750 像素²/token，不封顶），本 skill 默认 110dpi 渲染
≈1500 token/页：

| 操作 | API 调用 | 图片 token | 说明 |
|---|---|---|---|
| 索引（120 页，110dpi） | 6 次批量 | ≈18.7 万 | 一次付费，永久复用 |
| 提问 | 2 次 | ≈2~3 万 | 精排 12 图 + 深读约 12 图 |

想更省可用 `--dpi 90` 再降分辨率（文字小的 PDF 不建议低于 100）；扫描版/图表多的
建议 `--dpi 130` 保清晰度。

## 八、GLM API 要点（实测踩坑记录，详版见 references/api-notes.md）

1. **思考无法关闭**：`thinking=disabled` 返回 400。替代：`reasoning_effort`
   三档——`low` 实测零思考 token（批量任务用），深读回答用 `high`
2. **reasoning 计入 max_tokens**：预算不足返回空 content 且 finish=length，
   客户端已自动重试，不要绕过 `glm_client.py` 直接调 SDK
3. **无 Files API**：图片 base64 内联（实测单请求 30 图 OK），原 DeepSeek 版的
   上传断点续传机制不存在也不需要
4. 图片格式 jpg/png/webp 按 data URL 内联即可；无单请求张数硬限制实测通过 30 张

## 九、常见问题

**Q：和 DeepSeek 版怎么选？**
功能等同。经验上 GLM 版页面识别更细（附录/版权分类）、细节描述更丰富；
两套缓存独立，可以用同一本书对照两边答案。

**Q：索引建到一半断了要重来吗？**
按批推进，重跑会继续；已完成的批次结果在内存合并后落盘。极少有页失败时会用
文字层兜底并打印 WARNING。

**Q：PDF 改了一个字，索引会更新吗？**
缓存键是 PDF 内容哈希，内容变了自动另建新缓存。

**Q：扫描版（纯图片无文字层）能用吗？**
能。索引靠视觉阅读；只是本地粗筛少了文字层加持，会更依赖摘要关键词，
通常多一两秒精排兜底，准确性不受影响。

**Q：答案里的页码和阅读器显示的不一致？**
本 skill 用物理页码（第 1 张图=第 1 页）。书籍印刷页码可能从前言后起算，
差一个固定偏移；展示的原图就是证据。
