## 通道 A：kuluer（默认，xs.essclick.com 的搜索后端）

- 入口: `https://xs.essclick.com/`（首页为高级检索表单，其搜索提交到 kuluer.com）
- 直连检索 URL: `https://kuluer.com/scholar?q=<关键词URL编码>&hl=zh-CN`
- 实测状态: HTTP 200，无验证拦截，约 0.2 秒返回（"taurine cat retina" ≈ 11,000 条）
- 数据来源: 页面自述「检索数据来源于 Google Scholar；文献计量数据来源于 OpenAlex」

### 结果条目 DOM（实测定稿）

| 字段 | 选择器/规则 |
|---|---|

### 已知限制（如实告知用户，不冒充）

1. 摘要是**节选**（站点即如此展示），不是完整摘要。需要完整摘要时用「原文直链」打开出版社页面；出版社站点（如 academic.oup.com）常有 Cloudflare 验证 → 触发「暂停等人」协议。
2. 中文为**站点 AI 译文**（页面自述「速读、翻译、概览由 AI 生成，仅供参考」），非人工校对。报告中必须保留此标注。
3. 「✦ 速读」是 AI 生成内容，**不是英文原文**，严禁混入「摘要节选」字段。

## DOM 结构变化时的校准流程（两通道通用）

1. 用无头浏览器打开检索 URL，`document.body.innerText` 前 2000 字判断是否验证/登录拦截；
2. 以结果特征词（如条目里实际出现的期刊名）定位最小条目容器，记录其标签+类名与父容器；
3. 逐字段建立「字段 → 选择器」映射表，更新本文件与 `scripts/search-papers.cjs` 中的 `extractKuluer()`（或新增 `extractXxx()`）；
4. 用一个真实关键词跑 1 页 × 3 条验证 JSON 输出，再恢复批量运行；
5. 校准完成后在本文件记录实测日期与样例关键词。

### ⚠ 结果渲染延迟（2026-10-04 实测，最易误判的坑）

多次观察到同一 URL 在不同时刻的渲染耗时差异极大。一次受控对照实验
（同一共青城词条「牛磺酸 猫」，单页连续观测）结果如下：

| 观测时刻 | 「约 N 条结果」计数 | article 条目数 | 页面状态 |
|---|---|---|---|
| 等待 10s | 无 | 0 | 仍在加载（正文仅 360 字） |
| 等待 20s | 无 | 0 | 仍在加载（436 字） |
| **等待 30s** | **2,840** | **10** | 加载完成（1,423 字） |

结论与处置：

- **「0 条目」不等于「无结果」。** 旧版 `--ready-timeout 20s` 会把站点延迟直接误判为无结果，
  曾导致批量跑时 1/3 关键词被记为 `no_results_unconfirmed`。现已把默认提到 **45s**
  （`--ready-timeout` 可调，勿低于 30）。修复同一批关键词由 8 条 → 12 条、软重试由 2 次 → 0 次，
  总耗时反从 4 分钟降到 40 秒（原先大量时间浪费在无谓的重导航上）。
- 症状若升级为「**全部**关键词 0 条且站点未返回任何计数」，主脚本判定为站点侧疑似不可用
  （**退出码 5**），并在 summary 中明确写「勿据此判定检索式无效」。
- 排查顺序：先加 `--ready-timeout` → 再用已知有效对照词（如 `牛磺酸 猫`，应有约 2,840 条）验证站点本身是否正常 → 最后才怀疑自己的检索式。

| 项 | 实测 | 说明 |
|---|---|---|
| 单页条数 | **10 条/页**（第 2 页稳定读数） | 与 2026-10-04 一致 |
| 首屏渲染 | **分片**：先渲染 3~5 条再补满 | ★ 采样必须**等条数连续稳定 ≥1.5 s**，否则会读到中间态并得出「大页参数生效」的**假差异**（本轮实测踩过，见 CHANGELOG v4.3） |

| `--limit 50` 预期 | ≈ **55 s 以上**（首屏 + 4 次翻页，不含节流间隔） | 由站点侧单页上限与翻页耗时共同决定 |
| 大页参数 | `num` / `pageSize` / `limit` / `count` / `as_sdt` **均未获稳定生效证据** | 不能靠 URL 参数一页拿更多 |

### ★ 归因订正（2026-10-14 第 2 次复测：推翻「突发 ⇒ 持续限流」）

前一版把上述症状记为「**突发访问 ⇒ 站点持续限流**」（冷却 75 s 后仍为 0）。该结论**证据不足，现予撤回**。同日第 2 次复测（3 个关键词 / 20 条中文入库）取得的证据：

1. **同刻对照**：症状出现时，`curl` 对文档页（HTTP 200 / 0.7~16.3 s）与 20 个静态分片（HTTP 200 / 0.47~3.1 s）**全部可达** ⇒ 服务端并未拒绝我们。
2. **零突发也复现**：受控 A/B（同一 URL，仅 `proxy` 一项不同）**两次都成功**（`article=9`、首条标题一致），而当轮 `search-papers` 却失败 ⇒ 失败与「之前访问了多少次」**无稳定相关**。
3. **代理假设已排除**：本机 `http_proxy = http://127.0.0.1:59849`，而 playwright **不读该环境变量**；但 A/B 显示「无代理」（14.2 s）与「显式代理」（10.0 s）**均成功** ⇒ 浏览器可直连，代理非必要条件。
4. **重试确实有效**：第 2 次运行日志为 `retry`（`goto` 超时）→ `soft_retry`（`0 articles, text len 360`）→ **`keyword_done` `count=10`** —— 同一关键词第 3 次尝试拿到满页 10 条。
5. **真实瓶颈是链路抖动**：同一请求耗时 **0.7 s ~ 16.3 s**（≈20 倍波动）。20+ 个分片在一次导航内累计，**很容易吃掉 `goto` 的 30 s 预算**，表现为超时。

**结论（backlog B1 处置 · 订正版）**

- 「**提速**」方向仍**不可取** —— 单页上限 10 条、翻页 ≈12.2 s 属站点侧硬约束，与限流无关。
- 「**降突发**」**不再是针对限流的对策** —— 其依据的「限流」并不成立，故不以此为由变更抓取节奏。
- 真正值得做的是**提高单次运行的容错**：`goto` 超时 / 零条时不轻易终止关键词（`soft_retry` 已具备该能力，实测可救回）。若要变更重试预算，须先证明「提高预算能提升单次成功率」，**无验证门禁前不做抓取行为变更**。

## ★ 站点 AI 翻译链实测（2026-10-16 新增：`/api/ai/translate` 429 与面板失败态）

**背景**：受控 A/B（有头 vs 无头，单变量 `--headless`，每臂 3 次、两臂交错，n=6）**证伪**了
「无头导致中文译文填充率 0%」这一假设 —— 两臂**记录级中文填充率同为 0%**、**动作级触发率同为 100%**，
臂间差异 = 0。真因不在浏览器模式，而在站点侧：

| 端点 | 实测 | 结论 |
|---|---|---|
| `/api/ai/translate` | **429**（连续重试 4 次均 429） | ★ 真因：站点 AI 翻译被限流 / 配额耗尽 |
| `/api/ai/rewrite-query` | 429 | 同族 AI 端点的限流 |
| `/api/proxy/html` | 200 | **检索链正常**（所以英文结果照常拿到） |
| `/api/scholar/annotate` | 200 | 标注链正常 |
| `/api/auth/me` · `/api/auth/refresh` | 401 | 匿名会话（预期，非故障） |
| `/library` | 307 → 登录页 | 需登录，匿名不可用（预期） |

**面板失败态的原文（判据锚点，勿改写）**：原 dump 为三行 —— `✦ AI 翻译 · 中文` / `翻译失败` / `重试`
（面板文本共 **20 字**，不含任何译文结构）。⇒ 提取正则（要求 `标题` + `摘要节选：` 结构）**必然不匹配**
⇒ 记录级中文填充率 **0%**，**与浏览器模式无关**。

**复测与独立测量（2026-10-16 19:09，距 A/B 结束 18:32 相隔 37 分钟）**

| 测量 | 结果 | 含义 |
|---|---|---|
| 浏览器侧面板 | 仍为「翻译失败 / 重试」；`/api/ai/translate` 连续 4 次 **429** | **未恢复**：至少持续 37 分钟，非瞬时抖动（更早 A/B 两臂 r1/r3 亦全 429） |
| `curl GET /api/ai/translate` | **405**（Method Not Allowed） | 端点**存活**、只接受 POST ⇒ 非全局宕机 |
| `curl POST /api/ai/translate`（空体） | **400** | 空体在**限流层之前**即被拒 ⇒ 429 并非「IP 级无差别限流」 |
| `curl GET /api/proxy/html` | 200 | 检索链始终可用 |
| `curl GET /api/auth/me` | **000**（连接层失败） | 匿名直连该端点被拒于传输层 |

**假设（★ 未验证，勿当结论）**：匿名会话对 AI 端点的配额为 0 ⇒ 返回 429（而非 401）。
判别性实验 = **以已登录账号重跑同一探针**；若 429 消失则假设成立。
⚠ 本技能**不做任何绕过**（不代登录、不伪造会话）：无账号即视为该能力不可用，如实告知用户。

**待办**：原计划的「**隔日复测**」本轮**未完成**（仅观测到 37 分钟后仍 429）；是否恢复取决于站点侧的配额 / 会话策略变化。

**判据与处置（v4.7 起）**

- 「**站点译文**」一律取**记录级真值**（该条是否真的带译文），**不得**记为「翻译动作已触发」。
- 失败原因在 PRISMA「异常」列显式标为 `translate:all_failed` 等；整批 0 条译文时报告写入 `summary.warnings`。
- **排查动作**：中文列为 0% 且 `translateStatus` 非 `ok` ⇒ 查 `/api/ai/translate` 状态码与面板文案，
  **不要**去改检索式或选择器（检索链是好的）。
- **不要**据此切换有头 / 无头 —— 实测两臂无差异。

**顺带排除的假设（免得重走）**：有头启动失败（窗口**确实**启动，失败发生在 `page.goto` 超时）·
浏览器无网络（同一浏览器开 `example.com` 951 ms、底站 `xs.essclick.com` 593 ms）·
站点拒绝我们（`curl` 对 kuluer 200 / 0.7~3.3 s）· 本机代理缺失（确有 `http_proxy`，但两臂同条件，不影响结论）。

### ★ 2026-10-24 隔 8 天复测：**仍未恢复**，并补齐三处文档空白

**取证方式**：不猜字段，让站点自己的页面 JS 发请求（headless 打开 `kuluer.com/scholar?q=…`，点「翻译本页结果」，
截获每个 `/api/ai/*` 请求的 **method + postData + status + body**）。证据存档见工作区 `probe-translate-20261024/`。

| 观测项 | 2026-10-24 实测 | 与 10-16 对比 |
|---|---|---|
| `POST /api/ai/translate` | **429 × 10**（一页 10 条记录 = 10 次请求，全 429） | 一致 |
| 响应体 | `{"success":false,"error":{"code":"PROXY_RATE_LIMITED","message":"AI 使用频率或额度已达到上限"}}` | 首次拿到错误码 |
| `POST /api/ai/rewrite-query` | **429**（同族端点） | 一致 |
| 浏览器面板 | 「✦ AI 翻译 · 中文 **翻译失败 重试**」 | 一致，v4.7 `classifyTranslatePanel` 判据有效 |
| `GET /api/ai/translate` | **405** | 一致（端点存活） |
| `POST /api/ai/translate` 空体 | **400** | 一致（限流层之前即被拒） |
| `GET/POST http://xs.essclick.com/api/ai/translate` | **404**（HTML 错误页） | ★ 新事实，见下 |

**三处文档空白（本轮补）**：

1. **主机归属**：`/api/ai/*` 在 **`kuluer.com`**，**不在** `xs.essclick.com`。后者 `/` 返回 200（静态入口页），
   但 `/api/ai/translate` 是 **404** —— 拿错主机会得到「404 不是 429」的假象，误判成「限流解除」。
   传输层探针一律打 `kuluer.com`。
2. **真实请求体形态**：单条记录一次请求，`{"text":"标题：<title>\n摘要节选：<snippet>"}`，
   **不是批量**。故一页 10 条 ⇒ 10 次 POST ⇒ 配额消耗也按条计。
3. **空壳渲染态**：同一 URL 返回 200，但正文仅 ~360 字符、无结果卡片、**整页 0 个 XHR**；
   实测首屏 3 次里 2 次落入该态，第二次导航才就绪（同一 URL 另一次直接渲染出 127,000 条）。
   这不是缺陷而是环境特征 —— **技能已有防线**：`waitReady` 等 `article[id^="r-"]`/「约 N 条结果」/无结果文案，
   无 `article` 时 `soft_retry` 一次，仍空 ⇒ `aborted = no_results_unconfirmed`，计数三态判 `collect_failed`，
   **不会**被记成「0 条」。排查此类失败先加大 `--ready-timeout` 或重跑，**不要改检索式、不要改选择器**。

**结论**：429 与服务端配额/限流相关、与浏览器模式无关，**跨 8 天稳定复现 ⇒ 不是瞬时抖动**。
旧假设「匿名会话 AI 配额为 0」仍未验证（判别性实验需已登录账号）；本技能**不做任何绕过**。

## 已踩的两个工程陷阱（务必记住）

1. **page.evaluate 序列化陷阱**：传给 `evaluate` 的函数在浏览器上下文执行，**不能引用模块作用域的函数/常量**。实测因提取函数引用模块级 `nbsp()` 导致页面内 ReferenceError，又被 `.catch(() => [])` 吞掉 → 表现为"全部关键词 0 条但流程正常结束"。修法：提取函数内部自包含 + 捕获异常写进诊断（不再静默）。
2. **静默降级是头号敌人**：类名（Tailwind 产物）随时会变。因此每次提取都计算填充率，全量跑完做 QC 断言，低于阈值即以退出码 4 显式失败，而不是交付一份"看起来成功、字段全空"的报告。
