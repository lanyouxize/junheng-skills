# 微信「赞和收藏」逐篇自动点击流程 · 设计与实现

> 版本 v1 · 2026-10-23 · 依据：本机真机取证（两个独立后端）+ 联网调研
> 状态：架构与代码已落地并通过失败路径实测；**UI 模板待微信前台干净时校准**

---

## 1. 需求原文与拆解

> 按照所提供图片中的操作步骤，依次点击"我已点赞"的文章，文章按从上到下的顺序排列，
> 每轮仅点击一篇，并确保该篇文章所属公众号尚未在本程序中进行过历史文章采集；
> 只有满足此条件时才执行点击，否则跳过。

拆成 5 条可验收的子需求：

| # | 子需求 | 验收判据 |
|---|--------|----------|
| R1 | 按截图路径进入「赞和收藏」 | 能稳定停在文章列表页，且有页面在位判据 |
| R2 | 从上到下依次处理 | 行的处理顺序与视觉顺序一致，且不跳行、不重复 |
| R3 | 每轮仅点击一篇 | `--max-rounds` 默认 1；一次调用最多产出一次真实点击 |
| R4 | 仅当公众号未采集过才点击 | 判定依据 = 下载根目录子目录名 + manifest 的 account 字段 |
| R5 | 否则跳过 | 跳过也要留决策证据，不是静默忽略 |

## 2. 关键取证结论（决定架构，先看这段）

### 2.1 微信 PC 4.x 是 CEF/Chromium 自绘 UI，控件树不可用

2026-10-23 在本机用**两个独立后端**验证（`scripts/probe_wechat.py`）：

| 后端 | 能看到什么 | 结论 |
|------|-----------|------|
| UIA | `Chrome_WidgetWin_0` → `GlassBrowserFrameView` → `ToolbarView` / `LocationBarView`，以及三个原生按钮（最小化/恢复/关闭） | 只有 Chromium 框架，没有微信内容 |
| MSAA (win32) | `Chrome_RenderWidgetHostHWND` → `Intermediate D3D Window` | 同上，无任何可访问节点 |

另外：微信全部进程**无监听端口**（没有远程调试端口），主窗口 rect 在最小化时会变成 `(-32000,-32000,…)`。

⇒ **`Invoke` / `Toggle` / `SetValue` / `automation_id` 这一套对微信完全无效。**
现有 `clicker.py` 的 UIA 步骤表只能继续用于那个 PySide6 写的下载工具，不能用于微信。

这条结论与联网调研相互印证：`wechatauto-replica`（510★）README 明确记载
「微信4.x 自绘渲染使 UIA 树失效（无 accessibility 节点）」，其代码里保留了
UIA 分支纯粹是为了兼容 3.9.x。

### 2.2 因此采用「截图 + 模板匹配 + 坐标点击」

这是 RPA 社区对微信 4.x 的通用路线（`wechat4-auto` 用 OCR + 坐标点击，
商业案例用 PaddleOCR + DPI 感知 + 多窗口归属检测，均已跑通）。

### 2.3 三个本机实测的工程约束

| 约束 | 现象 | 处置 |
|------|------|------|
| **PrintWindow 拿到全黑** | `BitBlt`/`WM_PRINT` 对 Chromium + GPU 合成窗口返回纯黑图 | 一律用 `ImageGrab.grab(bbox=窗口rect)` 屏幕区域捕获 |
| **截图是合成桌面，会拍到压盖窗口** | 实测：微信窗口被 Windows 设置窗口压住时，截图上部是微信标签栏、中部是设置界面 | 每次点击前重新截图 + 模板校验；发现被盖住就停 |
| **pywinauto 的 rectangle() 对最小化窗口返回 0** | 导致"微信被最小化"和"微信没开"无法区分 | 改用 `win32gui.GetWindowRect` + `IsIconic` |

### 2.4 OCR 暂时不可用（以及为什么不装第三方包）

- 环境里**没有** tesseract 二进制，也没有 `pytesseract`；`node_modules` 里没有 tesseract.js。
- Windows 自带 `Windows.Media.Ocr`（WinRT，支持 `zh-Hans-CN`，已验证可枚举到），
  但它是全异步接口，PowerShell 5.1 需要 `System.Runtime.WindowsRuntime` 程序集提供
  `AsTask` 帮助器；而本机安全策略**禁止运行时加载程序集**
  （`Add-Type` 与 `Reflection.Assembly.Load*` 都被拦）。
- 结论：**不装第三方 OCR 包**（违背项目"拒绝第三方依赖"的验收纪律），
  改用零依赖的「候选集模板匹配」替代，见 §4.3。

## 3. 整体流程设计

### 3.1 在采集流水线中的位置

```
pipeline.py
  preflight ──► scout(新) ──► download ──► clean ──► manifest ──► meta ──► package ──► ingest ──► maps ──► derived ──► export ──► verify
                    │
                    └─ 发现"还没采过的公众号"→ 产出链接队列 → 交给 download 阶段
```

`scout` 插在 `download` 之前，因为它的职责是**发现**：把"我已点赞但还没采过"的号找出来，
再把文章链接喂给已有的下载工具。它不改变后 10 个阶段的任何契约。

### 3.2 状态机（每轮走一遍，失败即停并留证）

```
        ┌──────► INIT        微信进程在不在（不在 → 退出码 6）
        │         │
        │         ▼
        │      ENSURE_WIN   恢复最小化 + 置前 + 确认没被别的窗口盖住
        │         │
        │         ▼
        │      ENSURE_PAGE  确认停在「赞和收藏」页（页面标题模板分 ≥ 0.80）
        │         │ 不在 → 尝试 个人中心 → 赞和收藏；仍失败 → 退出码 3 并留证
        │         ▼
        │      SCAN         截图 → 定位最上方未处理的行 → 取该行公众号名区域
        │         │
        │         ▼
        │      IDENTIFY     公众号名区域 vs 已采集名单渲染出的候选模板，逐一比分
        │         │
        │         ▼
        │      DECIDE       命中且分 ≥ 阈值 → skip；否则 → click
        │         │
        │         ▼
        │      ACT          点击该行 → 等文章页打开 → 回列表
        │         │
        │         ▼
        └──── RECORD        追加一条决策记录（含证据图）→ 进入下一轮
```

**每轮仅一篇**由 `--max-rounds`（默认 1）强制。这是硬约束，不是默认值偏好：
点击后会离开列表页，列表状态、滚动位置都可能变，一次处理多篇会让
"第 N 行"的指代失效。

### 3.3 为什么"从上到下"不需要滚动列表

每轮重新截图、重新定位最上方未处理的行，处理完就结束本轮。
下一轮由调用方再次启动（或 `--max-rounds N` 连续跑）。
这样行的指代始终以"当前视觉最上方"为基准，不依赖跨轮的坐标记忆。

### 3.4 五条实现纪律（每条都对应一次真实故障）

| 编号 | 纪律 | 对应故障 |
|------|------|----------|
| D1 | **每轮重新截图**，不复用上一轮的行几何 | 列表滚动/页面切换后旧坐标全错 |
| D2 | **行内容指纹去重**：只取**文字区**（窗口左沿 → 缩略图左沿），dHash `size=16`（256 位梯度 + 3 位均色），journal 里的指纹不再点第二次 | 同进程多轮把同一行点两遍；含缩略图时 10 行只出 **9** 个唯一指纹 ⇒ 点了 A 行、B 行被当已处理 ⇒ **静默漏采** |
| D3 | **先离页再认页**：点击后等列表信号消失（文章页开）→ **Ctrl+W 关闭文章 tab** → 等信号恢复 | 点完立刻判定"还在列表页"→ 误以为没打开 → 重复点击 |
| D4 | **已采集名单每轮重读**（`refresh_registry`，只在变化时打日志、`grew` 报新增） | 名单只在启动读一次＝过期快照；`--max-rounds>1` 时点完美团同号第二行仍判"新号" |
| D5 | **skip 也推进**：跳过一行后把该行指纹写进内存 `processed`；**同号多行**用账号区域列投影指纹（`ACCOUNT_SAME_MIN=0.85`）在会话内拦截 | ① skip 不推进 ⇒ 每轮重评同一行、原地打转；② 同号占多行 ⇒ 连点同号多篇（该号第一篇刚点完，下载侧还没落盘，按名字比不出来） |
| D6 | **截图前把光标停到屏幕角落**（`vision.park_cursor()`，在 `_capture` 里统一做） | 列表行有 hover 态：鼠标压在某行上会让该行 dHash 变、而行几何 `y1/y2` **完全不变** ⇒ 该行指纹漂移 ⇒ 同一篇被重复点 |

D2 的细节：`dry-run` 只写 `would_click`（不算已处理），真点后才把指纹写进
`processed` 集合与 journal；否则一次预演就会让后续真跑**全部跳过**。

**返回键必须是 Ctrl+W**（`vision.close_tab()`，`--return-key` 默认 `ctrlw`）：
2026-10-23 真跑实测，Escape 与 Alt+Left **在微信 4.x 文章页都无效**（文章页是
主窗口内嵌的 CEF tab，不是浏览器历史），scout 因此卡在 `scout.return_failed`
一次；改 Ctrl+W 后 1.5s 内列表判据恢复（tab=1.0、rows=10）。`esc`/`altleft`
保留为可选项，仅作兜底。

D5 的取舍：`session_keys` 与 `processed` 都**只进内存、不进 journal**。跨进程重启后
skip 行会被重新评估（那个号可能后来采到了）、同号第二行也会重评（第一篇
可能已采完进名单）——这是期望行为，journal 只记真点过的行。

**D6 的实测证据**（2026-10-23，同一行几何 `y1=1097 y2=1155` 完全一致）：

| 光标位置 | 行指纹 |
|----------|--------|
| 屏幕角落 (2,2) | `011000000110…1110000011100000-ddd` |
| **hover 该行** | `011100000111…1111000011110000-ddd` |
| 移开后 | `011000000110…1110000011100000-ddd` |

行几何没变、只有像素变了 ⇒ 只看坐标永远查不出来。而**点击本身就把光标留在
那一行上**，于是"点过的行下次必然匹配不上"——实测 `y1=1097` 与 `y1=324`
各被重复点过一次。修法是把光标停靠放进**截图入口**而不是"点击后移开"：
用户手动停在列表上同样会污染首张截图。

**预演要复现真跑的决策链**：`--dry-run` 也会把指纹与账号 key 记进内存集合，
否则预演里同号多行会连报 N 次 `would_click`，与真跑行为不一致。

### 3.5 配套模块（拟人节奏 / 剪贴板）

| 模块 | 职责 | 关键设计 |
|------|------|----------|
| `scripts/rhythm.py` | 拟人节奏：档位 natural/calm/fast/off；`nap`、写间隔 2.5~6s、120s 窗口 ≤6 次写、jitter ±5px | 状态落盘 + `msvcrt` 文件锁读-改-写（并发下不丢记录）；`off` 档补睡——**功能等待不能被节奏吞掉** |
| `scripts/clipboard.py` | 复制链接取链：`CF_UNICODETEXT`(13)、OpenClipboard 重试 + finally Close、`mp.weixin.qq.com` 校验、reader 可注入 | 剪贴板是全局资源，句柄/重试/校验缺一个就会读到别人的内容 |

## 4. 三个核心判据

### 4.1 "已采集过"怎么判（R4）

`scripts/wechat_favorites.py: collected_accounts()` 取两个来源的并集：

1. **下载根目录的子目录名**（`桌面\下载\食品研发与生产\` → `食品研发与生产`）——
   "这个号已经采过"的最直接证据；
2. **各子目录 `_reports/manifest.json` 里的 `account` 字段**——
   兜住"目录建了但还没下完"的情况。

实测输出：`{"accounts": ["食品研发与生产"], "count": 1}`。

> 新增一个号后，这条名单自动增长，**不需要改代码**。

### 4.2 "在赞和收藏页"怎么判

**主判据**：`templates/page-title.png` 模板分 ≥ 0.80。
**回退判据**：`templates/tab-all.png` ≥ 0.80 **且** 实时检出 ≥ 2 个列表行。

回退判据两半都不可省：tab-all 单独在**聊天页**上能到 0.533（实测），
单靠它会误判；"≥2 行"单独在聊天页也成立（聊天气泡图会被当成行）。

实测证据（2026-10-23）：

| 画面 | title | tab | tab_edge | rows | 判定 |
|------|-------|-----|----------|------|------|
| 收藏页（干净） | — | 1.0000 | — | 10 | 在位（tab+rows） |
| 收藏页被设置窗口压住 | 0.0 | 0.5538 | — | 0 | 不在位（正确拒绝） |
| 聊天页 | 0.0 | 0.5330 | — | 2 | 不在位（正确拒绝） |
| 公众号文章页 | 0.0 | 0.4145 | 0.3339 | 0 | 不在位（正确拒绝） |
| **公众号「关注·最近更新」消息流页** | 0.0 | **0.9652** | 0.8245 | 0 | 不在位（靠 rows=0 兜住） |

最后一行是 2026-10-23 实机复验时抓到的**新风险**：消息流页顶部是
「关注 / 最近更新 / 最近关注」一排 pill 标签，与收藏页的「全部」标签同款，
`tab-all` 模板分高达 **0.9652**（对真收藏页 1.0 只低 0.035）——**tab 分本身
不具备区分力**，这一页被拒完全靠"行检测 0 行"。

⇒ 回退判据真正的判据是 **rows**，不是 tab。若微信改版让消息流的行结构
（标题深墨带 + 短灰摘要带 ≤500px）成立，`tab+rows` 会误判成收藏页、
进而把消息流某行当收藏行点开。彻底修需要给回退判据加**位置锚点校验**
（`tab-all` 的匹配位置按窗口宽度归一后与校准值比），见 §10 已知局限。

### 4.3 "这篇属于哪个公众号"怎么判（无 OCR 方案）

三步：**定位账号文字带 → 比指纹 → 过两道闸门**。

**① 定位账号文字带**（`vision.detect_rows` 的配对规则）

行 = **标题文字带 + 紧随其后的灰色账号带**。不再用「缩略图彩色块」定位：
缩略图只有一部分是彩色的，黑图/灰图的行整段漏检 —— 同一张收藏页（肉眼
10 行）旧算法只检出 **3 行**，70% 的文章永远不会被处理；按文字带配对则
10/10 命中。

| 判据 | 实测值（行0） |
|------|--------------|
| 标题带 | 深墨像素/行 ≥ 8（正文深色，账号名整带 0 个深墨像素） |
| 账号带 | 紧随标题、深墨/行 ≤ 4、宽 30~500px、与标题间距 ≤ 40px |
| 多行标题 | 相邻深墨带行距 ≤ 12px 合并（单行行距实测 11） |
| 颜色 | 账号名纯灰 160，页面底 250 |
| 左界 | 与标题左对齐（437 vs 438） |

左侧「合集 / 赞和收藏 / 最近阅读」分区标签栏靠 `vision._text_left` 在**列**
上排除：列墨量里标签栏峰值 116、正文列峰值 301，取首个 ≥45% 峰值的列
再左让 20px。比硬编码 `0.24W` 稳（标签宽度随文案变）。

**统计区间必须是页面下半部（y 35%~95%）**，这是 2026-10-23 实机补的：
标签栏在顶部且只有 5~6 行字，整页统计时一旦某个标签被**选中**（圆角底色块
+ 深色文字），它的列墨量会顶到 45% 峰值以上 —— 实测窗口 1652×1518 的收藏页
整页算出 **262**（落在「赞和收藏」标签内，正确约 **420**）。后果不是"少一
点边距"，而是文字带横跨进标签栏：

| 后果 | 表现 |
|------|------|
| 条目 1 的账号带混入「赞和收藏」四个深墨字 | `dark/h=22.5 > 4` ⇒ 判"非账号带" ⇒ 条目 1 配对失败 |
| 检出结果变成"从第 2 条开始数 10 行" | **行数看着正常**（10 行），肉眼只看账号框也对，但第 1 条永远不被点击 |
| 第一次真跑的实测 | 点击 y=366 打开的是**第 2 篇**「WorkBuddy 越用越慢」（元码助手），不是第 1 篇 |

改成下半部统计后：同一张图 262 → **420**，检出 **10 行**、`y1` 从 324 → **215**
（第 1 条回来了）；三张负面样本（被压盖 0 行 / 聊天页 3 行 / 文章页 0 行）不受影响。

被排除的非行：标签行「全部/♡/👍」（有深墨、无灰账号带）、底部半截行（无账号带）。
**不做行距投票**：多行标题使行距必然不均（实测 126 与 152 并存），投票会把
真实行当伪行剔除；配对本身已是更强的结构过滤。

> 历史教训：`account_box` 曾按「行中心 ± 固定偏移」猜，标题换行时整个偏移都
> 框到标题上，识别分恒 0.0、账号去重静默失效。位置必须从文字带量出来。

**② 比指纹**（`wechat_favorites.account_score`）

把灰度图二值化成墨迹、裁到墨迹外接框、取**列投影**（宽度归一到 96 格、
去均值、L2 归一），再与候选名渲染图的同款指纹做内积。

为什么不用像素模板匹配（`cv2.matchTemplate`）：实测同一段文字自匹配只有
**0.31**，无关名也有 0.21~0.31 —— **区分度几乎为零**（灰色细字 + 字体渲染
差异把相关分压平了）。列投影只看"每列有多少墨"，对字重/抗锯齿不敏感：

| 度量 | 自匹配 | 最像的无关名 | 余量 |
|------|--------|--------------|------|
| 像素 TM_CCOEFF | 0.31 | 0.31 | ≈0 |
| 二值化 TM_CCOEFF | 0.37 | 0.34 | 0.03 |
| **列投影内积** | **0.82** | **0.26** | **0.56** |

**③ 过两道闸门**（`identify_account`）

```
认 = 最高分 ≥ 0.70  且  最高分 − 第二名 ≥ 0.20
任一条不满足 → 判"新号" → 点击（宁可多点一次，不可漏采）
```

第二道闸门是**必须**的：实测「宠物食品联盟」与「宠物食品商情」前四个字相同，
指纹分只差 **0.008**；改用逐字单元反而让错误名字反超（0.7691 vs 0.7610）。
没有余量闸门就会把新号误判成已采集 → **漏采**（比多点一次严重得多）。

实测决策矩阵（out/wx-fav-clean.png 三行，真名从裁块肉眼核对）：

| 场景 | 名单 | 结果 | 分数 |
|------|------|------|------|
| 真名不在册 | {食品研发与生产, 公众号} | 未知 → 点击 | 0.168 |
| 真名在册、无干扰 | {宠物食品联盟, 公众号} | **宠物食品联盟** | 0.792 |
| 真名在册、有同前缀干扰 | {宠物食品联盟, 宠物食品商情} | 未知 → 点击（安全） | 0.792 |
| 真名在册 | {姚工说添加剂, 食品研发与生产} | **姚工说添加剂** | 0.823 |

> 局限（诚实记录）：这套方法只能分辨**字面差异足够大**的号名。同前缀的号名
> 一律判未知（多点一次）；要真正区分得靠 OCR 或读 DOM，两者当前都不可用。

### 4.4 会话内"同号多行"的实测校准

`ACCOUNT_SAME_MIN = 0.85`，判据是同号两行的**账号区域列投影指纹**内积
（两行文字同源，指纹应当几乎相同；不同号的标准是小）。

2026-10-23 真机 5 轮跑（`--max-rounds 5`，窗口 1652×1518）的实测矩阵，
账号名逐张截图人工核对过：

| round | 账号名（截图核对） | 与已点账号最高内积 | 决策 | 是否正确 |
|-------|-------------------|-------------------|------|----------|
| 0 | 元码思维 | —（首个） | click | ✓ |
| 1 | 元码思维 | **0.8952** | skip | ✓ 同号 |
| 2 | 喵圈研究生 | -0.0607 | click | ✓ 不同号 |
| 3 | 喵圈研究生 | **0.9943** | skip | ✓ 同号 |
| 4 | AI前沿速递 | 0.3718 | click | ✓ 不同号 |

⇒ 同号区间 **[0.895, 0.994]**、不同号区间 **[-0.124, 0.372]**，阈值 0.85 落在
两簇之间，最近余量 **0.52**。单测只覆盖控制流（patch `account_key`），

### 5.1 校准

- `out/wx-reference.png` —— 整页参考图，供人工核对。

### 5.2 证伪测试（关键，防"检测器本身失效"）

2026-10-23 实测踩过的坑：按错误坐标截的"页面标题"模板，实际框到的是
Windows 设置的搜索框。结果遮挡检测对"干净微信"和"被设置盖住的微信"
**都返回 1.0000 分** —— 检测器彻底失效，而表面上看一切正常。

所以每个模板必须**同时**满足三条（判别余量）：

```
在目标页得分 ≥ 0.80   且   在最差无关画面得分 ≤ 0.80
                      且   目标页 − 最差无关画面 ≥ 0.25
```

第三条是 2026-10-23 修的：早期写"无关画面 ≤ 0.50"会把 tab-all 误杀——
它对聊天页能到 0.533，但判别余量（1.0 − 0.533）足够大，是好模板。
换成余量判据后**目标页与无关画面同时高分**的坏模板仍会被抓（余量→0）。

负面样本：`out/wx-negative.png`（被压盖画面）、`out/wx-negative-chat.png`（聊天页）。

实测效果（本次校准，全部通过）：

| 模板 | 目标页 | 最差无关画面 | 余量 | 判定 |
|------|--------|--------------|------|------|
| tab-all | 1.0000 | 0.5330（聊天页） | 0.47 | OK |

历史教训：按错误坐标截的"页面标题"模板，实际框到的是 Windows 设置的搜索框，
结果对"干净微信"和"被设置盖住的微信"**都返回 1.0000** —— 检测器彻底失效
而表面一切正常。所以不通过的模板**不会写入 `templates/`**，只留证据。

## 6. 关键约束

| # | 约束 | 原因 |
|---|------|------|
| C1 | 每轮最多点一篇 | 点击后离开列表页，跨轮坐标指代会失效 |
| C2 | 点击前必须重新截图并校验页面在位 | 截图是合成桌面，压盖窗口会让坐标点错 |
| C3 | 点击坐标必须是**屏幕绝对坐标** | 窗口内坐标要加窗口 rect 左上角；多显示器用虚拟桌面坐标系 |
| C4 | 不新增第三方依赖 | 只用车载的 pillow / opencv-python-headless / numpy / pywinauto |
| C5 | 已采集名单只读，不被本流程修改 | 名单的所有权在下载侧；scout 只读它 |
| C6 | 模板必须过证伪测试（判别余量） | 坏模板会让所有下游判断假阳性 |
| C7 | 账号识别必须过「阈值 + 余量」双闸门 | 假阴性代价 = 重复下载；假阳性代价 = 漏采 |
| C8 | 账号文字带定位失败必须**告警**再兜底 | 静默兜底 = 账号去重失效而无人知情（真实事故） |
| C9 | 最小化哨兵 rect（-32000）必须拒绝 | 拿它算坐标会点到屏幕外，且能骗过"rect 为零"的旧判据 |
| C10 | **选窗只有一条路径**：所有脚本（含 `vision.py shot/rows/occl`、scout）都走 `vision.wechat_window()` | 曾出现 `shot` 用 `find_windows("微信")[0]`、scout 用类名级联——拍出来的证据图和 scout 看到的不是同一扇窗 |
| C11 | **每轮只点一篇，且同号只点一篇** | 同号多行时按"每轮一篇"会连点同号多篇；名单要等下载侧落盘才增长，不能只靠它（见 D4/D5） |
| C12 | **返回列表用 Ctrl+W**，且返回失败要留证 | 微信 4.x 文章页 Escape/Alt+Left 实测无效；返回失败后坐标已失效，硬撑会点错行 |
| C13 | **改检测算法后必须重算 `out/wx-rows.json`** | 校准缓存会把旧算法的缺陷一起缓存下来（如"从第 2 条开始数 10 行"），且窗口宽高一致时会被直接采用 |
| C14 | journal 每条 click 记 `algo`；算法变更时必须告警旧指纹条数 | 行指纹按图形裁切算 dHash，算法一变旧记录全失配 ⇒ 已点过的文章会被重复点一次（实测发生过） |
| C15 | 所有截图必须经过 `_capture`（内含 `park_cursor()`） | hover 态会改行像素而不改行几何，绕过入口截图 = 指纹漂移 = 重复点击，且无法从坐标上看出来 |

## 7. 异常处理

| 异常 | 检测方式 | 处置 |
|------|----------|------|
| 微信没启动 | `wechat_windows()` 为空 | 退出码 6，提示先启动并登录 |
| 微信被最小化 | `IsIconic(hwnd)` / rect 首坐标 ≤ -10000 | 先 `restore()`；仍最小化 → `scout.window_minimized` + 退出码 3（不拿哨兵坐标算点击） |
| 微信被其他窗口压住 | 页面判据不过，或截图空白 | 停止本轮，退出码 3，留 `out/scout-wrong-page.png` |
| 没把微信置前 | `GetForegroundWindow() != hwnd` | 打 warn 继续（坐标点击只要求不被遮挡），但在日志里标注 |
| 不在「赞和收藏」页 | §4.2 判据不过 | 报错并给出手动路径（个人中心 → 赞和收藏）；**不猜坐标** |
| 模板缺失/未校准 | `templates/` 为空或证伪未过 | 直接报错，提示先跑 `capture_templates.py` |
| 行几何缺失 | `out/wx-rows.json` 不存在且运行时检测为 0 行 | 报错，提示先校准；不用"假设行高"兜底 |
| 账号文字带定位失败 | 行检测未配出 `account_box` | 告警后按"新号"点击（账号去重暂不可信，多点一次不漏采） |
| 账号识别余量不足 | 最高分 − 第二名 < 0.20 | 打 `scout` warn，判未知 → 点击（多点一次，不漏采） |
| 列表行数耗尽 | 全部行指纹都在 journal 里 | `all_processed`，退出码 5（部分成功） |
| 点击后文章没打开 | 列表信号未消失（`--open-timeout` 内） | 记 warn，不重试点（避免重复打开同一篇） |
| 返回列表失败 | 离页后信号未恢复（`--back-timeout` 内） | 留证 `out/scout-return-failed-*.png`，退出码 5/3；日志带 `return_key` 便于定位。默认已是 `ctrlw`（Esc/Alt+Left 实测无效），仍失败再试 `--return-key altleft` |
| 未预期异常 | 顶层 try/except | 打 `scout.unexpected` 事件，退出码 3 |

所有事件都是 **JSONL 写 stderr**，决策记录追加到 `out/favorites-journal.jsonl`
（含轮次、行位置、命中账号、分数、决策、原因、证据图路径），可逐条人工复核。

**已验证（本机真机 + 164 个离线单测）**

- 已采集名单正确解析出 `["食品研发与生产"]`；
- 证伪测试能抓住坏模板，且不会误杀 tab-all（判别余量判据，§5.2）；
- 页面判据在四类真实画面上全部判对（收藏页 / 被压盖 / 聊天页 / 文章页，§4.2）；
- **行检测**：真实收藏页 10 行全部检出（旧缩略图法只有 3 行），10 个
  `account_box` 肉眼核对全部框在公众号名行上，无一框到标题/缩略图/左侧标签；
- **账号指纹比对**：决策矩阵四场景全部符合预期（§4.3 表）；
- dry-run 在真实收藏页上正确从上到下走行、指纹互不相同、走完报 `all_processed`。
- **同号多行只点一篇**：`identify_account` 判未知（模拟下载侧未落盘）+ 账号区域
  指纹相同 ⇒ 第 2、3 轮判 skip，`same_account_sim=1.0` 记入 journal（单测夹具穷举）；
- **skip 推进**：跳过后下一轮评估的是下一行（单测断言两轮 fp 不同），不会原地打转；
- **名单每轮重读**：`refresh_registry` 在新增目录后第二次调用即报
  `refreshed=true, grew=["乙号"]`，名单不变时不重复打日志。
- **真机端到端跑通 1 篇**（2026-10-23，窗口 1652×1518，`--max-rounds 1`）：
  `page_check tab=1.0 rows=10` → `decision=click`（y1=215，**第 1 条**）→
  `scout.article_opened` → `scout.back_on_list` → `exit=0`。同一次会话里
  journal 的 `processed=1` 成功跳过了上一轮点过的第 2 条。
- **正文左界**：同一张实机截图，整页统计 262（错，落进标签栏）→ 下半部统计
  **420**；行检出 9 → **10**，第 1 条 `y1` 324 → **215**。
- **返回键**：`Ctrl+W` 后 1.5s 内列表判据恢复；Escape / Alt+Left 实测无效。
- **5 轮连续真跑**（2026-10-23）：`clicked=3 skipped=2 rounds=5 exit=0`，三次
  点击均 `article_opened` → `back_on_list`，无一次返回失败；两次 skip 都是
  `same_account_sim ≥ 0.895` 的真同号（§4.4 表）。
- **算法变更会让旧 journal 指纹失配**：左界修好后每行 y 上移 109px，同一篇
  「WorkBuddy 越用越慢」被重复点了一次；现在 journal 记录带 `algo` 字段，
  启动时 `scout.fingerprint_algo` 告警旧记录条数（只告警、不删记录）。
- **hover 会改行指纹、不改行几何**：`park_cursor()` 进截图入口后，故意把光标
  hover 在 `y1=1097` 那行再截屏，拿到的仍是普通版指纹（`0110…0-ddd`，与光标
  在角落时逐位一致）；`park_cursor` 幂等（已在角落时 0ms 返回）。
- **整页 10 条走完**：三轮共 `--max-rounds 5/5/3`，累计 `clicked=8 skipped=4`，
  每次点击都 `article_opened → back_on_list`，无一例返回失败。
- **行指纹唯一性实测**（同一张真实收藏页、同一批 10 行）：

  | 算法 | 唯一值 |
  |------|--------|
  | 旧：缩略图左沿→窗口右沿 + `dhash(size=8)` | **9 / 10 —— 撞指纹** |
  | 新：文字区（0→thumb_x1-8）+ `dhash(size=16)` | **10 / 10** |

  撞指纹的后果不是"少点一次"，而是**静默漏采**（点了 A 行，B 行被当已处理跳过）。
  左边界必须固定取 **0**：标题首字笔画会让 `title_box[0]` 漂移上百像素
  （实测 262 vs 439），左侧标签栏是静态文字，不影响区分度。
- **单测夹具必须同样"逐行可辨"**：换成文字区指纹后，靠"缩略图配色不同"骗过
  指纹的旧夹具立刻 4 行同值变红——合成页的标题宽度必须**逐行不同**（真实页
  标题本就 8~40 字不等），否则测的是夹具巧合而不是去重逻辑。

**未验证 / 已知局限**

  位置锚点（匹配位置 ÷ 窗口宽度 与校准值比），需要停在收藏页时校准一次锚点；

  一律判未知、按新号点击；要真正区分需 OCR 或读 DOM，当前都不可用；
- **同号多行的"同号"判定依赖账号区域指纹**（≥0.85）：2026-10-23 已在真实画面上
  校准（2 组同号 / 3 组不同号，见 §4.4），余量 ≥0.52；但如果微信改了账号名的
  字号/透明度，自匹配分仍可能整体下移，届时要重新实测 `ACCOUNT_SAME_MIN`；
- 字号/配色阈值（160 灰 / 250 底 / 20px 字高）取自本次截图，若微信改版需重新实测；
- 深色主题未支持（所有模板与渲染都按浅色主题校准）。
