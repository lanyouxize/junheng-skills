## 4. 这条流程为什么值得封装

- 工具本身是**普通 Qt 应用、UIA 树完整**，可以纯模式调用（不抢焦点、不误点），比自绘窗口（如微信 4.x）好驱动得多。
- 人工点一遍的固定动作有 8–12 下，且每次都要重设格式/间隔/时间范围，容易漏勾导致导出格式不对。
- 日志区天然带进度信号，适合做 `wait_log` 断言，避免 `sleep` 猜时间。

## 6. 三条会让人踩坑的引擎行为（都是这次真机逼出来的）

1. **`pywinauto 0.6.9` 的 `descendants()` 不认 `auto_id`**：`IUIA.build_condition()` 只支持
   process / class_name / title / control_type / content_only。传 `auto_id=` 会抛 TypeError，
   而这条异常被"选择器列表兜底"吞掉 → auto_id 静默失效、退到按 index 命中**错误控件**
   （实测：把等待时间写进了日志框）。引擎已改成**枚举 + Python 侧精确过滤 automation_id**。
2. **窗口标题在 UIA 侧会变**：同一个工具窗，一会儿是中文标题，一会儿变成进程名
   `wechatdownload`（PowerShell 的 MainWindowTitle 仍显示中文）。所以匹配以 **class** 为准，
   标题正则只用来排序。
3. **窗口最小化时 UIA 坐标是垃圾**（实测 `-31948,-31426`），但 `invoke` / `toggle` 照样生效 ——
   这正是"模式优先、鼠标垫底"的价值：不需要窗口在前台或可见。

真正可用的两条来源：

| 字段 | 来源 | 写法 |
|---|---|---|
| 文章链接 | 本地 HTML 的 `og:url` | `<meta property="og:url" content="http://mp.weixin.qq.com/s?__biz=...&sn=...#rd">`，需反转义 `&amp;`、去掉 `#rd` |
| 公众号名 | 本地 HTML `id="js_name"` | `<span id="js_name">食品研发与生产</span>` |
| 发表时间 | **本地 HTML 里没有** | `<em id="publish_time"></em>` 是空标签，时间由 JS 运行时填；必须联网抓页面源码的 `var ct = "<unix ts>"` |

联网补时间的注意点（实测）：间隔 1.8s 抓 95 篇，94 篇首次成功；失败那篇返回的是 1.7 万字符的
风控短页（正常页 380 万字符），**重试一次即成功**。所以"单篇失败"应先重试，不要直接标 null；
但连续 3 次失败必须中止，别把号打黑。

幂等主键用 `sn` 参数（`95 篇 → 95 个唯一 sn`），比标题可靠（标题会被改、会被截断）。

## 三个真机故障（2026-10-23，全部修在引擎层）

| 现象 | 根因 | 修法 |
|---|---|---|
| 点了「1.获取公众号id」日志一字不变 | clicker 未做 DPI 感知：UIA 给物理像素、`GetWindowRect` 给逻辑像素 ⇒ 按钮中心算成 (1744,252)，而逻辑窗口只有 (230,65,1234,779) | `clicker._ensure_dpi_aware()`（import 时执行）＋ 点击点必须落在窗口矩形内的守卫 |
| 同上，且旧守卫还报"目标窗口不在前台" | Windows 前台锁让 `SetForegroundWindow` 静默失效；而真实鼠标点击**只认最上层窗口**，与焦点无关 | 守卫改成 `WindowFromPoint` 判归属；activate 抢不到焦点不再抛错（提 z 序即可点） |
| 日志只刷「可以把梯子关了试一试」 | **2026-10-23 更正**：这句是工具**请求失败后**才追加的建议行，不是启动横幅；本项目进程带过去的 `HTTP(S)_PROXY` 只是**可能原因之一**，不是唯一原因（URL 失效同样触发它）。系统代理本身也开着 `127.0.0.1:7890`（`HKCU\...\Internet Settings\ProxyEnable=1`） | `pipeline._clean_env()` 剥掉代理变量 + 设 `NO_PROXY=mp.weixin.qq.com,...`；**但判据必须用正向的「获取公众号历史消息页面成功」**，别拿这句当错误（见下） |

排查手法（可复用）：想确认"点击到底有没有生效"，别猜 —— 拿一个**可逆控件**当探针
（如「只下载原创」复选框），真实点击后回读 ToggleState，0→1 说明点击通路正常，
问题在业务前置条件而不是自动化。

## 假阳性：把工具的启动建议当成了错误（2026-10-23，真机抓到并修掉）

第一版 profile 用 `assert_log: not_contains: [可以把梯子关了试一试, 获取失败]` 来"取 id 失败就
立刻中断"。结果每次运行都在这一步误中断。取证方法：点按钮**前后各读一次日志正文**——启动时
静态横幅只有 3 行（教程/官网/更新，214 字符），点完失败后变成 308 字符，多出来的正是那句建议。

**结论：日志里的建议/横幅是 hint，不是终态。** 用 `not_contains` 做黑名单天然脆弱——只要日志
里出现该字样就中毒，与"当前是否真失败"无关。改成**正向判据**：

```yaml
- name: 等「获取公众号历史消息页面成功」（正向判据）
  action: wait_log
  contains_any: ["获取公众号历史消息页面成功"]
```

失败提示五花八门（未知错误 / 梯子建议 / 超时），黑名单列不全；而成功只有这一句。
`assert_log` 只留给"明确需要人工介入"的死结（「请先在左面打开微信内置浏览器」）。

### 铁律一：时序——预热必须早于点 id，导航必须晚于点 id

工具的「自动获取密钥」只在点完「1.获取公众号id」之后的短窗口内读**一次**微信当前页面。
所以"离开目标页"要发生在点 id **之前**，"导航到 profile_ext"要发生在点 id **之后**。
四次观测把这三种时序分得很清楚：

| 点 id 时微信停在哪 | 之后有真实导航？ | 结果 |
|---|---|---|
| 别号/别页 | 有（跳到目标页） | 成功 |
| 已在目标页 | 无 | 反复刷「请先在微信打开复制的链接」 |
| 已在目标页 | 有，但发生在工具开始读**之后**（在 `open_url` 内部 warmup） | 刷一次「开始获取密钥」后死等 |

所以预热是 profile 里的**独立一步**（第 18 步），排在 `activate` 之前；`open_url` 本身
**不许**带 `warmup`（有断言 `test_target_open_has_no_warmup` 守着）。

预热 URL 用**该号文章页**（`${ARTICLE_URL}`），不要用 `https://mp.weixin.qq.com/` 首页 ——
那是「微信公众平台」扫码登录页，与流程无关（用户 2026-10-23 明确要求不要打开它），
而文章页恰好就是教程说的「先在微信打开该号文章」。

### 铁律二：启动工具的 cwd 必须是 exe 所在目录

| cwd | 结果 |
|---|---|
| exe 所在目录（桌面） | 成功 **3/3** |
| `<下载根目录>` | 失败 **3/3** |
| 全新空目录（Temp） | 失败 |

已排除的候选原因：① 缓存体积（把 489MB 的 `缓存/` 清空无效）；② exe 与 cwd 同目录
（把 exe 复制到下载目录仍失败）；③ 目录内容（空目录同样失败）。闭源工具的黑盒行为，
只能按现象遵守，`pipeline.stage_download` 已把 cwd 固定为 `exe.parent`。

顺带更正一个历史误判：**产物目录不受 cwd 影响**。cwd=桌面时产物仍然落到
`<下载根目录>/<号名>/`（工具自己记住了保存目录），所以当初"用 cwd 保证产物归位"
的做法既不必要、还有害。

### 三条踩过的坑（都写成了断言/守卫）

- **"画面变了"不能证明点对了位置**：早先兜底坐标偏了约 100px，点到「问AI」右侧空白，
  页面照样变了（焦点没动）——所以定位必须以**模板命中**为准，锚点只是模板缺失时的兜底。
- **锚点会漂**：放大镜 x 随标签页数量在 1335~1437 之间浮动，任何"距右边缘恒定 N px"的假设
  都会失效。守卫用真正的不变量：**命中点必须落在标题栏右半部分且 y ≤ 90**。
  早先写的是"必须贴住锚点 ±40px"，结果把**正确命中**判成误匹配，退到错位坐标上（已修）。
- **纯色画面会给出假 1.0**：窗口被遮挡时截到空白/单色，`cv2` 的归一化相关在零方差下返回 1.0，
  命中点落在 (0,0)——那就是窗口左上角。区域守卫正是为这一条准备的。

### 排除过的捷径：工具自带的本地 MCP

作者仓库 `qiye45/wechatDownload` 提供了 `http://127.0.0.1:4545/mcp`（`get_public_account_id`
/ `batch_download_articles` / `export_article_data`），但那需要 5.0 的「启动MCP」开关；
本机 4.0 界面里没有这一项（那个无名 CheckBox 是「打开暗黑模式」），端口 4545 也就始终关闭。

## 仍未解决：取 id 的输入从哪来

- 「1.获取公众号id」**需要「微信文章链接」框里有可访问的文章 URL**（留空点击无任何日志）；
- 链接有两种形态，**短链会失效、全格式稳定**：
  - `https://mp.weixin.qq.com/s/<short>` —— 已实测退化成 2KB「未知错误」页（`curl` 200 但正文是
    错误模板），工具据此判定失败并刷"梯子"提示；
  - `https://mp.weixin.qq.com/s?__biz=...&mid=...&idx=...&sn=...&chksm=...#rd` —— 从已采集 md 的
    `<meta property="og:url">` 里抠出来，实测 200 / 3.85 MB，工具能正常取 id。
    所以**不需要人工到微信里复制新链接**，从历史产物里取 og:url 即可。
- 工具在取 id 失败后会**自行退出进程**（闭源行为，实测两次，均发生在失败后几分钟内）。
  所以"启动工具 → 跑步骤 → 读日志"必须写在**同一条命令**里（进程随外层命令结束被回收）。

所以 scout → download 的交接只剩一件事：拿到该公众号任一**全格式**文章 URL（历史 md 的 og:url
即可）。pipeline 用 `--article-url` 传进去，profile 第 16 步用 `${ARTICLE_URL}` 填写。
