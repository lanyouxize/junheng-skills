## 2. 关键取证：微信 4.x 的「三个点」到底在哪

`wechat_favorites-flow.md §2.1` 的结论仍然成立：微信 4.x 是 CEF/Chromium 自绘，
UIA 控件树里**没有**这些按钮，只能截图 + 模板匹配 + 坐标点击。

2026-10-26 真机（微信窗口 1821×1518，`hwnd=49678424`，窗口矩形 `[740,0,2561,1518]`）
对文章页标签栏做墨迹团块分析（`y∈[10,72]`，阈值 `L<120`），得到连续 x 区间：

```
880..904  文章标题文字的尾部（"...从..."，会随标题长度变化，不可作锚点）
939..966  刷新按钮 ↻       中心 (952, 44)
983..1012 「⊙」更多按钮     中心 (997, 44)   ← 用户说的「三个点」
1033..1054 关闭标签页 ✕     中心 (1043, 44)
1488..1518 放大镜 🔍        中心 (1503, 43)  距窗口右边缘 318px
```

**坑（改之前必读）**：「⊙」的 x 坐标**随标签标题长度变化**（标签条按标题宽度增长），
所以 997 这个数**不能硬编码**。稳定锚点是「⊙ 紧贴 ✕ 左侧 46px」这一相对关系，
实测用模板命中最稳。

### 2.1 真机第二个样本（2026-10-26 21:5x，模板定位，非硬编码）

第一次真机点击时模板给出的实际位置与上面的标定**差了 120px**：

| 项 | 上面那次的样本 | 真机点击时 | 差 |
|----|----------------|-----------|-----|
| ⊙ 中心 x | 997 | **1117** | +120 |
| 「复制链接」中心 x | 678 | **797** | +119 |
| ⊙ 与菜单项 y | 44 / 230 | 44 / 230 | 0 |

两条结论，都是血的教训：

1. **按常数点 997 会点到标签标题文字上**（那个位置是标题的中间部分），菜单根本不会弹出，
   后续必然超时。模板优先不是保险措施，是唯一可用方式。
2. **菜单是跟着 ⊙ 平移的**：⊙ 右移 120，菜单项也右移 119（y 完全不变）。所以
   "菜单项坐标可以硬编码"和"从菜单顶部往下数第 3 行是复制链接"两种写法都会在
   标题长度变化时**静默点到「刷新」**——刷新会重载文章，链接不变但打断后续 cookie 读取，
   是最难查的一类故障。

同一轮真机运行里「复制链接」模板命中分数 **1.00、attempts=1**（第一次就中，没触发
Escape 重试），说明这两个模板对本机微信版本是稳的。两次独立运行都命中
`(1117,44)` / `(797,230)`，可复现。

## 2.2 剪贴板判据：为什么不能用「内容是否变化」

第一版判据是"点复制链接前后，剪贴板文本变了才算成功"。真机第一次跑就撞了假阴性：
点之前剪贴板里**已经是这篇的同一个链接**（前一次人工验证留下的），WeChat 复制后写入
完全相同的字符串 ⇒ 判"没变" ⇒ 失败。

护栏本身要防的风险是真实存在的：**复制其实没生效、剪贴板里还留着上一篇的链接**，
此时若照收就会静默下载错文章。所以不能简单放宽。

正确判据是**换成"事件"而不是"内容"**——用
`user32.GetClipboardSequenceNumber()`（ctypes，stdlib 即可）读剪贴板写入序号：

```
接受 = (seq_after != seq_before 且 内容是合法 /s/ 链接)      # 主分支：修假阴性
    或 (内容 != old 且 内容是合法 /s/ 链接)                  # 兜底：序号 API 不可用/被干扰
失败 = 两支都不成立
```

为什么成立：序号对**任何进程**的剪贴板写入都会 +1，而这一步唯一的写入者是 WeChat 的
「复制链接」，它写的一定是**当前打开的那篇文章**。而"复制没生效"时没人写剪贴板，
**序号不会变**，仍然落到 `unchanged` 判失败 —— 护栏没有被放松。

两个实现约束（踩过才知道）：

1. `seq_before` 必须在**点「复制链接」紧邻之前**取，不能在进程入口取。取太早会被
   无关的剪贴板活动污染，"序号变了"这个信号就失去意义。
2. 序号变但内容为空/非链接时**仍然判失败**（`chain.bad_clipboard`），不能只看序号。

事件名约定：接受→`chain.clipboard_rewritten_same_text`(warn) /
仍失败→`chain.clipboard_unchanged` / 内容非法→`chain.bad_clipboard`。

## 4. 坐标换算

所有窗口内坐标 `(wx, wy)` 转屏幕绝对坐标：

```
abs_x = rect[0] + wx
abs_y = rect[1] + wy
```

`rect` 由 `vision.capture_window(hwnd)` 返回的第二个元素给出（每次现取，不缓存）。
2026-10-26 实测 `rect = (740, 0, 2561, 1518)`，即窗口左上角在屏幕 (740, 0)。

1. 微信 PC 端停在 **赞和收藏** 列表页，窗口不被完全遮挡
   （判断见 `wechat_favorites.page_state()`）。
2. 下载工具（`wechatdownload.exe`）已打开且停在主界面。
3. 列表行几何：`out/wx-rows.json` 只是**兜底缓存**，窗口宽度变了不必重跑校准。
   2026-10-26 更正：早先记的「缓存 1652 宽、当前 1821 宽 ⇒ 0 行」是**错的归因**。
   实测 `rows_for()` 走运行时检测（`source=runtime`），1821 宽下正常识别 10 行；
   当时 0 行的真实原因是**微信停在文章页**而不是列表页。宽度不符只在运行时检测
   失败时才会用到缓存，且会被 `scout.baked_stale` 丢弃。为「对齐宽度」去重跑校准
   反而引入新的不确定性。

## 6. 与「已采集名单」的幂等关系

第 1 步「从上到下点击」天然会重复点到同一个公众号（同一个号在收藏里可能有多篇）。
业务规则是**一个公众号只采一次**，因此：

- 行级指纹 `row_fingerprint()` 只防「同一行重复点」；
- 会话内账号指纹 `account_key()` 防「同号多行」；
- 台账（`out/favorites-ledger.csv`）按 **profile_ext 链接** 二次去重 ——
  同一个号不同文章的 profile_ext 是同一条，这是最可靠的号级主键。

注意这三层都**不能省掉真实的重复下载**：行指纹只管"这一行别点两次"，它不知道
"这篇属于已经采过的号"。叠加 `--range all` 后，同号 3 篇收藏会触发 3 次整号全历史
下载。账号级去重要在第 4 步拿到 `profile_ext` 之后、点「批量下载」之前做 ——
那时判断成本为零。

### 血泪教训：这两步原来没有 `activate`

全表三次真实鼠标点击里，只有「获取公众号id」「批量下载文章」各配了一条 `activate`，
**「设置时间范围」这两步没有**（首次 activate 排在第 20 步，在它们之后）。于是它成了
整张表唯一"在工具可能不在最前时发生的鼠标点击"。

2026-10-26 实测事故：工具窗口被别的窗口盖住时，这一步报 `status: ok 已鼠标点击
(979,694)`，但**单选状态纹丝不动**（点前 `一年内=1`、点后仍 `一年内=1`）。
`WindowFromPoint` 复核发现那三个坐标当时最上层分别是 `Wise Care 365`(hwnd 723044)
和微信窗口 —— 点击落进了**别的程序**。

两条结论：

1. **不能在点击前相信"窗口看起来在前面"**。z 序随时会变（实测同一坐标几秒内从
   Wise Care 365 变成微信）。每步真实点击前都要 `activate` + 核对落点归属。
2. **"日志写 ok" 不等于 "操作生效"**。单选按钮这类控件必须回读选中态，否则静默点空
   是无法察觉的 —— 而后果是采集范围被悄悄换成一个月内，工具照样报"下载完成"。
